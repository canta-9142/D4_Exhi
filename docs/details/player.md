# プレイヤーノードの実装詳細

本節は`player`ブランチの実装を記述する。PSRAM描画の移行は`5570db6`、Preparing画面と準備要求は`0ee62f2`、Finishedと確認表示はその後続の作業を対象とし、mainへのコード取り込み前はソースとの間に差異がある。

## タスク構成

ESP32-S3のデュアルコアとArduino環境のFreeRTOSを利用し、[game.hpp](../../src/player/game.hpp)と[drawing.hpp](../../src/player/drawing.hpp)で更新と描画を別コアに分離している。

| 処理 | 担当 | 所有する状態 |
| --- | --- | --- |
| ゲーム更新 | Arduinoの`setup()` / `loop()` | `PacketQueue`、`PacketAnimation`、デモ、スコア、残り時間、自ノードID |
| LCD描画 | `display_task` | LCD、PSRAMの2面バッファ、`PacketRenderer`、転送処理、各バッファの描画履歴、ソフトウェアTEの状態 |

描画タスクは優先度1、スタック4096Bで作成し、`DISPLAY_CORE = 1 - ARDUINO_RUNNING_CORE`でArduinoタスクと反対側のコアへ配置する。通常の設定ではゲーム更新がコア1、LCD描画がコア0となる。描画側がDMA完了や走査位相を待っている間も、別コアのゲーム更新は進められる。

ゲーム側は16ms以上経過するとアニメーションを更新し、`DisplaySnapshot`を発行する。スナップショットにはカード4件、表示値、自ノードID、押下ビットマスク、フェーズ・操作モード・同期状態、長押し進捗・準備要求の確認待ち、確定結果・終了演出の進捗、確認表示の設定・点滅状態、カウントダウン後の`GO!`表示の有無を格納する。FreeRTOSがバイトコピーできる型であることを`static_assert`で確認している。

受け渡し用のFreeRTOSキューは長さ1で、`xQueueOverwrite()`により未処理の古いスナップショットを最新値で置き換える。描画が追いつかない場合に中間フレームを省略し、古い表示要求を蓄積しない。ゲーム側は描画完了を待たず、描画側はキューが空なら`xQueueReceive(..., portMAX_DELAY)`で待つ。

したがって、更新側は描画処理に対して待ち合わせをしないが、LCD側の処理にはDMA完了待ちと位相待ちがある。16msは更新の目標間隔であって、実表示の62.5FPSを保証する値ではない。アニメーションは実経過時間で進めるので、表示フレームが省略されても時間軸は維持する。

描画タスクは起動表示、固定レイアウト、GSCANの初期推定、最初のスナップショットの描画を済ませてから、ゲーム側へタスク通知を送る。パケットデモの補充タイマー、USBの`hello`送信、押下によるパケット操作はこの通知を受けて開始する。フレームバッファやDMA用メモリの確保に失敗した場合は通知せず、通信の疎通テストも失敗する。

## プッシュスイッチ

[psw.hpp](../../src/player/psw.hpp)の`PSW_PINS`は画面左からGPIO 4、3、2、1。各スイッチをGPIOとGNDの間に接続し、`INPUT_PULLUP`で押下時LOWとして読む。

押下・解放の両方を`CHANGE`割り込みで検出する。ISRは4個の入力状態と各入力の最終変化時刻を、専用の長さ1のFreeRTOSキューへ`xQueueOverwriteFromISR()`でコピーする。複数回の割り込みは最新状態へまとめるので、ゲーム側は20msの安定判定間隔より短い周期で入力を処理する前提とする。描画の起動完了通知とは別経路で、ISRからLCDやパケットキューを操作しない。

ゲーム側の`psw_update()`は、最後の入力変化から`PSW_DEBOUNCE_MS`（初期値20ms）が経過したビットだけを押下状態へ反映し、新規押下を返す。解放も同じ方法で確定するので、長押しでは再送しない。押下状態は既存の描画スナップショットで渡し、描画側は前回と変わったボタンだけを再描画する。自ノードIDが変わった場合は4個とも描き直す。

オフライン用の`PLAYER_PACKET_DEMO`では、起動時に5件を用意し、以後1秒ごとに1件補充する。押した位置を`nodeLayouts`の送信先へ対応させ、先頭を1件削除する。通常ビルドでは同じ送信先で`send`を送り、成功応答後に削除する。同時押しは左側を優先して1件だけ扱い、空キューでは何もしない。

通信処理とキュー操作のホスト検証手順は、後述の「サーバーとの通信」を参照。

## MCUでの描画用パケット管理

[packet.hpp](../../src/player/packet.hpp)の`Packet`は、`uint16_t id`と`NodeId destination`のみを持つ

`PacketQueue`は容量1024件固定のFIFOリングバッファとして扱う。

キューを変更するのはゲーム側のタスクだけとし、通信受信も同じ`loop()`で処理する。描画側にはコピーしたスナップショットを渡すため、`PacketQueue`に複数タスク向けのロックは不要。

## LCD

### 構成と配線

- MCU: ESP32-S3
- LCD: ST7796S SPI接続 4.0" IPS 回転前解像度320×480 (横向き480×320で使用した)
- 描画ライブラリ: LovyanGFX (RGB565・16bit/pixel)
- 書き込みは SPI 80MHz で行っていて、ユニバーサル基板、線長約10cmの配線での動作を確認できている(動作を保証する文言ではない)。
- 当該ディスプレイアセンブリにはTE信号線が出ていなかったため、GSCAN命令(0x45)によるソフトウェアTEを実装しティアリングの軽減を行っている。ただしあらゆる条件下で完全にティアリングを消すということはできなかった。

[display.hpp](../../src/player/display.hpp)ではディスプレイの設定・DMA等に関する記述を行っている。

### 画面配置と画面遷移

横向き480×320の左上を原点とし、`FrameBuffer`がPSRAM上にRGB565の全画面バッファを2枚確保する。LovyanGFXの`Panel_FrameBufferBase`を描画先に使い、スプライトは使用しない。LCDとバッファを操作するのは描画タスクだけである。

Preparingは案内文、両端を指す矢印、2秒で満たすバーを表示する。要求送信後は`CONFIRMING...`、サーバーの`status.ready=true`取得後は`READY`と管理者の開始待ちを表示する。autoは開始待ちのみとし、長押し案内を表示しない。未同期・表示値未取得では同期待ちを優先する。Playingでだけパケットカードを表示する。

PreparingとPlayingなどの画面種別が変わったときは全画面を描き直す。描画先バッファとLCD上の表示はそれぞれ異なる古い画面を持ち得るため、描画と転送の両方で画面種別の変更を検出する。Finishedは同期・STATUS・結果取得の各待機状態を表示し、`summary`取得後に最終スコアと順位、対象外なら`NOT RANKED`を表示する。`status.score`から結果を補完せず、現在の操作モードからランキング資格を変更しない。

通常のPlayingからFinishedへ進んだ場合は、最初の有効な結果を受け取ると1.2秒の演出を行う。スコアはease-outでカウントアップし、後半で順位を下から表示する。演出の進捗はゲーム側の実経過時間で更新し、通信を止めない。再同期・初期同期・再接続では静止表示とし、重複結果では演出を再開しない。演出の開始可否はフェーズ通知を処理した時点の同期状態で判断し、通知を一括・分割のどちらで受信しても変わらない。設定・フェーズ変更・Reset・復旧で演出を取り消す。

結果画面は、右端のボタン（下段の4枠のうちi=3）を押すたびに①スコアと順位、②上位%、③ベストスコアの順に送り、③の次は①へ戻る。`summary.topPercent`がnullで`bottomHalf`がfalse（対象外・手動の終了・記録を使えない起動）では②を飛ばし、①と③を行き来する。ページは筐体だけの表示状態で、サーバーへは何も送らない。操作モードに関係なく送れる。Finishedのボタンは`send`に渡さず、ページ送りにだけ使う。各ページとも右端の枠に`NEXT`、大きな右向きの三角、送れるページの数だけの点を描き、現在のページの点を塗る。Finishedから離れたとき、設定の無効化（identify・configを含む）、新しい同期世代の結果を受けたときは①へ戻す。再同期の`reset`は新しい同期世代なので、復旧後は①を静止表示で出す。押下の立ち上がりは`psw_update()`の結果をスナップショットの発行まで蓄積し、`ResultPager`がページと②の演出の進捗を決める。①以外の間は①の終了演出を止め、①へ戻っても再演しない。①の演出中に押した場合も同じ。ページが変わったときは、ヘッダーより下（y=81〜319、上部とボタン枠）だけを描き直す。

②はボタン枠より上（y=81〜239）に、`TOP 12%`（自ノードの色、文字サイズ4）、`YOU ARE IN THE TOP 12%!`、ベルカーブ、10×10のマスを描く。ベルカーブは標準正規分布`y = exp(-x²/2)`の`x = -3.5〜3.5`を280列で白線で描き、`z = Φ⁻¹(1 - p/100)`より右を自ノードの色、左を暗い灰色で塗る。zは[top_percent.hpp](../../src/player/top_percent.hpp)にp=1〜50の定数表（1/1000単位）で持つ。zの位置に白の縦線と人のアイコンを立てる。マスは左上から行ごとに上位のp個を自ノードの色で塗り、p番目のマスを500msごとに白と自ノードの色で点滅させる。通常のPlayingからFinishedへの遷移で取得した結果（終了演出の対象）で初めて②を開いたときだけ、1秒のease-outで塗りを右端からzまで広げ、マスを順に塗る。再同期・初期同期・再接続で取得した結果と、2回目以降の表示では静止表示とする。演出中の再同期・ページの切替では演出を取り消す。点滅は演出ではなく表示内容の一部として、静止表示でも続ける。

`bottomHalf`がtrue（下位50%）の②は、値を受け取らないので、`BOTTOM 50%`（自ノードの色、文字サイズ4）と、中央に寄せたベルカーブだけを描く。曲線は上位%と同じ形で、左半分（z=0より左）を自ノードの色、右半分を暗い灰色で塗る。人のアイコン、10×10のマス、演出、点滅はない。本文を描くときだけ描き直す。

③はボタン枠より上に、`THIS GAME`・時間帯（`13:00-13:59`の形、`hourBestStart`がnullなら`THIS HOUR`）・`ALL TIME`の3行を、高さ48・間隔52で描く（[display_layout.hpp](../../src/player/display_layout.hpp)の`BEST_ROW_*`）。各行は、行頭に旗・時計・王冠の8×8のドット絵を3倍で描き、1段目に見出し（文字サイズ2）、2段目にスコア（文字サイズ3、nullなら`---`）を出す。`THIS GAME`の行では、スコアに続けて`gameBestNodes`のノードの表示名を、そのノードの色の札（18×24）で並べる。8人の同点と最大スコアでも行に収まる。自分のベストの行は2画素の自ノードの色の枠で囲み、絵と見出しを自ノードの色にして右上に`YOU!`を出す。その他の行は暗い灰色の1画素の枠とする。③に演出はなく、ページ・値・自ノードが変わったときだけ描き直す。

`config.preview=true`では、設定・FIFO・フェーズ取得後に確認専用画面へ切り替える。`IDENTIFY`と自ノードの表示名・色を大きく表示し、500msごとに点滅する。スコア・順位・パケットは表示せず、SENDとREADYおよび結果取得待ちを停止する。通常設定の再通知で解除し、未割当への`identify`では接続待ちへ戻る。

Playingで`status.countdown`が1以上の間は、通常のPlaying画面に代えてカウントダウン画面を表示する。通知された数字を文字サイズ18で、自ノードの色で中央に描き、右上には他の画面と同じく自ノードを表示する。数字は受け取った値をそのまま描き、MCUでは減らさない。数字の表示中に0を受け取ると、Playingのまま`GO!`を0.5秒表示してから通常のPlaying画面へ戻る。`GO!`の期間はゲーム側の`CountdownAnimation`が実経過時間で判定してスナップショットへ渡すので、描画タスクは待たない。表示だけの演出であり、通信の状態は変えない。同期待ち・STATUSの取得待ち・確認表示中は、カウントダウン画面を表示しない。

横方向の走査に合わせて左から右へ列方向DMA転送する。通常描画と列方向転送の向き・色の一致、およびGSCANの位相を進めると明るい領域が左から右へ移動することを実機で確認した。物理リフレッシュ周期の独立測定は行っていない。

### アニメーション

[packet_animation.hpp](../../src/player/packet_animation.hpp)の`PacketAnimation`は、キューの状態からカード位置・透明度を更新する。LCDやFreeRTOSには依存しない。

描画側へ渡す`Snapshot`は、同じ`PacketCard`型の4件固定配列。各カードはパケット、現在Y座標、目標Y座標、有効フラグ、フェード経過時間を持ち、4件とも共通の移動・フェード処理で更新し、同じ描画処理で表示する。

先頭3件にはキューの先頭3件を割り当て、最後の1件にはキューから取り除いたカードを画面外へ移動し終えるまで保持する。

カードの初期状態と目標位置は、キューの変化に応じて次のように決める。

1. 新規pushが表示枠に入る場合: 目標位置に置き、透明度0から255へフェードインする。
2. 4件目以降で待っていたカードが3件目の表示枠へ入る場合: 完全不透明のまま上から落下させる。新規pushとして扱わない。
3. 既存カードの繰り上がり: 現在位置から新しい目標位置へ移動する。
4. popされた表示中カード: 退出枠へ移し、下へ移動させる。Y=240に到達すると無効にする。

新規pushの判定には、パケットIDの大小ではなくpush累計とFIFO上の論理位置を使う。既存カードとの対応付けにはパケットIDを使う。

移動とフェードの両方に、正規化した経過時間`t`（0〜1）に対して次のイージングを使う。

```text
ease(t) = 1 - (1 - t)^3
移動位置 = 開始位置 + (目標位置 - 開始位置) × ease(t)
透明度 = 255 × ease(t)
```

### 差分描画と列方向DMA転送

`display_snapshot.hpp`で画面状態の差分を求め、`drawing.hpp`で描画し、`FramePresenter`で転送する。通常描画では全画面の画素比較を行わない。

- カードは有効フラグ・整数Y・ID・宛先・透明度を比較し、旧位置と新位置のY行を更新する。`PacketRenderer`は更新行だけを消去し、その行へ重なるカードを順に描く。
- ボタンは自ノードや押下状態の変化、数値は値や取得済み状態の変化から更新範囲を求める。
- Preparingは画面状態の変化、バーの進捗、両端の押下状態を分けて更新する。長押し中は案内全体を毎回描き直さない。
- Finishedは表示状態、スコア、順位、演出のラインを分けて更新する。ページの切替では本文全体を描き直す。②の演出中はベルカーブとマスの範囲、点滅では自分のマスだけを更新する。確認表示は点滅時の本文だけを更新する。
- カウントダウンは数字・`GO!`の切替と自ノードの変化で本文だけを更新する。ボタン・スコア・カードの変化では描き直さない。
- 更新矩形を`FrameDamage`の16×16画素タイルへ丸め、同じ16列で縦に連続するタイルをまとめる。丸めた周囲の画素も完成済みバッファから送る。

各バッファには、その面へ最後に描いた`DisplaySnapshot`を対応付ける。backは2フレーム前の画像の場合があるため、backの履歴から新しい状態への差分で描き直す。一方、LCDへ送る範囲は直前の表示状態から新しい状態への差分で決める。処理完了後に履歴を更新し、バッファ間の全画面コピーや更新領域の同期コピーは行わない。

更新がない場合は、描画、バッファ交換、GSCAN読み出し、DMAを省略する。更新時は描画後にバッファを交換し、転送元のfrontは最後のDMA完了まで不変に保つ。

列順への並べ替えには内部RAMのDMA用バッファを2枚使う。一方のDMA転送中に、もう一方へ次の区間の画素を用意する。再使用するバッファと前の転送の完了を確認してから次を送る。全転送完了後にMADCTLの通常設定へ戻す。

パネル操作は[display.hpp](../../src/player/display.hpp)の`ColumnPanel`で扱う。`rotation=1`では転送中だけ`MV`を解除し、論理Yをcolumn、論理Xをrowへ対応させる。他のMADCTLビットは維持し、切替時にウィンドウキャッシュを無効化する。詳細はデータシート[^2]を参照。

#### フェード合成とメモリ

フェードするカードの背景を保存してから不透明で描き、背景を`255 - 透明度`のアルファで重ねる。LovyanGFXと同じ合成処理を内部RAMの一行上で実行し、結果をまとめてPSRAMへ書き戻す。

| バッファ | 用途 | 容量 |
| --- | --- | ---: |
| 480×320のRGB565、2枚（PSRAM） | 表示用frontと描画用back | 614,400B |
| 16×320のRGB565、2枚（内部RAM） | 列方向DMAの準備・転送 | 20,480B |
| 200×60のRGB565背景（内部RAM） | フェード対象の背景 | 24,000B |
| 200画素のARGB行（内部RAM） | フェード合成 | 800B |
| 200画素のRGB565行（内部RAM） | 合成する前景の一行 | 400B |
| 合計 | 画素バッファのみ | 660,080B |

通常モードにはベンチマーク用の全描画比較バッファを確保しない。ゲーム状態、描画履歴、USB受信キュー、JSON行などのメモリはこの表に含めない。

### ソフトウェアTE

TE信号を配線できないため、GSCAN（`0x45`）の読み出し値と時刻から周期・位相を推定し、転送開始時刻を選ぶ。列方向転送と位相調整を組み合わせてティアリングが抑制されることを実機で確認している。

#### GSCAN読み出しで確認した条件

ST7796のGSCAN(45h)命令については、データシートとは異なる手順を要するというTFT_eSPIの著者による実機報告[^1]がある。今回はそれを採用した。

[scanline_reader.hpp](../../src/player/scanline_reader.hpp)の`ScanlineReader`で、読み出し手順と最低待機時間を扱っている。

#### 周期・位相の推定

[scan_timing.hpp](../../src/player/scan_timing.hpp)の`ScanTiming`はArduinoやLCDに依存しない数値処理として分離している。

- GSCAN値を0〜511の512カウントとして扱う。512以上は範囲外として除外する。
- 起動時に64サンプルを取り、読み出し後の待ち時間を5.0 / 6.7 / 9.3msで繰り返す。
- 有効サンプル32件以上、値の広がり256以上を必要とする。
- 周期を6〜24msの範囲で探索する。最初は80µs刻み、その最良値の周辺を2µs刻みで探索する。
- カウント値からの位相と経過時間の一致度が0.65以上なら推定を採用する。
- 以後は更新フレームごとの読み出しで位相・周期を少しずつ補正する。周期補正は1回につき最大±2µsとする。
- 位相誤差が周期の35%を超えるサンプルは追従処理に使わない。

実機では約8.75msの周期が推定された。現行の初期値は8.752ms。ただし、これは512カウントモデルに基づくGSCANの推定周期であり、画面の物理的なリフレッシュ周期を独立に測定して確定した値ではない。GSCANと横向き画面のX方向走査との対応も、現在の同期処理で用いるモデル上の仮定である。

#### 転送開始時刻の計画

[soft_te.hpp](../../src/player/soft_te.hpp)の`DisplayTransferTiming`がGSCANを読み、`FramePresenter`が更新範囲に応じて開始時刻を計画する。

1. 表示状態から更新範囲を決め、GSCANを読む。
2. back自身の描画履歴を基準に必要な部分を描き直す。
3. 更新する16列ブロックの物理Xと、実際に送る画素数・区間数を求める。
4. frontへ交換し、最初のDMA用データを用意して最低5msの間隔と目標位相を待つ。
5. DMAと次の区間の並べ替えを重ね、全転送完了後に通常のメモリ順へ戻す。

未更新の列を省略するため、物理的なXの間隔と累積転送時間を分けて計算する。各ブロックの開始下限にはSPIの画素データ量、完了上限には並べ替え時間と区間ごとの余裕も含める。並べ替え時間は実際の転送準備から更新し、旧フレームのプローブ再送による測定は行わない。

| 同期パラメーター | 現在値・扱い |
| --- | --- |
| カウントモデル | 512カウント、480有効ライン |
| ブランキングの見込み | 32カウント分を開始側へ見込む |
| 走査とのガード | 300µsと起動時位相誤差の95%点÷4の大きい方 |
| 並べ替え時間の初期見積り | 0.12µs/画素。実測値の1.25倍が大きければ更新 |
| 区間ごとの追加余裕 | 20µs |
| GSCANから走査原点への追加位相補正 | `DISPLAY_PHASE_CORRECTION_US = 4500` |
| 共通の開始範囲が不成立の場合 | 6.75msの基準オフセットと40カウントの余裕を用いる |
| GSCAN後の最低間隔 | 5ms |

各ブロックが前回走査後・次回走査前に収まる共通範囲が成立すれば、その中央を選ぶ。成立しない大きな更新は基準オフセットへフォールバックする。GSCANが範囲外なら位相待ちをせず最低間隔だけを守る。これらは実機調整を含む推定であり、全更新量でティアリングがなくなる保証はない。

#### 実測結果と検証

2026-10-26のPlaying描画移行時に、通常と同じ経路を使うベンチで部分描画を全描画と画素単位で比較し、転送範囲と各バッファの描画履歴を検証した。カード更新の処理時間は中央値17.0ms、95%点36.2msだった。検証用の描画・比較、USBログ、スケジューラの待機は計測から除いており、表示FPSを測った値ではない。フェード時の重いフレームは残っている。

全画面の前後比較も別のベンチで測定したが、変化が少ない場合の比較自体に約22msを要した。通常描画では状態差分を採用し、この全画面比較を呼ばない。ベンチ用の`FrameDamage::compare()`は再検証用に残している。

## サーバーとの通信

[server_link.hpp](../../src/player/server_link.hpp)でUSB CDC上のJSON Linesを処理する。通常ビルドではデモの自動補充を無効にし、`config`で自ノードIDを設定し、`reset`と`push`で表示キューを更新する。オフラインデモは`player.ino`の`PLAYER_PACKET_DEMO`を定義すると利用できる。

通信処理はゲーム側の`loop()`で1回につき最大4096バイトを読み、改行までバッファへ蓄積する。Hardware CDCの受信キューにも最大1行分を確保し、一括更新中の取りこぼしを防ぐ。JSONの分割受信と複数行の連続受信に対応し、行の途中で1秒間受信が止まると設定を無効化して`hello`から再識別する。起動時は`hello`を送り、設定・同期が完了するまで1秒間隔で`hello`または`resync`を再送する。`reset`は全件検証後に適用し、アニメーションも初期化する。

Preparingのmanualでは、デバウンス済みの両端入力を`ReadyHold`で2秒計測し、`ready(sync)`を一度要求する。途中で片方を離すと進捗を解除する。成立後と設定・Reset・フェーズ変更・復旧時は、両端の解放を確認してから次の計測を許可する。確認待ちは`status.ready=true`で終了し、falseの通知では3秒の期限を延ばさない。期限切れは`resync`で最新状態を取得し、要求を自動再送しない。MCUからモード変更やゲーム開始は要求しない。

Playingのmanualでは、ボタン押下時に先頭パケットの`send`要求を送る。応答待ち中は追加押下を無視し、`result.ok`が真の場合だけ先頭を削除する。3秒の応答タイムアウトと不正な入力は再同期へ移行する。上限値と応答順序の前提は[通信仕様](../spec/player.md)を参照。

`status.countdown`は0〜3の整数を必須とし、欠落・範囲外・型違いは他の不正な`status`と同じく以前の表示値を保持して再同期する。カウントダウン中のFIFOは空のはずだが、取得済みの`countdown`が1以上の間はボタンの`send`を送らない。再同期によるSTATUSの取得待ちでは、保持中の値で`send`を止めない。

`status.rank`はnullか1〜8の整数、`status.gains`は1〜15の整数を0〜16個並べた配列を必須とし、欠落・範囲外・型違いは他の不正な`status`と同じく以前の表示値を保持して再同期する。`status.combo`はまだ読まない。

`config.preview`は必須のbooleanとし、trueはautoでのみ受け付ける。欠落・型違い・manualとの組合せは設定全体を無効化し、`hello`から再識別する。

`summary`はsync・score・rank・eligible・topPercentと、ベストスコアの項目（gameBest・gameBestNodes・hourBest・hourBestStart・hourBestMine・allTimeBest・allTimeBestMine）をすべて検証し、FIFO同期済み・通常のFinished・同期世代一致の場合だけ適用する。対象外のrankは明示的なnullが必須となる。topPercentも必須で、1〜50の整数かnullとし、対象外ではnullだけを受け付ける。bottomHalfも必須のbooleanで、trueは対象者でtopPercentがnullのときだけ受け付ける。ベストスコアは0〜2147483647の整数かnull、gameBestNodesは1〜8を昇順に重複なく並べた配列で、gameBestがnullなら空、整数なら1個以上とする。hourBestStartはhourBestと一緒にnull、整数なら0〜23とする。`*Mine`はbooleanで、trueなら対象者で、対応するベストが`score`と等しくなければならない。nullは`FinalSummary::NO_BEST`（-1）として持つ。不正な通知は以前の正常値を保持して再同期し、形式が正しい古い世代の通知などは無視する。Finishedから離れるときと設定の無効化時に結果を破棄し、Resetで世代が変わったときは再取得する。通常表示でFIFO同期とFinishedが成立してから3秒以内に取得できなければ再同期する。取得待ち中の通常ResetやPHASE・STATUSの再通知では期限を延ばさず、復旧の同期成立後に新しい期限を開始する。結果取得済みの正常な無通信には期限を設けない。

Hardware CDCの接続判定が短時間だけ偽になる場合があるため、100ms連続で未接続となった場合に設定・同期状態・確定結果を破棄し、previewをfalseへ戻す。

### ビルド

LovyanGFXに加えてArduinoJson 7を使用する。ESP32-S3のHardware CDC、CDC On Boot、QSPI PSRAM（`PSRAM=enabled`）を有効にし、プロトコルへデバッグログを混ぜないようにする。設定は[EspressifのUSB CDC資料](https://docs.espressif.com/projects/arduino-esp32/en/latest/tutorials/cdc_dfu_flash.html)と[PSRAM設定](https://docs.espressif.com/projects/arduino-esp32/en/latest/guides/tools_menu.html#psram)も参照。

```sh
nix develop -c arduino-cli lib install ArduinoJson@7.4.3
nix develop -c arduino-cli compile \
  --fqbn esp32:esp32:esp32s3:USBMode=hwcdc,CDCOnBoot=cdc,DebugLevel=none,PSRAM=enabled \
  --build-path /tmp/d4-player-cdc-build src/player
```

### テスト

通信処理は`tests/server_link.cpp`、長押し判定は`tests/ready_hold.cpp`、表示状態と転送時刻は`tests/display_snapshot.cpp`、更新矩形は`tests/frame_damage.cpp`でホスト検証する。以下はplayerブランチのソースを対象に実行する。

```sh
nix shell nixpkgs#gcc -c bash -c '
  c++ -std=c++17 -fno-inline -Wall -Wextra -Werror -fsanitize=address,undefined \
    -I "$HOME/Arduino/libraries/ArduinoJson/src" \
    tests/server_link.cpp -o /tmp/d4-server-link-test &&
  /tmp/d4-server-link-test
'
```

長押しでは2秒境界、片端の遅れ、途中解放、内側ボタン、成立後の解放待ち、時刻周回を検証する。通信テストではREADYの同期世代、STATUSによる確認、3秒の復旧、設定・フェーズ変更・Reset・切断による解除、部分送信、RIDを消費しないことを検証する。カウントダウンでは`countdown`の範囲・型・欠落による再同期と、カウントダウン中の`send`の停止を検証する。結果では`topPercent`の範囲・型・欠落・対象外との組合せによる再同期と、不正時の正常値の保持を検証する。`bottomHalf`の欠落・型と、上位%・対象外との組合せによる再同期も検証する。ベストスコアの項目は、欠落・型・範囲・nullと空配列の組合せ・`*Mine`の条件による再同期を検証し、Finishedではボタンの`send`を送らないことも確かめる。順位と獲得点では、`rank`・`gains`の範囲・型・欠落・要素数による再同期と不正時の値の保持、獲得点の受信順の蓄積と取り出し、設定の無効化で捨てることを検証する。表示状態のテストでは、数字の変化で本文だけを描き直すこと、`GO!`の期間と取消し、通常のPlaying画面へ戻ることを検証する。上位%では、ページの切替・②の演出・点滅ごとの更新範囲、zの定数表、①→②→③→①のページ送り（②を飛ばす場合を含む）と①へ戻す条件（syncの変化・設定の無効化・Finishedから離れたとき）、②の演出を初回の通常遷移だけに限ること、下位50%で②を出して演出・点滅をしないことを検証する。③では、ページ・値・自ノードの変化だけで描き直すこと、行がボタン枠より上に収まること、Finished以外ではページの状態を使わずにそのフェーズの画面になることを検証する。

`tests/player_cdc.py`は通常ファームウェアに対するUSB CDCテスト。自動テストだけでは物理ボタンのSENDを検証しない。`--buttons`を付ける場合は端末の案内に従って操作する。

```sh
nix shell nixpkgs#python3 -c python3 tests/player_cdc.py --port /dev/ttyACM0 --idle-seconds 30
```

`PLAYER_PLAYING_BENCH`をコンパイル時に定義すると、通常の描画経路を使う検証モードを選択できる。`tests/playing_cdc.py`で各画面の差分描画・転送範囲・バッファの履歴を検証する。全描画による参照画像はベンチ中だけ追加のPSRAMへ確保し、通常ビルドには含めない。

```sh
nix develop -c arduino-cli compile \
  --fqbn esp32:esp32:esp32s3:USBMode=hwcdc,CDCOnBoot=cdc,DebugLevel=none,PSRAM=enabled \
  --build-property 'compiler.cpp.extra_flags=-DPLAYER_PLAYING_BENCH' \
  --build-path /tmp/d4-playing-bench-build src/player
```

`tests/preparing_cdc.py`は通常ファームウェアに接続し、実際の両端長押しと`ready(sync)`の送信を確認する。既定では受信1秒後に`status.ready=true`を返し、`CONFIRMING...`とREADYの両方を観察できる。確認後もPreparingを維持し、標準入力の`start`を管理者操作として受けたときだけPlayingへ進める。`start`ではサーバーと同じく`status.countdown`を1秒ごとに3・2・1・0と送り、0の後にパケットを追加する。カウントダウン中に`send`を受け取ると失敗とする。

```sh
nix shell nixpkgs#python3 -c python3 tests/preparing_cdc.py --port /dev/ttyACM0
```

カウントダウンが終わると暫定順位を4位とし、受理した`send`ごとにscoreへ15点を足して`gains=[15]`を送る。標準入力の`rank N`（1〜8、`none`でnull）で順位を、`gain N...`（1〜15を16個まで）で獲得点を送る。`gain`の点はscoreにも足す。

`--ack reject`はfalseを返す拒否応答、`--ack ignore`は応答欠落を再現する。標準入力の`reset`・`auto`・`manual`で解除や操作モードの切替を確認できる。終了時は`identify`で接続待ちへ戻す。

`tests/finished_cdc.py`は通常ファームウェアで、確定結果の最大値・順位対象外・形式検証、同期世代の照合、取得期限と再同期、確認表示の設定・解除を自動検証する。`--visual`では確認画面を維持し、標準入力の`animate`・`unranked`・`preview`・`result`・`top N`・`bottom`・`bests KIND`・`reset`・`duplicate`・`resync`で表示を切り替える。`top N`（Nは1〜50）は上位N%の結果を静止表示で送り、続く`animate`・`duplicate`・`resync`も同じ値を送る。`animate`は`top N`の後なら②の演出も確認できる。`bottom`は値を伏せた下位50%の結果（`bottomHalf=true`）を静止表示で送り、続く`animate`なども同じ値を送る。`result`・`unranked`などは`topPercent`をnull、`bottomHalf`をfalseへ戻す。`bests KIND`は③の値を`other`（他人のベスト）・`mine`（すべて自分、AとCの同点）・`max`（最大スコアと8人の同点）・`none`（すべてnull）に切り替え、新しい同期世代で①から静止表示で出す。以後の結果にも同じ種類を付け、対象外では`*Mine`をfalseにする。`stop`で終了し、接続待ちへ戻す。確認表示中の`resync`コマンドとMCUからの再同期要求では、autoを維持して`config(preview=false)`を再通知し、新しい同期世代と確定結果で通常表示へ戻す。

```sh
nix shell nixpkgs#python3 -c python3 tests/finished_cdc.py --port /dev/ttyACM0 --visual
```

`tests/finished_visual.py`は、この操作ツールの確認表示解除を実機なしで検証する。コマンドとMCU要求の両経路について、操作モードの維持、再設定・同期・結果の通知順序と世代の一致を確認する。`top N`・`bottom`・`bests KIND`の値が後続のコマンドでも送られ、範囲外の値を無視すること、すべての結果にベストスコアの項目が付くことも確認する。

```sh
nix shell nixpkgs#python3 -c python3 tests/finished_visual.py
```

実機のUSB CDC自動テストで不正な結果通知の復旧と取得期限、旧世代の無視、確認表示の解除を検証し、目視で最大スコア、終了演出、順位対象外、ノード名の点滅に欠けや重なりがないことを確認した。

描画ベンチはPlaying・PreparingにFinishedと確認表示を加え、最大スコア、全順位、順位対象外、待機状態と画面遷移を含む10場面・320サンプルを検証する。2026-10-27に実機で全320サンプルの参照画像との一致、転送範囲、両面の描画履歴を確認した。

通常のFinished演出はスコア`2147483647`・順位2・manual・同期済みに固定し、ウォームアップ2枚の後に進捗を更新する32サンプルを測る。全順位・順位対象外・同期待ち・画面遷移は別の場面で検証し、通常演出の計測には混ぜない。この条件でのFinished更新処理は中央値34.4ms、95%点37.0msだった。参照画像との比較は描画・転送の計測時間から除外しており、表示FPSの測定ではない。

`PLAYER_FRAMEBUFFER_BENCH`と`tests/frame_buffer_cdc.py`は、全画面転送と画素比較による差分転送の測定用。通常のゲーム通信とは別モードなので、通常のサーバーへ接続して使わない。
