# LEDノード

## LEDノードとLEDテープの対応

LED制御ノードは、制御用マイコン(ESP32-C3)及びレベル変換回路、ACアダプターによる電源供給を備えた基板である。通常構成はB1・B2・B3・P1・P3・P5・P7の7台とし、プレイヤー基板8台と合わせて物理MCUは計15台となる。P1・P3・P5・P7のLED制御基板は、同名のプレイヤー基板とは別の物理基板である。

Botのゲーム処理はサーバーが実行する。B1〜B3の3台は担当リンクのLEDとシグナルタワーを制御し、Bot処理専用のMCUを追加する構成にはしない。各LED制御基板の担当リンク・出力の一覧を以下に示す。

## シグナルタワー

シグナルタワーは、ボットノードの上に一周するように設置されたLEDテープで、各ボットノードのバッファの埋まり具合を示す。0~1件なら青、2件なら緑、3件なら黄色、4件なら赤に点灯する。

60LED/mのテープを使用する。

## パケット経路の点灯パターン

30LED/mのテープを使用する。

1フレームを10msとして1フレームごとに点灯位置を1つずつ移動させる。
尾の長さを10LEDとして、最高輝度255、最低輝度0でおおよそでよいので等比的に減衰させる。

点灯色はパケット目的地のノードに対応する色で点灯させる。

サーバーからの命令によっては点灯するLEDの位置が被ってしまう場合があるはずだが、この場合は両者を加算した値で点灯させる。加算した値が255を超える場合は255で飽和させる。

# サーバー↔LEDノード間通信インターフェース

## 基本仕様

- 通信経路: USB CDC
- データ形式: 改行区切り独自プロトコル。ただし識別要求`identify`はプレイヤーMCUと共通のJSON形式
- MCU: ESP32-C3, Arduino
- サーバー: 同

## メッセージ形式

文字コードはASCIIとし、送信時はLFで終端する。受信時はLF・CRLFを受け付け、終端のLF・CRLFを除く1行の上限を96バイトとする。共通のJSON形式の識別要求`identify`も、この文字コード・行長・終端の規則に従う。

独自プロトコルの送信時は、命令・引数の間を単一スペースで区切る。受信時は前後のスペース・タブと、区切りとしての連続スペース・タブを受け付ける。空行とスペース・タブだけの行は無視する。各命令の引数はすべて必須とし、不足・余分な引数は不正とする。独自プロトコルの命令名は大文字、DIRECTIONとPREVIEWは小文字とし、大文字・小文字を区別する。

途中で分割された行は終端まで蓄積し、連続する複数行は受信順に処理する。通信路にデバッグログを混在させない。識別要求`identify`だけは次節のJSON形式で受信し、その`type`は小文字の`identify`とする。

```txt
OPERATION OPTIONS
```

## 接続・識別

サーバーは新しいシリアルセッションで接続先の種別が未確定でも、次の共通識別要求をLF終端で直ちに送信し、有効な識別応答を受信するまで1秒間隔で再送する。

```json
{"type":"identify","data":{}}
```

この要求のJSONオブジェクトの構造・型・必須フィールド・追加フィールドの扱いは[プレイヤー通信仕様のJSON形式](./player.md#json形式)に従う。文字コード・行長・終端は本仕様のメッセージ形式に従う。LED制御MCUは全状態で有効な`identify`を受け付け、下記の初期化後に直ちに`HELLO UID`をLF終端で返す。繰り返しの要求にも毎回応答する。

サーバーはJSON形式の`hello`をプレイヤーMCU、`HELLO UID`をLED制御MCUの識別応答として受け付け、有効な応答の形式から種別を確定して`identify`の再送を停止する。識別前の不正な入力では種別を確定せず、入力を破棄して識別要求を継続する。種別確定後は対応する通信仕様に従って設定・同期へ進む。

同一セッション・同一UIDの`HELLO`再受信は正常な再識別として扱い、セッションと対応表を維持して通常の設定手順を再実行する。未割当なら管理操作または自動仮割当を待つ。同一セッションで異なるUIDを名乗った場合はセッションを終了する。異なるセッション間のUID重複では、サーバー仕様の既存Session IDを維持する規則をLEDにも適用する。

### MCUの起動・識別・切断

| 状況 | MCUの動作 |
|---|---|
| 起動時 | preview=false、全出力消灯、ノード設定なし・演出なしで開始。シリアル接続が利用可能になったら直ちに`HELLO UID`を送る |
| 有効なidentify受信（全状態） | preview=falseへ戻して確認周期を停止し、全出力を消灯。ノード設定・演出・尾・混雑度の表示状態・受信中の部分行を初期化して未設定へ戻す。直ちに`HELLO UID`を返し、再送周期を開始 |
| 未設定 | 有効な`CONFIG`を受け取るまで1秒間隔で`HELLO UID`を再送。`LIGHT`・`BUFFER`は適用しない。有効な`CLEAR`は受け付けて消灯を維持 |
| 有効なCONFIG受信 | NODE・PREVIEWを一括適用し、表示・演出状態を初期化して設定済みへ移る。preview=trueなら確認周期を開始、falseなら通常表示へ移る。`HELLO`の定期再送を停止し、この命令への`HELLO`応答は送らない |
| 不正なCONFIG・命令を判別できない入力・受信異常 | preview=falseへ戻して確認周期を停止し、全出力を消灯。ノード設定・演出・尾・混雑度の表示状態を無効化し、未設定へ戻して`HELLO UID`で復旧。受信行の破棄は「不正データと受信異常」節に従う |
| USB CDCの未接続を100ms連続して検出 | preview=falseへ戻して確認周期を停止し、全出力を消灯。ノード設定・演出・尾・混雑度の表示状態・受信中の部分行・行破棄状態を初期化。再接続後は直ちに`HELLO UID`を送り、識別から再開 |

`identify`と受信異常からの復旧ではUIDとシリアル接続を維持する。受信異常で設定済みから未設定へ移る場合は直ちに`HELLO UID`を送り、有効な`CONFIG`まで1秒間隔で再送する。既に未設定の場合は既存の再送周期を維持する。短い切断をMCUが検出できなかった場合も、新しいサーバーセッションの`identify`で未設定へ戻して再識別する。

設定済みの通常の無通信状態にはタイムアウトを設けず、NODE・PREVIEWと表示状態を維持する。preview=falseでは実行中の演出を通常どおり進め、preview=trueではMCU内の確認周期を継続する。通常の`LIGHT`の終了後に消灯することは演出処理とし、通常のシグナルタワーは次の`BUFFER`・`CLEAR`・`CONFIG`・`identify`、切断、または受信異常による未設定への移行まで表示を維持する。

通常の設定時の命令順序は「UIDの割当と基板交換」節、ゲームReset時は「CONFIGの適用とゲームReset」節、不正な入力は「不正データと受信異常」節に従う。

## UIDの割当と基板交換

UIDとLED制御ノードIDは一対一に対応付け、サーバーが管理する。割当先は上記の担当リンク表にあるB1・B2・B3・P1・P3・P5・P7とする。プレイヤーMCUの割当とは別に管理し、機器種別をまたいで割り当てない。

初めて識別したUIDには、Preparing・Finishedで既存の対応を上書きせず、空いているLED制御ノードIDを自動で仮割当し、下記の通常設定手順を行う。「実機の確認表示」節の手順で実機の配置を確認し、管理者がWeb管理画面から本番の割当へ変更する。仮割当は通常の対応表を使用し、専用の確定操作は設けない。

管理画面からは空いているIDへの割当・移動・解除に加え、2台の割当を一括で交換する操作と、予備基板への付け替えを行える。変更はPreparing・Finishedでのみ受け付け、サーバー仕様の[割当・交換規則](./server.md#421-デバイスの割当交換)に従う。予備基板への付け替えでは旧UIDを未割当にし、新UIDへ同じ役割を引き継ぐ。新UIDに既存の仮割当があれば解除する。

自動仮割当・再接続・担当変更時の通常設定は、接続済みMCUごとに`CONFIG NODE false` → 新担当がBot用ならそのBotの現在の正本FIFO使用量の`BUFFER`の順に送る。有効な`CONFIG`を受け取ったMCUが確認周期を停止して全出力を消灯し、演出状態を初期化するため、直前の`CLEAR`は送らない。旧担当の`BUFFER`は復旧せず、旧役割の点灯を残さない。未割当になる接続済みMCUへは`identify`を送り、確認表示・一時設定を解除して未設定へ戻す。サーバーは以後の`HELLO`で確認表示を再開せず、通常の未割当機器として扱う。

空きがない場合とPlaying中の初回接続では、管理画面へ公開して未割当で待機させる。切断だけでは割当を解除せず、再接続時は保持している対応を使用する。管理操作で未割当になったUIDは自動仮割当の対象から外し、旧基板が戻っても交換先の割当を奪い返させない。対応表と自動仮割当の対象外UIDはゲームのResetで維持し、[サーバー仕様の保存・復元手順](./server.md#423-デバイス対応表の保存復元)に従って再起動後も復元する。割当変更では、保存成功後に割当先が実際に変わるUIDの確認表示だけをサーバーの確認対象から解除し、割当を確定してから新しい担当の通常設定、または未割当への`identify`を送る。旧担当の表示復旧は省略する。自動仮割当の置換前の保存失敗・置換自体の失敗では未割当で待機し、置換後の親ディレクトリ同期失敗ではサーバー仕様に従ってサーバーを停止する。

## CONFIGの適用とゲームReset

`CONFIG NODE PREVIEW`の2引数を必須とする。MCUはNODEが担当リンク表にあるB1・B2・B3・P1・P3・P5・P7のいずれか、PREVIEWが小文字の`true`または`false`であることを検証し、一括で適用する。PREVIEWの省略や`0`・`1`などの別表記は不正とし、暗黙のfalseとして扱わない。

有効な場合は、旧担当で使用していた出力を含む全出力を消灯し、実行中の確認周期・経路演出・尾・混雑度の表示状態を消去して新しいNODE・PREVIEWへ切り替える。同じNODE・PREVIEWへの再設定でも毎回同じ初期化を行う。PREVIEW=trueなら適用時を起点に確認表示を開始し、falseなら通常表示へ戻る。MCU内の初期値はfalseとする。

Bot用へpreview=falseで設定した場合も、シグナルタワーは次の`BUFFER`を受け取るまで消灯を保持する。MCUが独自に`BUFFER 0`相当の青表示を開始しない。UIDとシリアル接続は維持し、有効な`CONFIG`への応答として`HELLO`を送らない。不正な`CONFIG`は部分的に反映せず、旧設定も信頼しない。preview=falseへ戻して確認周期を停止し、全出力を消灯して未設定へ戻す。「不正データと受信異常」節の`HELLO`再識別を行う。

ゲームのResetではサーバーが確認対象を解除し、接続・識別済みのLED制御MCUへ次を送る。確認中のMCUにはPREVIEW=falseへの再設定、未割当なら`identify`による一時設定の解除を先に行い、MCU内の確認周期を止める。

| Reset前の状態 | Reset時の送信 |
|---|---|
| 通常表示のLED制御P1・P3・P5・P7 | `CLEAR` |
| 通常表示のLED制御B1・B2・B3 | `CLEAR` → `BUFFER 0` |
| 確認中・割当済みのLED制御P1・P3・P5・P7 | 現在の担当の`CONFIG NODE false` |
| 確認中・割当済みのLED制御B1・B2・B3 | 現在の担当の`CONFIG NODE false` → `BUFFER 0` |
| 確認中・未割当 | `identify` |

`BUFFER 0`はゲーム状態の初期化後に送信し、空き状態の青表示へ戻す。正式なUIDの割当、担当NODE、およびシリアル接続は維持する。通常表示中のMCUには`CONFIG`を再送しない。確認解除用の`CONFIG`が消灯も行うため、その直後に`CLEAR`を重複送信しない。経路演出と尾は消去し、過去の`LIGHT`を再現しない。未接続の機器へは送信せず、再接続時に通常の設定手順で初期化後の状態を通知する。

## 実機の確認表示

Preparing・Finishedで接続・識別済みのUIDを管理画面から選択し、`CONFIG NODE true`で確認表示を開始する。全IDが使用中でも、未割当の予備基板を対象にできる。プレイヤーMCUを含めサーバー全体で同時に1台だけを対象とする。確認周期はMCUが管理し、サーバーから確認用の`LIGHT`・`BUFFER`・`CLEAR`を周期送信しない。

確認用ノードIDは、割当済みなら現在の担当、未割当ならLED制御P1とする。開始時は確認用ノードIDの`CONFIG NODE true`を送り、MCUが初期化後に以下の確認パターンを開始する。未割当への`CONFIG P1 true`は一時的な表示用設定とし、P1が使用中でも正式な対応表・既存P1の担当・ゲーム状態を変更しない。未割当のまま確認表示を行い、一時設定を通常の演出通知の送信先として扱わない。

MCUは設定されたNODEの担当リンク表からGPIO0・1の出力を選ぶ。仮割当と現実の配置が異なっていても、この2出力にはLEDテープが接続されていることを前提とする。経路部分には、点灯するGPIOのNEIGHBOR、確認用NODEのDESTINATION、DIRECTION=outgoingの`LIGHT`と同じ演出をMCU内で生成する。

`CONFIG NODE true`の適用時を0msとして、MCUが以下を1秒周期で繰り返す。表はMCU内の表示処理を表し、通信命令の周期送信は行わない。

| 周期内の時刻 | LED制御P1・P3・P5・P7 | LED制御B1・B2・B3 |
|---|---|---|
| 0ms | 前周期の表示・尾を消去し、GPIO0・1の経路演出を開始 | 前周期の表示・尾を消去し、GPIO0のシグナルタワーを赤く点灯、GPIO1の経路演出を開始 |
| 500ms | 全出力を消灯し、演出と尾を消去 | 全出力を消灯し、演出と尾を消去 |

確認用の表示はサーバーの正本FIFO件数・パケット・得点を変更しない。MCUの処理が遅延した場合は、経過した周期をまとめて再生せず、現在の経過時間に対応する周期内の表示だけを反映する。

preview=trueの間も受信・検証は継続するが、通常の`LIGHT`・`BUFFER`は適用せず、確認表示へ混ぜない。`CLEAR`はその時点の表示と演出を消去するが、NODE・PREVIEWと確認周期の起点を変更しないため、次の点灯周期で確認表示を再開する。`CLEAR`だけでは確認モードを解除できない。不正入力からの復旧はpreviewの値によらず「不正データと受信異常」節に従う。

割当済みMCUの確認終了時は、現在の担当の`CONFIG NODE false`を送り、Bot用なら続けてそのBotの現在の正本FIFO使用量の`BUFFER`を送る。未割当MCUへは`identify`を送り、一時的なNODE・PREVIEWを解除して未設定へ戻す。先にサーバーの確認対象を解除し、続く`HELLO`では確認表示を再開しない。ゲームのResetに伴う復旧では初期化後の件数0を使用する。過去の`LIGHT`は再現しない。

担当変更・交換・付け替えによる終了では、新しい担当の`CONFIG NODE false`と新担当がBot用なら`BUFFER`を送り、旧担当の復旧を省く。未割当基板への正式な割当時も確認表示を終了して正式な`CONFIG NODE false`へ置き換える。割当解除によって未割当になる場合は`identify`で一時設定・確認モードを解除する。

対象の切替、割当変更、ゲーム開始・Reset、HELLO再受信、切断時には[サーバー仕様](./server.md#422-実機の確認表示)に従って終了する。確認表示の開始・停止では自動仮割当の対象外UID情報を変更しない。切断時は送信せず、再接続後も確認表示を自動再開しない。

## メッセージ一覧

### LEDノード → Server

- HELLO:
  - UID: プレイヤーMCUと同じく、`ESP.getEfuseMac()`を大文字・ゼロ埋め12桁の16進文字列で表した端末識別子

```txt
HELLO AABBCCDDEEFF
```

### Server → LEDノード

- identify: 共通のJSON形式で識別を要求し、`HELLO UID`での応答を求める

- CONFIG: ノード設定と表示・演出状態の初期化
  - NODE: `B1`・`B2`・`B3`・`P1`・`P3`・`P5`・`P7`のいずれかの文字列
  - PREVIEW: 確認表示を行うかを表す小文字の`true`または`false`。通常はfalse。必須で、省略や数値表記は不正

- LIGHT:
  - NEIGHBOR: 現在のNODEの担当リンク表にある隣接ノードの文字列。対象テープを指定し、自分自身のシグナルタワーは含めない
  - DESTINATION: 点灯色を指定する`P1`〜`P8`・`B1`〜`B3`の文字列。表示色は[プレイヤーノード仕様](./player.md#ノードidと表示)に従う。通常ゲームの最終宛先の制約はルールの正本に従うが、確認表示でBotの色も使用するため通信上は全11ノードを受け付ける
  - DIRECTION: `incoming`または`outgoing`の文字列。次節に従って移動方向を指定する

- BUFFER: (ボットノードのみで有効)
  - COUNT: FIFO使用量を表す`0`〜`4`の1文字の10進数。符号や先行する0を付けず、`CONFIG`のNODEがB1・B2・B3の場合だけ有効

- CLEAR: 全出力の表示を消去し、実行中の経路演出と尾を取り消す。NODE・PREVIEWは変更しない。preview=falseではシグナルタワーも次の`BUFFER`まで消灯を保持し、後続の`LIGHT`・`BUFFER`を通常どおり受け付ける。preview=trueでは次の確認用の点灯周期で表示を再開する

## LIGHTの方向と命令例

経路テープはLED番号0を制御ノード側、最後のLEDを隣接ノード側として設置する。DIRECTIONは制御ノードから見た方向を指定する。

| DIRECTION | 移動方向 | LED番号の進行 |
|---|---|---|
| outgoing | 制御ノード側から隣接ノード側 | 0から最後へ |
| incoming | 隣接ノード側から制御ノード側 | 最後から0へ |

以下はサーバーからLED制御MCUへの命令例で、各行が独立したメッセージである。`CONFIG B1 false`でB1の通常表示を設定し、`LIGHT P2 P7 outgoing`でGPIO3のテープにP7の色をB1からP2へ向かって流す。`BUFFER 2`でシグナルタワーを緑にし、`CLEAR`で全表示・演出を消去する。

```txt
CONFIG B1 false
LIGHT P2 P7 outgoing
BUFFER 2
CLEAR
```

次の例はB1の確認表示を開始し、通常表示へ戻して現在件数2のシグナルタワー表示を復旧する。

```txt
CONFIG B1 true
CONFIG B1 false
BUFFER 2
```

## 不正データと受信異常

MCUは命令全体とすべての引数を検証してから適用する。`CONFIG`以外と判別できる不正な命令（`LIGHT`・`BUFFER`・`CLEAR`の引数の不足・過剰、値・担当リンクの不正、方向が逆の`HELLO`など）は、その行だけを破棄する。設定・表示状態は変更せず、既存の演出は通常どおり進行させる。この場合は`HELLO`を送らない。

不正な`CONFIG`、未知の命令、復号できないJSONなどで命令を判別できない入力、および下表の受信異常は、設定変更を取りこぼした可能性があるため再識別の対象とする。preview=falseへ戻して確認周期を停止し、全出力を消灯。ノード設定・演出・尾・混雑度の表示状態を無効化して未設定へ戻す。設定済みから未設定へ移った時点で直ちに`HELLO UID`を送り、有効な`CONFIG`まで1秒間隔で再送する。既に未設定なら再送周期を維持する。UIDとシリアル接続を維持し、サーバーは同一セッション・同一UIDのHELLO再受信として現在の担当をpreview=falseで再設定する。

入力の検証が行末で完了した場合は、その行だけを破棄して続く行を処理する。すでにLFを受け取った不正な`CONFIG`などを理由に、次の正常な行まで破棄しない。エラー専用の応答は追加せず、不正な入力をそのまま返信しない。診断ログをシリアル通信路へ出力しない。

ASCII外のバイト、NUL、区切りのスペース・タブと終端のLF・CRLF以外の制御文字を含む行も不正とする。96バイトの上限は終端のLF・CRLFを含めずに判定し、96バイトの本文にCRLFが続く行は受け付ける。

| MCUでの検出 | 復旧 |
|---|---|
| 行長超過または使用できない文字 | 消灯・未設定へ移行して`HELLO`再識別を開始。当該行を次のLFまで破棄し、続く行から通常の受信へ戻る |
| 部分行の最後の受信から1秒間データが来ない | 消灯・未設定へ移行して`HELLO`再識別を開始。部分行を捨て、次のLFまで行破棄状態を継続する |

後から到着した当該行の後半を新しい命令として解釈しない。未設定へ戻す初期化でも行破棄状態は解除せず、行破棄中は`CONFIG`・`identify`らしい文字列でも処理しない。LFの次から改めて行として解釈する。行破棄中も`HELLO`の周期再送を続けるため、最初の再設定応答を当該行とともに破棄しても、次の再送で復旧できる。破棄中の各バイトや繰り返しのタイムアウトでは、`HELLO`の再送周期を巻き戻さない。まだ1バイトも受信していない状態や、設定済みの通常の無通信にはこの1秒の受信タイムアウトを適用しない。

サーバー側の受信は次のとおりとする。

| サーバーの状態と入力 | 処理 |
|---|---|
| 種別判別・HELLO待ちに両方の識別形式で不正な入力 | セッションを維持し、有効な応答以外を破棄して`identify`の1秒間隔の再送を継続 |
| 種別判別・HELLO待ちに行長超過・使用できない文字・行途中の1秒の受信停止 | 当該行を次のLFまで破棄し、識別要求を継続 |
| LEDと識別済みの接続から不正な入力、行長超過、使用できない文字、行途中の1秒の受信停止 | `serial`がセッションを終了して`Disconnected`を通知。対応表は維持し、再接続時は通常の識別・設定を行う |

LEDと識別済みの接続では、有効な`HELLO UID`と空行以外の入力を受け付けない。空行・スペースやタブだけの行は状態によらず無視する。種別未確定のサーバー側の受信蓄積上限はプレイヤーも識別できるよう32768バイトとし、文字と書式は両方の識別形式に照らして判定する。LED側で不正な文字でも、有効なプレイヤーのJSONをその理由だけで破棄しない。LEDの`HELLO`候補は本仕様の96バイト上限・文字・引数を検証してから種別を確定する。LEDと識別した後は本仕様の96バイト上限を適用する。サーバーのログは通信路とは別の標準出力へ記録する。

## 同時演出数の上限

`LIGHT`1件を1つの演出として、MCU全体で同時に最大128件まで保持する。GPIOごとの上限ではない。新規`LIGHT`の受理前に終了済みの演出枠を解放し、空きがなければ新しい`LIGHT`だけを破棄する。既存の演出は最後まで再生し、上限超過を理由に設定変更・消灯・エラー応答・再識別を行わない。

上限は表示専用とし、サーバーの正本FIFO・パケット・得点には影響しない。`BUFFER`は演出枠を消費せず、`BUFFER`・`CLEAR`・`CONFIG`は枠が満杯でも通常の検証・処理を行う。有効な`CLEAR`・`CONFIG`、`identify`、切断時および受信異常で未設定へ戻す初期化は全演出枠を解放する。
