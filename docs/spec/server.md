# サーバー側プログラム

## 1. 概要

### 1.1. 目的

本ドキュメントは、ネットワークゲームの進行を管理するサーバープログラムについて、各Goパッケージの責務、外部インターフェース、入力イベントに対する処理、および状態管理の規則を定義する。

各パッケージの内部実装、ゲームルール、MCUとの通信プロトコルの詳細は対象外とする。

ゲームルールの正本は[ゲームのルール](../rules.md)とする。パケット生成、転送優先順位、処理速度の初期値、配送・破棄、得点、上位%およびベストスコアの判定は同文書に従う。本仕様では、それらをサーバーが処理する契機と状態管理の責務を定義する。Botの処理速度は管理操作によって変更できる。

プレイヤーMCUとの通信は[プレイヤー通信仕様](./player.md)に従う。MCUへの筐体の段階・スコア・残り時間・確定結果の通知、長押し（`ready`）とモード選択（`choose`）の受理、練習用キューの同期、および`config.mode`・`config.preview`による操作モードと確認表示の設定を対象とする。

LED制御ノードの担当リンク・GPIO、シグナルタワーの混雑度表示、経路演出、および通信命令は[LEDノード仕様](./led.md)を正本とする。本仕様ではゲーム上の出来事とLED制御要求の対応を定義し、LED数など同文書で未確定の項目は7.1に残す。

### 1.2. 用語

| 用語 | 定義 |
|---|---|
| サーバープログラム | `main`、`app`、`serial`、`web`、`records`で構成されるGoプログラム全体 |
| 実行ホスト | サーバープログラムを実行するコンピュータ |
| 論理ノード | ゲーム内のネットワークを構成する頂点。プレイヤー8個、Bot3個 |
| プレイヤーノード | プレイヤーが操作できる論理ノード |
| Botノード | `app`が自動操作する論理ノード |
| MCU | USB CDCによって接続される物理的な制御デバイス |
| 管理クライアント | `web`へHTTPリクエストを送る管理用端末上のソフトウェア |
| 運転 | サーバー全体の状態。運転中（ネットワークが止まらず、筐体ごとにラウンドを行う）または停止中 |
| ラウンド | 筐体ごとに独立して行う1回の遊び。通常ラウンド（カウントダウン3秒＋ゲーム時間90秒）と練習ラウンド（時間制限なし） |
| 筐体の段階 | 運転中のプレイヤーノードの状態。停止中・待機・モード選択・ラウンド・結果 |
| 練習用キュー | 練習ラウンドの間、実際のFIFOとは別にサーバーが作る、練習者に見せる仮想のパケットのキュー（3.6） |
| ゲーム状態 | 運転状態、筐体の段階、論理ノード、パケット、FIFO、スコア、ゲーム内時間に関する情報 |
| 接続状態 | MCUの識別情報、セッション、接続状況 |
| 同期状態 | `app`が管理する、セッションごとの現在の同期世代、MCUに送信済みの情報と再同期の要否 |
| 入力イベント | `app`に処理を要求する操作、通知、またはTick |
| 状態変更 | 入力イベントの処理によって確定したゲーム状態または接続状態の変化 |
| ゲーム記録 | 終えた通常ラウンド1回分（または旧来の一斉ゲーム1回分）の終了時刻・終了理由と、プレイヤーの最終スコア・ランキング資格・順位 |
| 記録ファイル | ゲーム記録を保存するSQLiteのデータベースファイル |

論理ノードはプレイヤー8個（P1〜P8）とBot3個（B1〜B3）の計11個である。通常構成の物理MCUは次の計15台とし、実行ホストはこの台数に含めない。

| 物理MCUの種別 | 台数 | 割当先 |
|---|---|---|
| プレイヤー基板（ESP32-S3） | 8 | P1〜P8 |
| LED制御基板（ESP32-C3） | 7 | B1・B2・B3・P1・P3・P5・P7 |

Botのゲーム処理は`app`が実行する。B1〜B3のLED制御基板は担当リンクとシグナルタワーの表示を担当し、Bot処理専用のMCUは設けない。プレイヤー基板のP1とLED制御基板のP1は別の物理機器であり、割当先は機器種別とノードIDの組み合わせで区別する。

論理ノードの集合と物理機器の一覧は別に管理する。15台は通常構成の台数であり、未割当の予備基板や交換後の旧基板も機器一覧へ保持できるため、一覧の件数を11件や15件に固定しない。

### 1.3. パッケージ構成

| パッケージ | 責務 |
|---|---|
| `main` | 設定の読み込み、各パッケージの初期化、起動・終了 |
| `app` | ゲーム状態・論理ノード・接続対応付け・同期状態の管理、入力イベントの処理 |
| `serial` | USB CDC接続の管理、メッセージの送受信、通信プロトコルの処理 |
| `web` | 管理クライアントのHTTPリクエスト受付、`app`への操作要求、レスポンスの生成 |
| `records` | 記録ファイルへのゲーム記録の保存と読込 |

`app`はゲームロジックを内包する。`serial`と`web`はゲーム状態を直接変更しない。`records`はSQLiteの読み書きだけを担当し、ベストスコアの集計は`app`が行う（3.5）。`web`は`records`を直接読まず、`app`の`State`から記録を取得する。記録ファイルの確認と展示前の準備には、サーバーとは別のコマンド`records`を使う（3.5.8）。

## 2. 外部インターフェース

### 2.1. 基本規則

- `app`はゲーム状態を変更する操作を直列に実行する。
- `app`は操作要求の成否と、操作に伴う状態変更を区別する。
- `serial`はゲームルールを判断しない。
- `web`はゲームルールを判断せず、`app`の返した結果をHTTPレスポンスへ変換する。
- `app`はゲーム状態と接続状態の整合したコピーを管理クライアントへ提供する。

### 2.2. web → app

| 操作 | 入力 | 戻り値 |
|---|---|---|
| `Execute(ctx, command)` | 管理操作 | 成否・拒否理由 |
| `ExecuteWithResult(ctx, command)` | 管理操作 | 成否・拒否理由と、操作の結果（`SetAllNodesEnabled`だけが結果を持つ） |
| `State(ctx)` | なし | 状態のSnapshot |

`Execute`が受け付ける操作は以下とする。

| 操作 | 引数 |
|---|---|
| `Start` | なし |
| `Stop` | なし |
| `SetNodeEnabled` | 論理ノードID、有効/無効 |
| `SetAllNodesEnabled` | 有効/無効 |
| `ReturnToBot` | プレイヤーノードID |
| `SetBotRate` | BotノードID、処理速度（pkt/s） |
| `SetDeviceAssignment` | Device ID、対応先の種別とノードID（未指定で対応解除） |
| `SwapDeviceAssignments` | 割当を交換する2台のDevice ID |
| `ReplaceDeviceAssignment` | 交換元と交換先のDevice ID |
| `SetDevicePreview` | 確認表示を行うDevice ID（未指定で停止） |

一斉ゲームの`Finish`・`Reset`は廃止した。運転は`Start`で始め、`Stop`で止めるまで続く（3.1）。ラウンドの終わりは、ゲーム時間の経過、プレイヤーの長押し、および`ReturnToBot`・`SetNodeEnabled`などの打ち切りによる（3.1）。

`SetNodeEnabled`の有効は手動操作（受付）、無効は自動操作（ボット固定）を意味する。運転中・停止中のどちらでも受け付ける。無効にしたときに、そのノードでラウンド・モード選択・結果が進んでいれば打ち切って待機へ戻す（3.3）。論理ノード自体の生成・転送処理を停止する操作ではない。

`SetAllNodesEnabled`は全プレイヤー（P1〜P8）に`SetNodeEnabled`と同じ切替を1つの入力イベントとして行う。`Execute`は成否だけを返し、手動にできなかったノードは`ExecuteWithResult`の結果の`Skipped`（ノードIDの昇順。なければ空）で返す。`Execute`は`ExecuteWithResult`の結果を捨てるだけで、既存の呼び出し元の動作は変わらない。

`ReturnToBot`は、指定したプレイヤーのラウンド・モード選択・結果を打ち切って待機へ戻す。操作モードは変えない（手動なら受付を続ける）。「自動」にしてボットに固定する操作は`SetNodeEnabled`が担う。次の人をすぐ受け付けたい場面で、自動へ切り替えてから手動へ戻す2回の操作を要しないようにするためである。

Device IDの対応付けはプレイヤーMCU・LED制御MCUの両方を対象とし、`app`が管理する。初回は4.5に従って空きIDへ自動で仮割当し、管理者が実機の表示・点灯から配置を確認してWeb管理画面から本番の割当へ変更する。管理画面は通常の割当・解除、2台の割当交換、予備基板への交換を上記の操作で要求し、対応表を直接変更しない。LED制御ノードの担当リンクはLEDノード仕様の対応表に従う。

`State`は以下の情報を返す。

| 分類 | 情報 |
|---|---|
| 運転 | 運転状態（停止中・運転中）、運転開始からの経過時間、開始可否（canStart）、開始不可理由 |
| 論理ノード | ID、種別、操作状態、FIFO使用量（実際のFIFO） |
| 筐体 | 各プレイヤーの段階（停止中・待機・モード選択・ラウンド・結果）、ラウンドの種別、カウントダウンの残り秒数、通常ラウンドの残り秒数、段階が時間切れになるまでの秒数 |
| MCU | 識別子、機器種別、割当先の種別とノードID、接続状態（未割当の識別済みMCUを含む） |
| 実機確認 | 現在確認表示中のDevice IDと確認用ノードID（一時設定を含む。対象がなければ未指定） |
| スコア | 各プレイヤーの現在のラウンドの得点。結果の段階では確定した得点と上位% |
| Bot | 各Botの処理速度 |
| 記録 | 直近のラウンド、1時間ごと・通算のベストスコア、記録ファイルを使えるか（使えない場合は理由）、直近の保存の失敗（3.5） |

`web`は管理クライアントからの定期ポーリングに応じて`State`を呼び出す。ポーリングそのものはゲーム状態を変更しない。

開始可否は4.2のStart受理条件から導出する。開始不可理由には、停止中でないこと（運転中）を含める。開始可能な場合は理由を空とする。古いSnapshotによる操作もあり得るため、`app`はStartの処理時点で条件を再検証し、満たさなければ拒否理由を返す。

HTTPエンドポイント、JSON形式、拒否理由とHTTPステータスの対応、および管理画面からの状態取得・再試行は[Web管理API仕様](./web.md)に従う。画面のレイアウトは`web`の担当範囲として別途定義する。

### 2.3. serial → app

`serial`は以下の入力イベントを`app`へ通知する。

| 入力イベント | 内容 |
|---|---|
| `Connected` | シリアル接続が確立した |
| `Disconnected` | シリアル接続が終了した（送信キュー溢れ・書込失敗による終了を含む） |
| `MessageReceived` | MCUからメッセージを受信した |

各入力イベントには、発生元を識別するSession IDを含める。

MCUのDevice IDは識別処理によって取得する。`app`はDevice IDごとに機器種別と割当先の種別・ノードIDを管理し、Session IDと区別する。同じDevice IDでも、再接続時には新しいSession IDを用いる。

### 2.4. app → serial

`app`は`Send(session, message) error`によって、指定したシリアルセッションへのメッセージ送信を要求する。送信キューへの登録に成功した場合は`nil`、失敗した場合は`error`を返す。

`serial`は接続ごとに送信順序を維持する。

`Send`の成功は送信キューへの登録成功を意味し、MCUによる受信完了を保証しない。

送信キュー溢れ、または登録後の書込失敗が発生した場合、`serial`は当該セッションを終了し、`Disconnected`を通知する。終了したセッションへの追加送信は`error`を返す。`app`は通常の切断処理を行い、再接続・識別完了後に現在のゲーム状態へ再同期する。通信失敗によって確定済みのゲーム状態を取り消さない。

メッセージ形式、送信順序、応答・同期・再送処理は、別途定義されたシリアル通信プロトコル仕様に従う。

## 3. ゲーム状態と処理規則

### 3.1. 運転状態と筐体の段階

サーバー全体の状態は、運転中と停止中の2つとする。運転中はネットワークが止まらず、筐体ごとに独立してラウンドを行う（[ゲームのルール](../rules.md#運転とラウンド)）。

| 運転状態 | 動作 |
|---|---|
| 停止中 | パケット生成・転送・スコア更新を行わない |
| 運転中 | パケット生成・転送を続ける。スコアは筐体の段階に従って更新する |

許可する運転状態の遷移は以下とする。

| 操作 | 遷移 |
|---|---|
| `Start` | 停止中 → 運転中 |
| `Stop` | 運転中 → 停止中 |

定義されていない遷移は拒否する。ゲーム時間の経過や管理操作の`Finish`・`Reset`による全体の遷移は設けない。一斉ゲームを廃止し、連続運転に置き換えたためである。一斉ゲームと連続運転を切り替えて両方を持つと、状態遷移・管理画面・通信がすべて二重になる。

サーバー起動時は停止中とし、パケット・FIFO・スコア・タイマーを初期化する。プレイヤーノードは自動操作で開始する（全員自動）。管理者は管理画面の「全員を手動」などで受付にする。4.2.3に従って保存済みの対応表を復元し、保存のない機器は4.5の条件で自動仮割当する。管理者が実機の表示から対応を確認・調整して手動操作へ切り替える。起動直後から全員を手動にしないのは、未接続・未割当の筐体を手動にできない規則（3.3）を変えずに済ませるためである。

運転中の各プレイヤーノードは、筐体の段階を持つ。段階は停止中・待機・モード選択・ラウンド・結果の5つとし、プレイヤーMCUへは`phase`と`status`で通知する。

| 段階 | 通信の`phase` | 転送 | 点 |
|---|---|---|---|
| 停止中 | `Preparing` | 生成・転送しない | なし |
| 待機 | `Idle` | 実際のFIFOを自動（ゲームルールに従う速度）で捌く | 数えない |
| モード選択 | `Select` | 自動 | 数えない |
| ラウンド（通常） | `Playing` | 手動。カウントダウンの開始で自動転送を止める | ゲーム時間中だけ数える |
| ラウンド（練習） | `Playing` | 実際のFIFOは自動のまま。プレイヤーは練習用キューを操作する（3.6） | 数えない |
| 結果 | `Finished` | 自動 | 数えない |

`Preparing`は、かつての一斉ゲームの準備中ではなく、停止中を表す値として残す。

筐体の段階の遷移は以下とする。

| 契機 | 遷移 |
|---|---|
| `Start` | 全プレイヤー: 停止中 → 待機 |
| `Stop` | 全プレイヤー: どの段階からでも停止中（打ち切り） |
| 4.7の条件を満たすREADY | 待機・結果・練習 → モード選択。残り時間は20秒 |
| 4.8の条件を満たすCHOOSE（通常） | モード選択 → 通常ラウンド。3秒のカウントダウンを始める |
| 4.8の条件を満たすCHOOSE（練習） | モード選択 → 練習ラウンド。3秒のカウントダウンを始める |
| モード選択の20秒の経過 | モード選択 → 待機 |
| 通常ラウンドのゲーム時間（90秒）の終了 | 通常ラウンド → 結果。残り時間は30秒 |
| 結果の30秒の経過 | 結果 → 待機 |
| 練習の無操作60秒の経過（3.6） | 練習ラウンド → 待機 |
| `ReturnToBot`、`SetNodeEnabled`（無効）、MCUの切断、FIFOの上限（3.2） | ラウンド・モード選択・結果 → 待機（打ち切り） |

打ち切りでは、結果を確定せず、記録せず、上位%もベストスコアも求めず、`CHEER`も送らない（[ゲームのルール](../rules.md#打ち切り)）。通常ラウンドの途中の得点は捨てる。結果を打ち切っても、結果の確定時に保存した記録は取り消さない。待機に戻ったノードは、自動転送を再開する。打ち切りは運営の事情で起こり、ベストスコア・上位%の対象外になるだけなので、打ち切ったラウンドを`manual`として保存しない。待機に戻るモード選択の20秒と結果の30秒の経過は、打ち切りに含めない。

練習ラウンドの実際のFIFOと練習用キューの分離、練習の`send`、練習の終わり、`status`に付ける`bots`は3.6に従う。

CHOOSEを受理した時刻から3秒間をカウントダウンとし、その終了時刻をゲーム時間の起点（通常）、または練習の`send`を受け付け始める時刻（練習）とする。カウントダウンはPlayingの一部とし、別の段階を設けない。カウントダウン中の通常ラウンドの経過時間は0、残り時間はゲーム時間のままとし、そのノードの得点を数えない。通常ラウンドでは、カウントダウンの開始でそのノードの自動転送を止める。ネットワーク全体は止めないので、そのノードのFIFOにはパケットが届く。カウントダウン中は、SENDを4.4の条件で拒否する。Playingを条件とする受理規則（READYの拒否、切断による打ち切り）はカウントダウン中にもそのまま適用する。READYは、練習ではカウントダウン中も受理する（4.7）。

カウントダウンの残り秒数は`ceil(起点 - 現在時刻)`とし、カウントダウン中は3・2・1、それ以外は0とする。値は4.1の時間進行処理で確定して保持し、`State`と`status`は保持した値を返す。`State`は時間を進めないため、表示はTick（100ms）で確定した値に従う。

カウントダウンを新しいフェーズとしない理由は次のとおり。通常ラウンドと練習ラウンドの両方にカウントダウンがあり、フェーズを増やすと、Web管理API・プレイヤー通信仕様と、`app`のフェーズによる各分岐へ変更が広がる。起点をずらすだけであれば、既存の時間進行処理（4.3）は起点より前に処理する期限がないため変更を要しない。

通常ラウンドのゲーム時間の終了は`app`が経過時間から判定する。結果の段階への遷移後は、MCUの接続・再同期や管理クライアントの状態取得によって確定した得点を変更しない。

通常ラウンドの結果を確定するとき、そのラウンドの得点・上位%・ベストスコアを同じ確定状態から決定する。ラウンドは1人で行うため、順位は付けない（`status.rank`と`summary.rank`は常に`null`）。同じ確定状態から3.5のゲーム記録を作り、保存を要求する。さらに、そのゲーム記録を3.5.5の集計へ加えた後に、3.5.6に従って上位%を、3.5.7に従ってプレイヤーへ送るベストスコアを確定する。同じ確定状態から、5.3に従ってLED制御MCUへ`CHEER`を送る。結果の段階の間は、確定した値を再同期・`State`で変更しない。結果の段階を出るとき（READYで次のモード選択へ移るとき、30秒が過ぎて待機へ戻るとき、打ち切りで待機へ戻るとき）に、上位%とプレイヤーへ送るベストスコアを消す。

### 3.2. 論理ノード

| 項目 | プレイヤーノード | Botノード |
|---|---|---|
| 個数・パケット生成 | ゲームルールに従う（運転中） | ゲームルールに従う |
| 転送方式 | 通常ラウンドのゲーム時間中とカウントダウン中は手動。それ以外は自動 | 自動 |
| 転送順序 | FIFO | FIFO |
| バッファ容量 | ゲーム上は無制限。通常ラウンドの上限は下記 | ゲームルールに従う |
| 経路選択 | 手動時はプレイヤー、自動時は事前計算した優先順位 | 事前計算した優先順位 |

生成元・宛先の条件、転送速度の初期値、転送先の優先順位、パケットロスの判定はゲームルールに従う。

プレイヤーノードの手動・自動は、操作状態（3.3）ではなく、筐体の段階で決まる。手動（受付）のノードも、通常ラウンドが始まるまでは自動で転送する。ラウンドが終わる、または打ち切られると、自動転送を再開する。

Botの処理速度は初期値1pkt/sとし、SetBotRateでノードごとに変更できる。プレイヤーの自動転送速度はゲームルールに従い、SetBotRateの対象としない。

`app`は各パケットについて、所在・FIFO順序に加え、ゲームルールの判定に必要な発信元、宛先、ホップ数、TTL、通過ノードを管理する。MCUは表示用キャッシュを持ち、ゲーム状態の正本は持たない。

PIDは0〜65535の範囲で、運転中に0から昇順に発行し、65535の次は0に戻る。周回の際は、使用中のPID（いずれかのノードのFIFOにある、または転送を処理している途中のPID）を飛ばして採番する。配送・破棄によって採番カウンタを戻さない。`Start`と`Stop`で採番カウンタを0に戻し、運転開始後の最初のパケットのPIDを0とする。ネットワークに同時に存在するパケットはプレイヤーのFIFO（通常ラウンドの上限は1000件）とBotのFIFO（各4件）を合わせても65536件に遠く及ばないので、空きのPIDは必ず見つかる。

連続運転では、一斉ゲームのように1ゲーム1000件の範囲に収まらず、PIDを昇順に発行し続けると約2時間で65536件に達する。そのため周回させる。周回してもPIDを重複して使わない仕組みは、PIDの非再利用ではなく、使用中のPIDを飛ばすことと、同期世代とセッションの照合（4.4）に置く。旧来の要求の照合はもともと同期世代で行っており、PIDの非再利用には頼っていない。プレイヤー通信仕様が求めるPIDの一意性は、同じMCUのキャッシュ内に限る。実際のFIFOのPIDを使用中として飛ばすので、同じMCUのキャッシュ内で重複しない。練習用キューのPIDは別の連番とする（3.6）。

プレイヤーノードのFIFOは、全体をMCUの最大1024件のキャッシュへ同期し、部分キャッシュや分割補充は行わない。キャッシュの上限を超えないよう、通常ラウンドのプレイヤーのFIFOが1000件に達したら、その筐体のラウンドを打ち切って待機へ戻す。この上限は通常ラウンドだけに適用する。通常ラウンドは手動で捌くため、放置された筐体などでFIFOが増え続けるおそれがある。それ以外の段階では、実際のFIFOをサーバーが自動転送で捌くので、上限を設けず、打ち切りの契機にしない。練習中もサーバーが実際のFIFOを自動で捌く（3.6）。FIFOがキャッシュ容量を超えた場合のサーバー動作は本仕様では定義しない。通信データの検証はプレイヤー通信仕様に従う。

### 3.3. ノードの操作状態

プレイヤーノードは手動操作または自動操作で動作し、初期値は自動操作とする。手動は人の参加を受け付ける状態（受付）、自動はボットに固定した状態を意味する（[ゲームのルール](../rules.md#自動操作)）。MCUへの通知は`config.mode`の`manual`・`auto`を用いる。

- 管理者はいつでも、プレイヤーノードを手動・自動に切り替えられる。停止中も同様である。
- 管理者がプレイヤーノードを無効化（自動）すると、`app`は当該ノードを自動操作へ切り替える。ラウンド・モード選択・結果が進んでいれば打ち切って待機へ戻す。以後、READYを受理しない（長押しを受け付けない）。
- 手動にするときは、対応するプレイヤーMCUが接続・識別済みでなければならない。未接続の場合は拒否する。
- 対応するプレイヤーMCUが切断されると、`app`は当該ノードを自動操作へ切り替え、ラウンド・モード選択・結果が進んでいれば打ち切って待機へ戻す。
- 自動操作中もパケット生成、FIFO管理およびゲーム上の転送を継続する。
- MCUが再接続しても手動操作には自動復帰せず、自動操作を継続して`config(mode=auto)`を送信する。手動操作への切替は管理者の操作による。
- 管理者が手動へ切り替えても、そのノードは待機のままである。ラウンドは、プレイヤーの長押しとモードの選択で始まる。
- 管理操作`ReturnToBot`は操作モードを変えず、段階だけを待機へ戻す。
- 得点計算はゲームルールに従う。

管理者の切替はラウンド中にも受け付ける。運営が壊れた筐体を止められないと展示が止まるためである。ゲーム中の切替を拒否していた一斉ゲームの規則は、連続運転では使わない。

ゲーム上の操作状態と、MCUの接続状態は別々に管理する。

### 3.4. 長押しの通知

プレイヤーが両端のボタンを同時に2秒押し続ける操作（長押し）の判定はMCUが担当し、サーバーへは`ready`で通知する。サーバーは、`ready`を「モード選択へ進む合図」として扱う。受理条件と処理は4.7に従う。

一斉ゲームでは`ready`を準備完了の通知とし、サーバーが準備完了状態を保持していた。準備完了を廃止したため、サーバーは長押しの状態を保持せず、`status.ready`は常に`false`とする。

| 契機 | 長押しに関する状態 |
|---|---|
| 4.7の条件を満たすREADYを受理 | モード選択へ移る。READYそのものは保持しない |
| 通常のFIFO再同期、同じ設定の再通知 | 段階を保持 |
| 操作モード変更、MCU切断、対応付けの解除・変更 | 長押しの結果は保持されない。打ち切りの規則（3.1）による |

READYを受理しない場合（自動、運転停止中、受理する段階でないなど）も、MCUへは現在の`status`を返す（4.7）。

### 3.5. ゲーム記録とベストスコア

#### 3.5.1. 保存の時機と内容

`app`は通常ラウンドの結果を確定するとき（3.1）に、確定した得点と同じ確定状態から、1ラウンド分のゲーム記録を作る。通常ラウンドのゲーム時間（90秒）が終わったときに1ラウンドにつき1回だけ作り、`records`へ保存を要求する。打ち切り（管理操作・切断・運転停止・FIFOの上限）と練習は、記録を作らず、保存も要求しない。運転の開始・停止、MCUの切断・再接続・再同期、`State`、および結果の段階中のモード・割当の変更でも、記録を作り直さず、保存も要求しない。

同じ入力イベントの時間進行処理（4.3）で複数のラウンドが終わった場合は、ゲーム時間が終わった時刻の順に、同時刻ならノードIDの昇順に、1件ずつ処理する。1件のゲーム記録の保存と集計への加算（3.5.5）、上位%（3.5.6）とベストスコア（3.5.7）の確定を済ませてから、次の1件に進む。後のラウンドの記録を先のラウンドの集計より前に加えないのは、同点のベストスコアで「先に終わったもの」を採る規則（3.5.5）を、終わった順に適用するためである。

保存は`app`が入力イベントを処理する中で同期的に要求し、その完了後に同じ入力イベントの残りの処理と以後の入力イベントを処理する。保存処理から`app`を呼び出さない。

ゲーム記録は、1件の表`games`と、遊んだプレイヤーの結果の表`results`へ保存する。通常ラウンドの結果は1件である。

| 表 | 列 | 値 |
|---|---|---|
| games | id | 保存順に増える整数 |
| games | kind | `round`（通常ラウンド1回）または`game`（旧来の一斉ゲーム）。版1の記録から移行したゲームは`game` |
| games | finished_at | ラウンドが終わった壁時計の時刻。ラウンドのゲーム時間の起点の時刻に90秒を加えて求める。UTCのRFC3339形式でミリ秒までとする |
| games | duration_ms | ルールで定めるゲーム時間のミリ秒。現行90000 |
| games | elapsed_ms | 確定済み経過時間のミリ秒。ラウンドではduration_msと同じ |
| games | reason | ラウンドは`timeout`だけ。`manual`は旧来の一斉ゲームの手動の終了にだけ残る |
| results | game_id | gamesのid |
| results | node | ラウンドは遊んだプレイヤーの1件（`P1`〜`P8`）。旧来のゲームは`P1`〜`P8`の8件 |
| results | score | 最終スコアの非負整数 |
| results | eligible | ラウンドは1。旧来のゲームは、ランキング対象者が1、対象外が0 |
| results | rank | ラウンドは1。旧来のゲームは、対象者が1〜8の最終順位、対象外がNULL |

ラウンドの`rank`を1とするのは、ランキング対象者の`rank`は1〜8とする既存の規則に合わせるためである。1人の中の1位という記録上の値であり、ゲームルールの順位ではない。順位は付けない（[ゲームのルール](../rules.md#最終順位)）ので、`status.rank`、`summary.rank`およびWeb APIには出さず、集計や表示にも使わない。

finished_atはゲーム時間と同じ基準で求めるため、遅れたTickで終了を処理した場合も、ゲーム時間が終わった時刻となる。ラウンドのゲーム時間の起点はカウントダウンの終了時刻であり、CHOOSEを受理した3秒後となる。

#### 3.5.2. 保存形式

ゲーム記録は1つのSQLite 3のデータベースファイルへ保存する。保存先は起動設定で指定でき、既定は作業ディレクトリからの相対パス`data/records.sqlite3`とする。接続には`journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`、および`busy_timeout`による待機時間を設定する。1ゲーム分の記録は1つのトランザクションで書き込む。

スキーマの版は`PRAGMA user_version`で管理し、現行は2とする。版0でスキーマを持たないデータベースには現行のスキーマを作成する。現行より古い版のファイルは、起動時に1つのトランザクションで現行の版へ移行する。版1から版2への移行は、`games`に列`kind`（`game`または`round`、既定`game`）を足し、既存のゲームをすべて`game`とする。版2のファイルを旧来のサーバーで開くと「未対応の版」（3.5.3）となり、記録を使えない起動になる。記録は壊れない。

#### 3.5.3. 起動時の読込と失敗時の扱い

`main`はHTTP・シリアル通信の受付前に記録ファイルを開き、全件を読み込んで検証してから`app`へ渡す。ファイルが存在しない場合だけ、親ディレクトリがなければ作成し、新しいデータベースを作成して通常どおり使用する。既存の0バイトのファイルは、SQLiteの仕様どおり空のデータベースとして使用する。

開けない・読めない場合は、理由をログへ記録して起動を続ける。権限不足、SQLiteのデータベースでないファイル・壊れたファイル、未対応の版、版0で他のスキーマを持つファイル、記録の内容の検証失敗などが該当する。記録の内容の検証は、1ゲームの結果が1〜8件で、ノードに重複がないことを求める（旧来のゲームは8件、ラウンドは1件）。`app`には記録を使えない状態とその理由を渡し、その起動中は保存を要求しない。ファイルを上書き・削除・作り直しせず、版の移行も行わない。実行中に開き直す再試行は行わず、管理者がファイルを確認してからサーバーを再起動する。

デバイス対応表（4.2.3）は読込に失敗すると起動を中止するが、ゲーム記録では起動を続ける。対応表を失うとMCUの割当をやり直す必要があるのに対し、ゲーム記録はゲームの進行に必要なく、展示を止めないことを優先するためである。

#### 3.5.4. 保存の失敗

起動後の保存に失敗した場合は、ゲームを止めずに理由をログへ記録し、直近の保存が失敗したことをSnapshotに示す。保存を自動で再試行しない。次の保存に成功すると、失敗の表示を解除する。失敗したラウンドの記録もメモリ上の集計には含める。ファイルには残らないため、再起動後の集計には含まれない。

#### 3.5.5. ベストスコアの集計

`app`は、起動時に渡された記録とこの起動中のゲーム記録をメモリ上で集計し、`State`のSnapshotに含める。ベストスコアの種類・対象・同点の扱いは[ゲームのルール](../rules.md#ベストスコア)に従い、次の規則で求める。

- 1時間ごと・通算の対象は、reasonが`timeout`で、duration_msが現在のゲーム時間と一致するゲームの、eligibleが1の結果とする。kindが`round`か`game`かは問わない。旧来の一斉ゲームの記録も母集団に含める。
- 1時間ごとの時間帯は、finished_atを日本時間（UTC+9に固定し、夏時間を考慮しない）で表したときの正時から、次の正時の直前までとする。対象の結果がある時間帯だけを、新しい時間帯から順にすべて返す。
- ルールの「先に終わったもの」は保存順（gamesのidの昇順）で判定する。記録を使えない起動では、この起動中に終わった順とする。同じ入力イベントで複数のラウンドが終わった場合は、3.5.1の順に保存する。finished_atで比べると、実行中にホストの時計が直された場合に、実際に終わった順と異なるためである。
- 直近のラウンドは、この起動中に結果を確定した通常ラウンドを、新しい順に最大10件返す。各要素は、ノードID、得点、上位%（3.5.6でそのラウンドの結果を確定したときに求めた値）、finished_atとする。打ち切ったラウンドと練習は含まない。起動時に読み込んだ記録は含めない。上位%は保存せず、結果を確定したときの母集団で求めた値なので、記録ファイルから同じ値を求め直せないためである。運転の開始・停止では消さない。サーバーを再起動すると空に戻る。
- 記録を使えない起動（3.5.3）では、この起動中に終わったラウンドだけを同じ規則で集計し、その旨をSnapshotに示す。

#### 3.5.6. 上位%の計算

`app`は、ゲームルールの「[上位%](../rules.md#上位)」を次の規則で求める。上位%はゲーム記録へ保存せず、保存済みの最終スコアから毎回求める。

- 求める時機は、通常ラウンドの結果を確定するときの1回とする。3.5.1のゲーム記録を作って保存を要求し、3.5.5の集計へ加えた直後に、同じ入力イベントの中で、そのゲーム記録の結果から求める。得点と同じ確定状態から求めるので、Snapshotとプレイヤーの`summary`は同じ値を返す。
- 母集団は、3.5.5の1時間ごと・通算の対象と同じ、reasonが`timeout`で、duration_msが現在のゲーム時間と一致するゲームの、eligibleが1の結果のscore全件とする。今回のラウンドの結果は常にこの条件を満たすので、母集団に含める。旧来の一斉ゲームの記録も含める。保存に失敗したラウンドも、3.5.4に従って母集団に含める。
- 母数の下限は設けず、母数が1件でも付ける。打ち切ったラウンドと練習には付けない（そもそも記録を作らない）。
- 値は、100 × （母集団でscoreが自分より大きい件数 ＋ 1）÷ 母数 を切り上げた整数とし、1〜100に収める。母集団に自分の結果が含まれるので、母数は1以上であり、通常は1〜100に収まる。
- 求めた値はノードごとに保持し、結果の段階の間は、モード・割当の変更、再同期、`State`では求め直さない。結果の段階の間は母集団が変わらないが、他の筐体のラウンドが終わると母集団は増える。値が変わらないことは母集団ではなく保持によって保証する。結果の段階を出るときに消す。停止中・待機・モード選択・ラウンド中は、値を持たない。
- 記録を使えない起動（3.5.3）では、母集団はこの起動中に終わったラウンドだけになる。その値はSnapshotには含めるが、プレイヤーの`summary`には含めない。ファイルの記録と合わせた母集団ではないので、プレイヤーの画面に出す値としては信頼できないためである。
- プレイヤーの`summary`へは、保持した値が50以下の場合だけその値を`topPercent`で送る（定数）。51以上の場合と、記録を使えない起動では`topPercent`を`null`とする。保持した値が51以上の場合は、値を伏せて`bottomHalf`を`true`とし、それ以外では`false`とする。記録を使えない起動では、どちらも送らない（`topPercent`は`null`、`bottomHalf`は`false`）。Snapshotには、51〜100を含む保持した値をそのまま返す。

#### 3.5.7. プレイヤーへ送るベストスコア

結果の段階のプレイヤーの画面にもベストスコア3種を示すため、`app`はプレイヤーの`summary`にその回・このラウンドが終わった時間帯・通算のベストスコアを含める。項目の型・範囲・組合せは[プレイヤー通信仕様](./player.md)に従い、値は次の規則で求める。

- 求める時機は、通常ラウンドの結果を確定するときの1回とする。3.5.6と同じく、3.5.1のゲーム記録を3.5.5の集計へ加えた直後に、同じ入力イベントの中で求めて保持する。結果の段階の間は、モード・割当の変更、再同期、`State`では求め直さず、結果の段階を出るときに消す。
- その回（`gameBest`・`gameBestNodes`）は、そのラウンドの自分の得点と、自ノードだけとする。ラウンドは1人で行うため、その回の最高点は常に自分である。
- 時間帯（`hourBest`・`hourBestStart`）は、そのゲーム記録のfinished_atを3.5.5と同じく日本時間の正時で区切った時間帯の、3.5.5の1時間ごとのベストスコアとする。今回のラウンドは3.5.5の1時間ごとの対象なので、今回の結果を加えた後の値になる。`hourBestStart`は時間帯の開始の時（0〜23）とする。
- 通算（`allTimeBest`）は、3.5.5の通算のベストスコアを、今回のゲーム記録を加えた後の値で送る。
- `hourBestMine`・`allTimeBestMine`は、そのベストスコアが今回のゲーム記録によって決まる場合だけ`true`とする。3.5.5の同点の扱いにより、今回の結果が既存のベストスコアと同点ならベストスコアは先のものなので、`false`とする。
- 記録を使えない起動（3.5.3）では、`hourBest`・`hourBestStart`・`allTimeBest`をnull、`hourBestMine`・`allTimeBestMine`を`false`とし、`gameBest`・`gameBestNodes`だけを送る。3.5.6と同じく、この起動中のラウンドだけの集計はプレイヤーの画面に出す値として信頼できないためである。Snapshotの集計は3.5.5のとおり返す。
- `summary`は、結果を確定した筐体のセッションだけに送る。`hourBestMine`・`allTimeBestMine`はそのノードで決める。
- 項目は`summary.data`の直下に平らに置く。既存のファームウェアはJSONの入れ子の深さを4までに制限しており、入れ子にすると深さが4を超えて再識別を繰り返すためである。サーバーとプレイヤー基板は互換性を持たず、同時に更新する（プレイヤー通信仕様）。

#### 3.5.8. 記録の保守コマンド

記録ファイルの確認と展示前の準備のために、サーバーとは別のコマンド`records`を設ける。対象のファイルは`-records-file`で指定し、既定はサーバーと同じ`data/records.sqlite3`とする。

| サブコマンド | 動作 | サーバーの動作中 |
|---|---|---|
| `histogram` | 3.5.6の母集団と同じスコアを、0〜99・100〜199・…・1400〜1499の100点ごとの15の帯と1500以上の、計16の帯に分け、帯ごとの件数と割合を表示する | 実行できる |
| `clear` | ゲーム記録をすべて削除する | 実行できない |
| `seed` | 空の記録へゲーム記録を追加する | 実行できない |
| `restore` | 記録をバックアップの内容に置き換える | 実行できない |

- `histogram`はファイルを読むだけとする。ファイルがなければ作らずに失敗する。
- `clear`・`seed`・`restore`は、他の接続がファイルを開いていれば、何も変更せずに失敗する。サーバーは起動時に読み込んだ記録をメモリ上で集計するので（3.5.5）、動作中にファイルを変えると、集計とファイルが食い違うためである。実行中はファイルを排他的にロックする。その間に起動したサーバーは、記録を使えない起動（3.5.3）になる。
- `clear`・`seed`・`restore`は、変更の内容を表示した後、件数を含む確認の文字列（`DELETE <件数> GAMES`、`SEED <件数> GAMES`、`RESTORE <バックアップの件数> GAMES`）が入力された場合だけ変更する。それ以外の入力では何も変更しない。
- `clear`は、削除の前に同じディレクトリへ、`<記録ファイル名>.bak-<日本時間のYYYYMMDD-HHMMSS>`という名前でバックアップを作る。作れなければ削除しない。削除は1トランザクションで行い、スキーマと版は残す。記録がなければ何もしない。
- `seed`は、記録が1件もない場合だけ追加する。点数は一覧で指定するか、指定した平均・標準偏差の正規分布から整数で作る。正規分布から作る場合は、指定した範囲に収まるまで引き直す。1つの点数につき1ラウンド（kindは`round`）とし、reasonは`timeout`、duration_ms・elapsed_msは現在のゲーム時間とする。結果は1件で、P1（プレイヤーA）にその点数を与え、eligibleは1、rankは1とする。
- `seed`のfinished_atは、指定がなければ、実行時刻の24時間前を含む日本時間の正時とする。2件目からは1件ごとに1秒ずつ進める。最後のゲームが現在より後になる指定は拒否する。全件を1トランザクションで追加する。
- `seed`で追加した記録は、通常のゲーム記録と区別しない。3.5.5の1時間ごと・通算のベストスコアと、3.5.6の上位%の母集団に含まれる。
- `restore`は、`-from`で指定したバックアップの全ゲームで、記録ファイルの全ゲームを1トランザクションで置き換える。バックアップは一時的な複製から読み、3.5.3と同じく全件を検証してから使う。バックアップのファイルは変更しない。バックアップに`-wal`のファイルがある場合、記録ファイル自身を指定した場合、記録ファイルがない場合は、何も変更せずに失敗する。
- `restore`は、ファイルを置き換えずに、記録ファイルを開いたまま中身を入れ替える。異常終了したサーバーの`-wal`のファイルが残っていても、SQLiteはそれを本来の記録ファイルへ適用するので、バックアップの内容と混ざらないためである。置き換える前の記録が1件以上あれば、`clear`と同じ名前の規則でバックアップを作り、作れなければ置き換えない。ゲームのidは保存順のまま1から振り直す。

### 3.6. 練習ラウンドと練習用キュー

練習ラウンドは、時間制限なしでヒントを見ながら転送を練習する段階である（[ゲームのルール](../rules.md#チュートリアル練習)）。練習中のノードは、実際のネットワークでは自動（ゲームルールに従う速度）のまま中継を続け、プレイヤーには、そのノード専用の練習用キューを見せる。プレイヤーは他のプレイヤーのパケットの中継点でもあり、練習者が実際のFIFOを手動で遅く捌くと、そこを通る他人のパケットが滞留して他人のスコアが下がるためである。打ち切りの契機（3.1）は放置への対策であり、ゆっくり操作を続ける人は防げないので、実際のFIFOを練習者の操作から切り離す。

サーバーは練習中のノードに、二つのキューを持つ。

| キュー | 中身 | 動き |
|---|---|---|
| 実際のFIFO | ネットワークを流れる実際のパケット | 待機中と同じく自動で捌く。生成・受信・中継は止めない。得点は数えず、記録しない |
| 練習用キュー | サーバーが作る仮想のパケット | 練習者の`send`で先頭を消費し、直ちに3件へ補充する |

練習用キューは次の規則に従う。

- 練習ラウンドを始めるとき（CHOOSE）に3件を作る。常に3件を保ち、`send`で先頭を取り除いたら直ちに1件を補充する。時間無制限の練習なので、時間で溜める必要がない。
- 補充するパケットの宛先は、自分以外の7プレイヤーノードから一様に選ぶ。両隣のノード宛てを含める。ヒントが光らない両隣宛てのケースも体験できるようにするためである。TTL・経路・パケットロスは持たない。
- PIDは、実際のパケットのPID（3.2）とは別の連番とする。練習ラウンドごとに0から昇順に発行し、65535の次は0に戻り、そのとき練習用キューにあるPIDを飛ばす。
- MCUへ送る`reset`・`push`と`send`の応答は、練習中は練習用キューの内容にする。MCUの通信形式は変えない。MCUは練習用キューと実際のFIFOを区別せず、`status.round`で画面を切り替える。
- 練習中は、実際のFIFOの変化（`push`・`reset`）をMCUへ送らない。MCUの表示用キャッシュは練習用キューだけを持つ。
- 管理画面には練習用キューを出さない。Snapshotの`fifoLength`は実際のFIFOの件数を返す。

練習の入りと出では、MCUのキャッシュを丸ごと入れ替える。入りと出のたびに`reset`を新しい同期世代で送るので、それ以前の`send`は同期世代の照合（4.4）で拒否される。実際のFIFOのPIDと練習用キューのPIDが同じMCUのキャッシュに同時にあることはなく、MCUがキャッシュ内のPID重複を理由に復旧処理へ入ることもない。練習用のPIDを実際のPIDの採番器から払い出す必要はない。

| 契機 | 送信順 |
|---|---|
| 練習ラウンドの開始（CHOOSE） | `phase(Playing)` → 練習用キューの新しい同期世代の`reset` → `status`（`round=tutorial`、`countdown=3`、`window=60`、`bots`） |
| 練習中の`resync` | 練習用キューの新しい同期世代の`reset` → `phase(Playing)` → `status` |
| 長押しで練習ラウンドを出る（READY） | `phase(Select)` → 実際のFIFOの新しい同期世代の`reset` → `status` |
| 無操作の60秒で練習ラウンドを出る | `phase(Idle)` → 実際のFIFOの新しい同期世代の`reset` → `status` |
| 打ち切り（4.2） | `phase(Idle)` → 実際のFIFOの新しい同期世代の`reset` → `status` |

練習の`send`は、同期世代・要求ID・ノードの操作状態・隣接関係を通常の`send`（4.4）と同じ規則で検証する。受理条件は次のとおりとする。

- 筐体が練習ラウンドの段階にあり、カウントダウンが終わっている。
- Session IDがプレイヤーノードに対応している。
- `sync`が当該セッションの現在の同期世代と一致する。
- 対象プレイヤーノードが手動操作中である。
- 送るPIDが練習用キューの先頭と一致し、転送先が自ノードに隣接するノード（隣のプレイヤーノード2つとBot2つ）である。

受理した場合は、`result(ok=true)`を返して練習用キューの先頭を取り除き、直ちに1件を補充して`push`を送る。`result`を先に登録する。TTL・パケットロス・到達の判定はなく、満杯のBotへ送ってもロスしない。練習の`send`は、実際のFIFO・LED（`LIGHT`・`CHEER`・`BUFFER`）・得点・送信成功コンボ・記録に何も作用しない。LEDは他人の実際のパケットの光と区別がつかなくなる。練習者には筐体の画面で足りるので、見せ用の`LIGHT`も送らない。拒否した場合は`result(ok=false)`の後に、練習用キューの`reset`を新しい同期世代で送る。

受理した`send`は、練習の無操作のタイマー（60秒）を戻す。タイマーはカウントダウンの終了時刻から数え始め、カウントダウン中は60秒のままとする。

練習中の`status`は、`score=0`、`remaining=0`、`ready=false`、`rank=null`、`gains=[]`、`combo=0`とし、`round=tutorial`、`window`は無操作の残り秒数（`ceil`）を通知する。実際のFIFOの自動転送で入る点を練習画面に出さないためである。

#### 3.6.1. Botの混雑の通知

練習中の`status`にだけ、`bots`を付ける。B1・B2・B3の実際のFIFO使用量（0〜4の整数3つ）で、LED制御MCUへの`BUFFER`（5.3）と同じ値である。プレイヤー基板はBotの混雑を何も受け取っておらず、満杯のBotへ送るとロスする規則（[ゲームのルール](../rules.md#輻輳)）を、練習中に知る手段がないためである。実際の値を示すので、展示では本物のシグナルタワーが同じ状況を光らせ、画面と実物が対応する。練習の`send`自体はロスしない（上記）。仮想のBotを持って練習の`send`で実際にロスさせたり、TTL・ループの警告を出したりする案は、練習用キューを単純にする方針（経路やロスを持たない）に反し、作る量が大きいので採らない。

- `bots`は練習ラウンドの`status`にだけ付ける。停止中・待機・モード選択・通常ラウンド・結果では付けない。
- 形式・検証はプレイヤー通信仕様に従う。`status.data`の直下の配列で、JSONの入れ子の深さは3に収まる。旧来のファームウェアは未知の項目として無視する。
- 練習中にBotのFIFO使用量が変わったとき、練習中のノードへ最新の`status`を送り直す。送り直しは、プレイヤー通信仕様のスコア・残り秒数などの`status`と同じ規則とする。入力イベントを確定した後に、値が変わっていれば1回だけ最新の値を送る。同一の入力イベントで複数のBotの値が変わった場合も1回にまとめる。定期的な送信は追加しない。`BUFFER`は使用量が変わるたびにLEDへ送られる（5.3）ので、変化の粒度をそろえれば、画面とタワーの表示がずれない。変化ごとの送信が最大でも秒に数回であり、既存の`status`の送信頻度と同じ範囲に収まる。
- 練習に入った直後の`status`には、その時点の値を付ける。`bots`が来ていない間（練習に入る前や、再同期の直後）はMCUが警告を出さない。

## 4. 入力イベントの処理

### 4.1. 共通規則

`app`は入力イベントを直列に処理する。

各入力イベントについて、`app`は受理条件の判定、ゲーム状態の変更、要求元への応答、MCUへの通知の要否判定を行う。

異なる入力元から同時に到着した入力イベントについては、`app`が受け付けた順序で処理する。入力元間の固定優先順位は定めない。

ゲーム状態の変更は、1入力イベントの処理単位で確定させる。

管理操作、MCUからの入力イベント、およびTickを処理する際は、まず`app`が処理を開始した時点の単調増加する時刻を基準に、未処理の生成・自動転送・筐体の期限（4.3）を期限順に確定する。その後、更新後の状態に対して入力イベントの受理条件を判定し、操作を適用する。Tickの発行時刻やMCU側の時刻によってゲーム時間を巻き戻さない。

筐体の期限（通常ラウンドのゲーム時間の終了など）に達している場合は、期限より前の生成・転送を確定し、期限の処理（結果の確定、待機への復帰など）を行った後、入力イベントを処理する。`State`は確定済み状態のSnapshotを取得するだけとし、時間進行処理を起動しない。

### 4.2. 管理クライアントからの入力

| 入力 | 受理条件 | appの処理 | webへの結果 |
|---|---|---|---|
| Start | 停止中 | 初期化して運転中へ遷移し、全プレイヤーを待機へ移す。各プレイヤーの最初のパケット生成期限を処理時刻の1秒後に設定する | 成否・拒否理由 |
| Stop | 運転中 | 全プレイヤーのラウンド・モード選択・結果を打ち切り（記録しない）、初期化して停止中へ遷移する | 成否・拒否理由 |
| SetNodeEnabled | プレイヤーが指定され、手動にする場合は対応MCUが接続・識別済み。運転中・停止中のどちらでも可 | 操作状態を変更し、ラウンド・モード選択・結果を打ち切って待機へ戻す。接続中ならconfigから再同期 | 成否 |
| SetAllNodesEnabled | 運転中・停止中のどちらでも可 | P1〜P8を番号順に、SetNodeEnabledと同じ処理で切り替える。有効（手動）は対応MCUが接続・識別済みのノードだけに適用し、それ以外は自動のまま残す。無効（自動）は全員に適用する | 成否と、手動にできなかったノードID（昇順。無効では常に空） |
| ReturnToBot | 運転中。プレイヤーが指定されている | 対象のラウンド・モード選択・結果を打ち切り、待機へ戻す。操作状態は変えない | 成否・拒否理由 |
| SetBotRate | 全状態。Botが指定され、設定値が有限の正数 | 処理速度を変更 | 成否 |
| SetDeviceAssignment | 停止中、または運転中。識別済みDevice IDと同じ機器種別の有効な対応先で、対応が競合しない。解除も可。運転中は、担当が変わるプレイヤーノード（旧担当と新担当）がすべて自動操作 | 対応表を更新し、接続中なら対象MCUを再設定 | 成否 |
| SwapDeviceAssignments | 停止中、または運転中。同じ機器種別の異なる2台が割当済み。運転中は、担当が変わるプレイヤーノードがすべて自動操作 | 2台の対応を一括で交換し、接続中なら再設定 | 成否 |
| ReplaceDeviceAssignment | 停止中、または運転中。交換元が割当済みで、交換先が同じ機器種別の別UIDかつ接続・識別済み。交換元は未接続でも可。運転中は、担当が変わるプレイヤーノードがすべて自動操作 | 交換元の役割を交換先へ付け替え、交換元を未割当にする | 成否 |
| SetDevicePreview | 開始は停止中または運転中で、対象が接続・識別済み。未割当も可。割当済みプレイヤーの場合はauto。停止は全状態で可 | 4.2.2に従い、対象1台の確認表示を開始・停止 | 成否・拒否理由 |
| State | 常時 | Snapshotを取得 | Snapshot |

運転中の割当・確認表示は、プレイヤー基板では担当のノードが自動操作（ボット固定）のときに限り、LED制御基板では常に許可する。停止中は、これまでどおり手動のノードも対象にできる（担当が変わる手動のノードは自動操作へ切り替える。4.2.1）。展示中に故障した基板を、全体を止めずに予備と交代できるようにするためである。手動のノードで担当を変えると、遊んでいる人の筐体が入れ替わる。

StartとStopは、一斉ゲームのResetと同じ初期化を行う。MCUとのシリアル接続、Device IDの対応表、プレイヤーの操作状態、Botの処理速度、およびゲーム記録を維持する。パケット・FIFO・PIDの採番カウンタ（0に戻す）・スコア・未送信の獲得点・送信成功コンボ・ゲーム内時間および生成・転送タイマー・筐体の段階を初期化する。割当済みプレイヤーMCUには、Startでは`phase(Idle)`、Stopでは`phase(Preparing)`、新しい同期世代の空FIFOの`reset`、`status(score=0, remaining=0, ready=false, countdown=0, rank=null, gains=[], combo=0, round=null, window=0)`の順に送信する。この手順は、停止中の筐体を休止中の表示にし、運転の開始・停止の前に進んでいたラウンドの表示を消すためのものである。

LED制御MCUには5.3とLEDノード仕様のゲームReset手順を、StartとStopのそれぞれで適用する。確認対象を解除し、確認中の割当済みMCUには現在の担当の`CONFIG NODE false`、Bot用には続けて初期化後の件数の`BUFFER 0`を送る。確認中の未割当MCUは`identify`で一時設定を解除する。それ以外の接続・識別・割当済みMCUには`CLEAR`、Bot用には続けて`BUFFER 0`を送り、担当NODEを維持して`CONFIG`は再送しない。確認解除用の`CONFIG`直後に`CLEAR`を重複送信しない。

ラウンド・モード選択・結果の打ち切り（`ReturnToBot`、`SetNodeEnabled`による自動への切替、MCUの切断、FIFOの上限）は、対象ノードを待機へ戻し、通常ラウンドの途中の得点・未送信の獲得点・送信成功コンボ・練習用キューを捨てて、自動転送を再開する。FIFOが空でなければ、処理時刻から`1 / 処理速度`秒後を次回の転送期限とする。接続中のMCUには、`phase(Idle)`、練習ラウンドだった場合は実際のFIFOの新しい同期世代の`reset`、現在の`status`の順に送信する。`config`は送らない。送ると筐体の表示状態が初期化されるためである。`SetNodeEnabled`・`SetAllNodesEnabled`による切替は、下に示す順で`config`から再同期し、この手順は適用しない。

SetBotRateで速度を変更した場合、運転中でFIFOが空でなければ、変更時刻から新しい速度に基づく1パケット分の待ち時間を経て次回の転送を行う。FIFOが空の場合は、次にパケットが到着した時点から待ち時間を計る。停止中では設定のみ変更し、転送を実行しない。

SetNodeEnabledの対象はプレイヤーノードのみとする。Botは常に自動操作とし、この操作の対象に含めない。ReturnToBotも同じである。ReturnToBotが指定したノードがすでに待機であれば、何も変えずに成功とする。

SetAllNodesEnabledは、手動にできないノードがあっても拒否しない（`device_disconnected`を返さない）。そのノードは自動のまま残して結果に含め、残りのノードを切り替える。各ノードの処理（打ち切り、`config`・`reset`・`phase`・`status`の送信、確認表示の解除）はSetNodeEnabledと同じで、各MCU宛の送信順序も同じとする。MCUをまたぐ順序は、`config`・`reset`・`phase`がノードの番号順で、`status`は入力イベントの最後にまとめて送り、MCU間の順序を定めない。入力イベントとしては1つなので、途中で別の入力イベントは処理しない。

SetNodeEnabledで操作モードを実際に変更した場合、対象ノードのラウンド・モード選択・結果を打ち切って待機へ戻す（停止中は停止中のまま）。接続済みの対象MCUへ現在のモードを含む`config(preview=false)`、実際のFIFOの`reset`、現在の`phase`、現在の`status`の順に送信する。打ち切るので`summary`は送らない。同じセッション内の要求IDの履歴は維持する。同じモードの再設定では何も変更せず、ラウンドも打ち切らない。運転中の再接続・識別に伴う`config`は現在モードの通知であり、管理操作による切替や手動操作への復帰を意味しない。

ReturnToBotは、操作状態を変えないので`config`を送らない。上記の打ち切りの手順だけを行う。次の人をすぐ受け付けられるよう、受付（手動）を保ったまま待機へ戻す。

#### 4.2.1. デバイスの割当・交換

対応は機器種別ごとにDevice IDとノードIDの一対一とする。プレイヤーMCUはP1〜P8、LED制御MCUはLEDノード仕様のB1・B2・B3・P1・P3・P5・P7を割当先とする。例えばプレイヤーP1とLED制御P1は別の割当先であり、機器種別をまたぐ割当・交換は拒否する。

| 操作 | 対応表の変更 |
|---|---|
| SetDeviceAssignment | 空いている対応先へ割当・移動する、または解除する。同じ対応の再設定も受け付ける。他のUIDが使用中の対応先は上書きせず拒否する |
| SwapDeviceAssignments | 2台の割当先を一括で交換する。一方だけの変更は確定しない |
| ReplaceDeviceAssignment | 交換元の割当を解除し、同じ役割を交換先へ割り当てる。交換先に仮割当などの既存の役割があれば、その割当も解除する。交換元へはその役割を引き継がせない |

`app`は各操作の条件を処理時に検証し、4.2.3の保存に成功してから、対応表の変更を1入力イベント内で一括確定する。条件不成立または保存失敗なら、その操作に伴う対応表・自動仮割当の対象外情報・操作モード・確認表示の変更とMCUへの通知を行わない。交換・付け替えは物理基板の担当を変更する操作であり、ノード間でFIFO・スコアを移動・初期化しない。

担当UIDが実際に変わるプレイヤーノードは、担当を失う側・新たに受け取る側ともに自動操作とする。運転中は4.2の受理条件によりすべて自動操作であり、操作モードと筐体の段階は変わらない。停止中に手動だったノードは自動操作へ切り替える。同じ対応の再設定では変更しない。管理者は表示を確認して手動操作へ切り替える。

接続済みプレイヤーMCUが新しい担当を受け取る場合は、`config(mode=auto, preview=false)`、現在のFIFOの新しい同期世代の`reset`、現在の`phase`、そのプレイヤーの現在の`status`の順に同期する。担当を失って未割当になる接続済みプレイヤーMCUへは`identify`を送り、旧設定・表示・操作を無効化する。以後の`hello`では再割当せず、管理操作を待つ。同じセッション内の要求IDの履歴は維持する。

LEDの担当変更・交換・予備基板への付け替えでは、割当が実際に変わるUIDに確認対象が含まれる場合だけ、サーバーの確認対象を解除する。変更対象と無関係な機器の確認表示は継続する。新しい担当を受け取る接続済みMCUへ`CONFIG NODE false`、新担当がBot用ならそのBotの現在の正本FIFO使用量の`BUFFER`を送る。`CONFIG`自体でMCUの確認周期を停止し、全出力の消灯と演出状態の初期化を行うため、直前の`CLEAR`は送らず、旧担当の`BUFFER`も復旧しない。未割当になるMCUには`identify`を送り、確認表示・一時設定を解除して未設定へ戻す。自動仮割当や再接続による通常のLED設定も`CONFIG NODE false` → 新担当がBot用なら`BUFFER`の順とする。実機確認中の一時設定は4.2.2とLEDノード仕様に従う。

#### 4.2.2. 実機の確認表示

Web管理画面でUIDを選択し、`SetDevicePreview`で実機の確認表示を行う。サーバー全体で同時に1台だけを対象とし、開始条件を満たす別のUIDを選択した場合は、現在の確認表示を終了・復旧してから新しい対象を開始する。条件不成立なら現在の確認表示を変更しない。同じ対象への再要求は確認表示を継続し、停止要求は対象がなくても成功とする。共通の`identify`は通信上の識別要求のままとし、確認表示専用のMCU命令は追加しない。

未割当の予備基板も、既存の担当を解除せずに確認できる。確認用ノードIDは、割当済みなら現在の担当、未割当なら機器種別に応じたP1を使用する。未割当への`config`・`CONFIG`は表示のための一時設定とし、P1が既に使用中でも送信できる。正式な対応表、既存P1の担当・操作状態・ゲーム状態、および自動仮割当の対象外UID情報は変更しない。SnapshotのMCU欄は未割当のままとし、一時設定は実機確認欄にだけ公開する。一時設定をゲーム操作の受理や通常通知の送信先として使用しない。

| 対象 | 確認表示の通知 |
|---|---|
| プレイヤーMCU | 確認用ノードIDの`config(mode=auto, preview=true)`、新しい同期世代の`reset`、現在の`phase`、確認用の`status`を順に送信。MCUは通常画面に代えてノードの表示名・色を大きく点滅させる。FIFOは割当済みなら正本、未割当なら空配列を通知する |
| LED制御MCU | 確認用ノードIDの`CONFIG NODE true`を送る。MCUが表示・演出状態を初期化してGPIO0・1の1秒周期の確認表示を開始する。サーバーから確認用の`LIGHT`・`BUFFER`・`CLEAR`を周期送信しない |

プレイヤーの確認用`status`は、割当済みなら現在の担当の正本値、未割当なら`score=0`・`ready=false`・`remaining=0`・`countdown=0`・`round=null`・`window=0`を通知する。未割当へのスコア・準備完了状態は表示専用であり、正式なP1の値を参照・変更しない。確認中は結果を表示せず、未割当・割当済みのいずれにも`summary`を送らない。

確認表示のためのダミーパケットは生成・送信しない。正本FIFO・パケット管理・PID採番・生成数・得点を変更せず、PIDの値による確認表示の判別も行わない。確認中も運転状態・筐体の段階・操作モードを変更しない。プレイヤーはautoかつpreview=trueのため`send`・`ready`・`choose`を送らず、同期世代の発行・更新と要求照合は通常の規則に従う。運転中の確認表示でも、正本FIFOの変化は通常どおり同期する。

割当済みプレイヤーの確認終了時は、現在の担当・モードの`config(preview=false)`、新しい同期世代の正本FIFOの`reset`、現在の`phase`、現在の`status`の順に復旧する。未割当プレイヤーには`identify`を送り、一時設定・表示・同期状態を無効化して未設定へ戻す。以後の`hello`は通常の未割当機器として扱い、確認表示だけを理由に正式なP1へ対応付けない。

LEDの確認終了時は、正式に割当済みなら現在の担当の`CONFIG NODE false`を送り、Bot用なら続けてそのBotの現在の正本FIFO使用量の`BUFFER`を送る。未割当なら`identify`で一時的なNODE・PREVIEWを解除して未設定へ戻す。`CLEAR`はPREVIEWを変更しないため、確認解除には使用しない。担当変更時は4.2.1の新担当への再設定に解除を統合し、旧担当の`BUFFER`は送らない。過去の`LIGHT`・`CHEER`は再現しない。先にサーバーの確認対象を解除し、未割当MCUの続く`HELLO`で確認表示を再開しない。

次の場合は確認表示を自動終了する。

- 受理されたStartで運転中へ遷移する前、Stopの受理時。
- 対象プレイヤーをmanualへ切り替える前。
- 対象の割当を実際に変更・交換・解除する前。未割当の対象への自動仮割当・管理操作による割当も含む。
- 対象MCUから`hello`・`HELLO`の再受信または`resync`があった場合、および対象セッションの切断時。

開始可否などの操作条件は通常どおり検証し、拒否された操作だけを理由に確認表示を終了しない。Startではpreview=falseへの再設定と正本への復旧、または未割当機器の一時表示の解除を、`phase(Idle)`より先に送信キューへ登録する。モード・割当変更、HELLO・RESYNCへの通常の設定・同期が確認解除も含めて正本を復旧する場合は、それを復旧処理として用い、重複した同期は不要とする。StartとStopで確認中の割当済みプレイヤーには`config(preview=false)`を先に送り、以後は通常の`phase`、空FIFOの`reset`、初期値の`status`で復旧する。未割当プレイヤーの確認終了では、先に確認対象を解除してから`identify`を送り、その応答の`hello`では確認表示を再開しない。StartとStopで確認中の割当済みLEDには`CONFIG NODE false`を送り、Bot用には初期化後の件数の`BUFFER 0`を続ける。確認中の未割当LEDは`identify`で一時設定を解除する。切断時は確認対象を解除し、MCUは確認モードを初期化する。再接続時は通常の設定・同期を行い、確認表示を自動再開しない。復旧中の送信失敗は2.4の通常の切断処理に従う。

#### 4.2.3. デバイス対応表の保存・復元

対応表と自動仮割当の対象外UIDは、1つのUTF-8のJSONファイルへ保存する。保存先は起動設定で指定でき、既定は作業ディレクトリからの相対パス`data/devices.json`とする。`main`が起動時の読込と検証を行い、`app`は復元された情報を正本として管理し、以後の変更と保存を直列に処理する。実行中にファイルを再読込する機能や、保存専用の管理操作は設けない。

保存形式は次のとおりとする。割当済み、または自動仮割当の対象外である機器を保存し、未接続の機器も含める。未割当かつ対象外ではない機器は保存せず、再起動後に接続・識別された時点で再登録する。

```json
{
  "version": 1,
  "devices": [
    {"deviceId": "001122334455", "kind": "led", "nodeId": "B1", "autoAssignExcluded": false},
    {"deviceId": "112233445566", "kind": "player", "nodeId": null, "autoAssignExcluded": true},
    {"deviceId": "AABBCCDDEEFF", "kind": "player", "nodeId": "P1", "autoAssignExcluded": false}
  ]
}
```

| フィールド | 保存する値 |
|---|---|
| version | ファイル形式のバージョンを表す整数。現行は1 |
| devices | Device ID順の配列。保存対象がなければ空配列 |
| deviceId | MCUのUIDと同じ大文字・ゼロ埋め12桁の16進文字列 |
| kind | `player`または`led` |
| nodeId | 4.2.1で機器種別ごとに許可された`P1`などの文字列。未割当はnull |
| autoAssignExcluded | 未割当時に自動仮割当の対象から外すかを表すboolean。交換元や管理操作で解除されたUIDの情報も保持する |

全フィールドを必須とし、型の暗黙変換や欠落時の補完は行わない。UIDは機器種別をまたいで重複させず、割当先は機器種別ごとに一意とする。対象外フラグは割当先とは別に保持し、明示的な再割当だけでは消去しない。接続ポート・Session ID・接続状態・同期世代・操作モード・確認表示の一時設定・ゲーム状態は保存しない。

保存と変更の確定は次の順で行う。

1. 受理条件を検証し、変更後の対応表と対象外情報の候補を作る。自動仮割当も同じ手順を使う。
2. 保存内容が変わる場合は、候補全体を保存先と同じディレクトリの一時ファイルへ完全に書き込み、そのファイルの`fsync`とクローズに成功してから、既存ファイルを原子的に置き換える。親ディレクトリがなければ作成し、新規作成した各階層のディレクトリについて、その親ディレクトリも同期して作成を永続化する。交換・付け替えの複数UIDの変更は、1回の置換にまとめる。
3. 置換後に保存先の親ディレクトリを`fsync`し、その成功を保存完了とする。保存内容が同一なら書込・置換・同期を省略し、既存の同じ対応への再要求の規則に従う。
4. 割当先が実際に変わるUIDに確認対象が含まれる場合は、先にサーバーの確認対象を解除する。この時点ではMCUへ通知せず、旧担当の通常表示を復旧しない。無関係な機器の確認表示は維持する。
5. 候補をメモリ上の正本へ一括反映し、4.2.1に従って操作モードを変更して、新しい割当に従ってMCUを再設定する。未割当になるMCUには`identify`を送る。これらを同じ入力イベント内で処理し、管理操作の成功応答はその後に行う。

置換前のディレクトリの作成・同期、一時ファイルの作成・書込・同期・クローズ、または原子的な置換そのものに失敗した場合は、既存の保存ファイルと正本を維持し、一時ファイルを復元には使用しない。管理操作では保存失敗をログへ記録してエラーを返し、Web APIは`500 internal_error`へ対応付ける。自動仮割当では識別情報・接続状態を維持して未割当で待機させ、ログへ記録する。既存機器の動作を継続し、4.5の仮割当の契機で再試行する。保存失敗だけを理由に自動仮割当の対象外へ変更しない。

置換に成功した後の親ディレクトリの同期に失敗した場合は、保存結果を不明とする。旧ファイルの維持や永続化完了を保証せず、ファイルを旧内容へ書き戻さない。候補を正本へ反映せず、その操作に伴う確認対象・操作モードの変更とMCUへの通知、管理操作の成功応答を行わない。管理操作と自動仮割当のどちらでも理由をログへ記録し、以後の入力イベントの処理と送信要求を停止してHTTP・シリアル接続を終了し、サーバープロセスを異常終了する。再起動時は通常の検証・復元手順で保存ファイルを読み込み、旧版・新版のどちらが残っていても全件を検証してから起動する。失敗した管理操作を自動再送しない。

空きの発生などに続く別機器の自動仮割当は、それぞれ独立した保存・確定とする。その失敗で、既に保存・確定した管理操作や他の機器の割当を取り消さない。保存完了後のMCUへの送信失敗は2.4に従い、保存済みの対応表を戻さない。運転の開始・停止・切断・確認表示の開始と停止自体は保存内容を変更しないため、保存を要求しない。ただし、空きの発生などを契機に自動仮割当が成立する場合は、その変更を保存してから確定する。

起動時はHTTP・シリアル通信の受付前に、指定した保存ファイル全体を読み込み、構文・必須フィールド・型・バージョン・UID形式・機器種別・割当先の範囲・UIDと割当先の重複を検証する。全件が正常な場合だけ一括で復元する。ファイルが存在しない場合に限り、初回起動として空の対応表から開始する。空ファイル、不正な内容、未対応バージョン、権限不足などの読込失敗では理由をログへ出力して起動を中止し、空の対応表への置換や部分的な復元を行わない。

復元した機器はSnapshotにも未接続として公開し、Session IDと同期状態を新たに作るのは接続・識別後とする。未接続でも保存された割当先は予約済みとして扱い、他UIDへ自動仮割当しない。UIDと機器種別を照合し、保存された種別と異なる識別応答のセッションは終了して保存内容を維持する。割当済みなら通常の初期同期を行い、未割当かつ対象外なら管理操作を待つ。サーバーは3.1の初期状態（停止中）で開始し、全プレイヤーをautoとする。確認表示を再開しない。

### 4.3. Tick

**発生元：** `app`の100ms周期タイマー

**受理条件：** 時刻更新は全状態で受け付け、進行処理は運転中のみ実行する。

**処理：**

1. `app`は4.1の規則に従って処理開始時点の時刻を求め、前回処理した時刻から現在までの未処理区間を処理対象とする。
2. 対象区間内で最も早く期限を迎えるパケット生成、自動転送、または筐体ごとの期限（下表）を選択する。
3. 生成の場合はゲームルールに従ってパケットを生成し、自動転送の場合は対象Botまたは自動転送中のプレイヤーのFIFO先頭の転送を試行し、筐体の期限の場合は下表の処理を行う。
4. パケットの生成・移動・配送・破棄をゲーム状態へ反映し、得点規則に従ってスコアを更新する。得点を数えるのは、通常ラウンドのゲーム時間中のノードだけである。
5. 次回の生成・転送・筐体の期限を更新し、対象区間内の未処理の期限がなくなるまで2〜5を繰り返す。

筐体ごとの期限は次のとおりとする。

| 期限 | 時刻 | 処理 |
|---|---|---|
| カウントダウンの終了 | CHOOSEを受理した時刻の3秒後 | 通常ラウンドではゲーム時間の起点とし、そのノードの得点を数え始める。練習ラウンドでは`send`の受け付けと無操作のタイマーを始める |
| 通常ラウンドの終了 | ゲーム時間の起点の90秒後 | 結果を確定し（3.1・3.5）、結果の段階へ移る。そのノードの自動転送を再開する |
| 結果の終了 | 結果の段階へ移った時刻の30秒後 | 待機へ移る |
| モード選択の終了 | READYを受理した時刻の20秒後 | 待機へ移る |
| 練習の無操作 | カウントダウンの終了、または最後に受理した`send`の時刻の60秒後 | 練習ラウンドを出て待機へ移る（3.6） |

筐体の期限は、同じ時刻のパケット生成・自動転送より先に処理する。ゲーム時間の終了時刻と同時刻の生成・転送・加点は、そのノードの得点に含めない。筐体の期限が同じ時刻なら、ノードIDの昇順で処理する。

カウントダウン中の通常ラウンドは、ゲーム時間の起点より前のため、そのノードの得点を数えない。ネットワーク全体の生成・転送は、他のノードを含めて通常どおり処理する。カウントダウンの残り秒数（3.1）は処理開始時点の時刻から毎回求め直す。

`app`はゲーム上の出来事に基づいて、MCUへの通知を生成する。LEDの確認表示の周期はMCUが管理し、Tickから確認用の周期送信は行わない。Tick自体に対する外部応答は生成しない。

処理周期の判定にはTickの回数ではなく経過時間を使用する。

Tickが遅延した場合も、未処理の生成・転送・筐体の期限を期限順に処理する。新たに生成・到着したパケットを、その生成・到着時刻より前の期限で転送してはならない。管理操作やMCUイベントの前処理も同じ時間進行規則を用い、既に処理した区間を再処理しない。

生成・転送の期限は以下の規則で設定する。

- 各プレイヤーの最初のパケット生成は運転開始（Start）の1秒後とし、以後はゲームルールに従う周期で生成する。
- Botまたは自動転送中のプレイヤーのFIFOが空から非空になった場合、その到着時刻から`1 / 処理速度`秒後を最初の転送期限とする。空のFIFOには転送期限を設定しない。
- 転送・破棄によって先頭を取り除いた後もFIFOが非空の場合は、その処理時刻から`1 / 処理速度`秒後を次回の転送期限とする。FIFOが空になった場合は転送期限を解除する。
- 通常ラウンドを始める（CHOOSEを受理する）とき、そのノードの自動転送の期限を解除する。通常ラウンドが終わる、または打ち切られたとき、FIFOが非空であれば、その処理時刻から`1 / 処理速度`秒後を最初の転送期限とする。手動にしただけのノードは、待機の間も自動で転送する。
- 生成・転送の期限が同じ場合は、パケット生成、Botの自動転送、プレイヤーの自動転送の順に処理する。同じ種類の処理はノードIDの昇順で行う。この規則はゲーム内の期限が同じ処理に適用し、外部入力イベントの先後は4.1に従う。

### 4.4. SEND

**発生元：** プレイヤーMCU

**入力：** Session ID、同期世代（`sync`）・要求ID（`rid`）・PID・転送先を含むSENDメッセージ

**受理条件：**

- 運転中である。
- 筐体の段階が通常ラウンドで、カウントダウンが終わり、ゲーム時間が終了していない。練習ラウンドのSENDは3.6に従う。
- Session IDがプレイヤーノードに対応している。
- `sync`が当該セッションの現在の同期世代と一致する。
- 対象プレイヤーノードが手動操作中である。
- SENDの内容がFIFOおよびゲームルールに適合している。

SENDのPIDは現在の送信元FIFO先頭と一致する必要がある。配送・破棄済みのパケットのPIDを指定した要求は拒否する。PIDは周回して再利用されるが、使用中のPIDは飛ばして採番する（3.2）ので、現在のFIFOにあるPIDは一意である。ラウンドの入りと出、運転の開始・停止では、PIDの値だけでは旧来の要求を判別できないが、MCUへ新しい同期世代の`reset`を送るので、旧世代のSENDは同期世代の照合で拒否する。受信が遅れた旧来のSENDが新しいラウンドへ適用されることはない。通常ラウンドの段階でないノードのSENDは、PIDが実際のFIFOの先頭と一致しても実行しない。切断・再接続ではSession IDが変わり、旧セッションのイベントは無視する。

要求IDはSession IDと組み合わせて扱い、同じセッション内の重複要求を再適用しない。同期世代は新しいRESETを送信キューへ登録する時点で更新し、旧世代のSENDはPIDが先頭と一致しても実行しない。同期世代不一致の新規SENDには要求の`sync`・`rid`で`result(ok=false)`だけを返し、追加のRESETを発行しない。同期世代・要求IDの形式・発行・重複処理はプレイヤー通信仕様に従う。

**処理：**

1. `app`はSession IDから送信元論理ノードを特定する。
2. `app`は同期世代、FIFO先頭および転送先の妥当性を検証する。
3. `app`はゲームルールに従い、転送・配送完了・パケットロスを判定する。
4. `app`は判定結果を送信元と転送先のFIFO、およびパケットの管理情報へ反映する。
5. 配送完了時は、ゲームルールに従って発信者・中継者のスコアを更新する。発信者・中継者のそれぞれについて、通常ラウンドのゲーム時間中であるときだけ加点し、そうでなければ数えない。加えた点は、各プレイヤーの未送信の獲得点として加えた順に積む（5.2）。
6. 送信元プレイヤーの送信成功コンボを更新する。この転送でパケットロスにならなかった（目的地に着いた、または転送先のFIFOに入った）場合は1増やし、999で止める。この転送でパケットロス（輻輳・タイムアウト・ネットワークループ）になった場合は0に戻す。

**出力：**

- `app`は受信した同期世代と要求IDをそのまま付けた`RESULT`の送信を`serial`へ要求する。
- `app`はパケット移動によって表示内容が変わったMCUの同期処理を実行する。練習ラウンドのノードには、実際のFIFOの変化を送らない（3.6）。
- `app`はパケットが通過した論理リンクに対応するLED制御MCUへの演出を、LEDノード仕様の`LIGHT`として要求する。宛先色・方向・点灯パターンは同仕様に従う。

初回に処理するSENDについては、成功・失敗にかかわらず、既定プロトコルが要求する応答の送信を`serial`へ要求する。重複要求はプレイヤー通信仕様に従って無視する。送信不能時は2.4に従ってセッションを終了し、再接続時に再同期する。

`result.ok`は転送要求の受理を表し、最終目的地への配送成功を表さない。正当なSENDを受理し、送信元FIFOから先頭を取り除いた場合は、転送先でパケットロスとなる場合も`ok=true`を返す。不正なSENDや段階・操作状態による拒否では`ok=false`を返し、要求によってFIFOを変更しない。パケットロスの条件と得点への影響はゲームルールに従う。

送信成功コンボは`app`がプレイヤーノードごとに保持する、筐体の表示専用の値であり、スコア・上位%・ゲーム記録には影響させない。得点に影響させると得点のルールの変更になり、3.5のゲーム記録の母集団に変更前と変更後のスコアが混ざるためである。判定は処理3のパケットロスの判定だけを用い、転送先より先のノードでパケットロスになっても変えない。他のプレイヤーやBotの操作でコンボが切れないようにするためである。拒否したSENDでは変えない。Botと自動転送のプレイヤーの転送（4.3）は数えず、自動操作のプレイヤーとBotのコンボは常に0とする。通常ラウンドを始めるとき（カウントダウンの開始）、ラウンド・結果から待機・モード選択へ移るとき、運転の開始・停止、自動操作への切替（3.3の切断による切替を含む）で0に戻す。結果の段階では終了時点の値を保持する。時間の経過では戻さない。練習ラウンドでは常に0とする。

RESULTと表示同期の順序、再送、重複要求の扱いはプレイヤー通信仕様に従う。旧来の要求と、RESET前の要求は、同期世代とセッションの照合で拒否する。MCUも同期世代と要求IDを照合し、取り消された要求の遅延応答を新しい要求へ適用しない。

### 4.5. MCUの接続種別判別とプレイヤーMCU接続・切断

サーバーは新しいシリアルセッションで接続先の種別を未確定として扱い、共通の識別要求`{"type":"identify","data":{}}`をLF終端で直ちに送信する。有効な識別応答を受信するまで1秒間隔で再送する。

`serial`は識別前の受信行を、プレイヤー通信仕様のJSON形式の`hello`と、LEDノード仕様の`HELLO UID`の両形式で判定する。有効な応答の形式から種別を確定し、UIDをDevice IDとして識別したら`identify`の再送を停止する。不正な入力は破棄して識別要求を継続し、片方の形式で解釈できないことだけを理由にセッションを終了しない。

種別未確定の受信蓄積上限は32768バイトとする。LEDの`HELLO`候補はLEDノード仕様の96バイト上限・文字・引数を検証し、LEDと識別した後はそのセッションに96バイト上限を適用する。HELLO待ちの行長超過・行途中の1秒の受信停止は当該行をLFまで破棄して識別要求を継続する。識別後は対応する通信仕様の異常時処理に従う。

初めて識別したUIDには、停止中・運転中を問わず、同じ機器種別の空いているノードIDを一つ選んで自動で仮割当する。空いているノードには手動のプレイヤーがいない（MCUのないノードは自動操作である）ので、運転中の仮割当で遊んでいる人の筐体が入れ替わることはない。既存の対応は未接続の機器の分も予約済みとして扱い、上書きしない。仮割当は4.2.3の保存に成功してから通常と同じ対応表へ確定し、専用の確定操作は設けない。置換前の保存失敗・置換自体の失敗では未割当で待機し、置換後の親ディレクトリ同期失敗では4.2.3に従ってサーバーを停止する。管理者が実機の表示・点灯を確認し、4.2.1の操作で本番の配置へ合わせる。

空きがない場合は、UID・機器種別・接続状態を管理画面に公開して未割当のまま待機させる。まだ一度も割り当てていない接続済み機器については、空きが生じた時点で仮割当を再試行する。管理操作の結果として未割当になったUIDは自動仮割当の対象から外し、再接続しても明示的な管理操作を待つ。この対象外情報も4.2.3に従って保存・復元する。

切断だけでは対応を解除しない。同じUIDの再接続では現在の対応表に従って元の役割へ戻す。予備基板への交換後に旧基板が再接続しても、旧UIDの割当を自動復元せず、交換先の担当を奪い返させない。対応表と自動仮割当の対象外となったUIDの情報は運転の開始・停止で維持し、サーバー再起動時も4.2.3の保存ファイルから復元する。

種別確定後は、その種別の通信形式・設定・同期手順を適用する。以下の表と4.6はプレイヤーMCUを対象とし、LED制御MCUの識別と識別後の手順はLEDノード仕様に従う。

| 入力イベント | appの処理 |
|---|---|
| Connected | Session IDを登録し、identifyを送信してMCUの識別処理を開始する |
| 識別完了（割当済み） | 対応表からプレイヤーノードを特定し、初期同期を実行する。自動仮割当した場合も同じ |
| 識別完了（未割当） | 上記の仮割当条件を満たせば割り当て、満たさなければ管理クライアントへ公開して待機 |
| Disconnected | Session IDを無効化し、対象MCUを未接続にする |
| 再接続後の識別完了 | 新しいSession IDを登録し、現在のゲーム状態に基づいて再同期する |

プレイヤーMCUの切断時は、対応するプレイヤーノードを自動操作へ切り替え、ラウンド・モード選択・結果が進んでいれば打ち切って待機へ戻す（3.1）。

未割当のMCUからゲーム操作を受け付けない。再接続時は最新の対応表を使用し、3.3の規則に従って操作状態を維持する。無効化済みSession IDからの遅延イベントはゲーム状態に反映しない。

同じDevice IDを持つ接続が既に有効な場合、既存Session IDを維持し、新しいセッションを論理ノードに対応付けない。重複をログに記録し、重複セッションからゲーム操作を受け付けない。既存セッションの切断後に行われた識別は、通常の再接続として扱う。

MCUの接続・切断は運転状態を変更しない。

### 4.6. プレイヤーMCUのIDENTIFY・HELLO・RESYNCと通信形式の不正

新しいセッションでは直ちに`identify`を送信し、有効な`hello`を受信するまで1秒間隔で再送する。MCUはどの状態でも`identify`で操作を停止して`hello`を返すため、100ms以上の切断検知に依存せず再識別できる。UIDをDevice IDとして識別したら`identify`の再送を停止し、4.5の仮割当・再接続規則を適用する。割当済みなら`config(preview=false)`、新しい同期世代と現在のFIFOの`reset`、現在の`phase`、現在の`status`の順に送信し、結果の段階なら続けて`summary`を送る。練習ラウンドの`reset`は練習用キューの内容にする（3.6）。未割当なら管理画面へ公開して待機する。HELLOの再受信でセッションや要求IDの履歴を初期化しない。

HELLO待ちに受信した旧SEND・READY・RESYNCはゲーム操作や要求IDの履歴に反映せず破棄し、切断せずに識別要求を継続する。不正な行や受信途中の旧データもプレイヤー通信仕様に従って破棄する。

通常表示中の割当済みMCUからの`resync`には、全段階で現在のFIFO（練習ラウンドでは練習用キュー）の`reset`、現在の`phase`、現在の`status`の順に返し、結果の段階なら新しい同期世代の`summary`を続ける。確認中の対象からの`resync`では先に確認を終了し、4.2.2の復旧手順で`config(preview=false)`から送る。同期を理由にゲーム状態・操作状態・受理済みの準備完了状態・要求IDの履歴を初期化しない。入力前の時間進行処理は4.1に従う。未割当の識別済みMCUからの`resync`は、実機確認中なら確認表示を終了して`identify`で一時設定を解除し、それ以外は対応付けを待つ。再試行周期、識別前のメッセージ、不正データおよび切断時の処理は[プレイヤー通信仕様](./player.md)に従う。

初期設定・再同期でMCUが`status`を取得できなかった場合や、結果の段階の通常表示で`summary`を取得できなかった場合も、プレイヤー通信仕様の3秒の取得期限に従って`resync`が送信される。サーバーはこれを通常の再同期要求として処理し、値が変わっていなくても現在の`status`と、Finishedなら確定結果の`summary`を返す。正常な無通信を検出するための定期的な`status`・`summary`送信は追加しない。

識別後の通信データのJSON形式・必須フィールド・型・範囲の不正は`serial`が検出し、当該セッションを終了して`Disconnected`を通知する。HELLO待ちの不正な入力は切断せず破棄する。形式が正しいSENDの同期世代・筐体の段階・操作状態・FIFO・隣接関係による拒否は`app`が判定する。

### 4.7. READY（長押しの通知）

**発生元：** プレイヤーMCU

**入力：** Session ID、最後に適用したRESETの同期世代（`sync`）

**受理条件：**

- Session IDが現在有効で、識別・プレイヤーノードへの割当が済んでいる。
- 運転中である。
- 筐体の段階が待機、結果、または練習ラウンド（カウントダウン中を含む）である。通常ラウンド・モード選択・停止中では受理しない。
- 対象プレイヤーノードがmanual（受付）である。autoはボット固定であり、長押しを受け付けない。
- 当該セッションでRESETを発行済みで、要求の`sync`が現在の同期世代と一致する。

`app`は4.1の入力イベントの処理単位で条件を検証し、成立した場合だけ対象ノードをモード選択へ移し、20秒の期限を設ける。結果の段階から移る場合、確定した結果と記録は変えない。上位%とプレイヤーへ送るベストスコアは消す（3.1）。練習ラウンドから移る場合は、実際のFIFOをMCUへ送り直す（3.6）。受理したときは、`phase(Select)`、練習ラウンドから移る場合は実際のFIFOの`reset`、`status`の順に送る。要求の重複（すでにモード選択にある場合）は、受理しない条件に当たる。操作モード・FIFO・スコア・SENDの要求ID履歴を変更しない。長押し時間の判定はMCUが担当し、サーバーは通信仕様の受理条件を検証する。

割当済みの有効なセッションから形式が正しいREADYを受信した場合、受理・拒否にかかわらず、同じ確定状態から生成した現在の`status`を返す。RESULTや追加のRESETは送らない。同期世代不一致、auto、受理する段階でない場合は段階を変更しない。未割当の識別済みセッションは無視して対応付けを待ち、HELLO待ち・無効な旧Session IDは既存の規則に従って破棄する。

READYとStart、Stop、切断、設定変更、ReturnToBotが競合した場合も、4.1の受け付け順で直列に確定し、各処理で最新状態を検証する。モード選択へ移る前に打ち切られたノードは、待機へ戻る。Stop前の遅延READYは、運転の開始・停止のたびに同期世代が新しくなるので、次の運転で受理されない。

### 4.8. CHOOSE（モードの選択）

**発生元：** プレイヤーMCU

**入力：** Session ID、最後に適用したRESETの同期世代（`sync`）、選択（`round`: `normal`または`tutorial`）

**受理条件：**

- Session IDが現在有効で、識別・プレイヤーノードへの割当が済んでいる。
- 運転中である。
- 筐体の段階がモード選択である。
- 対象プレイヤーノードがmanualである。
- 要求の`sync`が現在の同期世代と一致する。

`app`は条件を検証し、成立した場合に次の処理を行う。モード選択の20秒の期限は解除する。

| 選択 | 処理 |
|---|---|
| `normal` | 通常ラウンドへ移る。ゲーム時間の起点を処理時刻の3秒後に設定し、そのノードの自動転送を止める。そのノードの得点・未送信の獲得点・送信成功コンボを0にする。`phase(Playing)`、`status`（`round=normal`、`countdown=3`、`remaining=90`）の順に送る |
| `tutorial` | 練習ラウンドへ移る。3秒のカウントダウンを始め、3件の練習用キューを作る（3.6）。`phase(Playing)`、練習用キューの`reset`、`status`（`round=tutorial`、`countdown=3`、`window=60`、`bots`）の順に送る |

拒否した場合は、READYと同じく現在の`status`を返す。RESULTや追加のRESETは送らない。MCUはCHOOSEの送信後、3秒以内に`phase(Playing)`を取得できなければ`resync`する（プレイヤー通信仕様）。`round`が`normal`・`tutorial`以外の値は、通信データの形式の不正としてserialが処理する（4.6）。

CHOOSEとStop、切断、設定変更、ReturnToBotが競合した場合も、READYと同じく4.1の受け付け順で直列に確定し、各処理で最新状態を検証する。

## 5. MCUへの出力

### 5.1. 出力の分類

`app`が`serial`へ送信を要求する契機を以下に限定する。プレイヤーMCU向けメッセージは、プレイヤー通信仕様の`identify`、`config`、`reset`、`push`、`result`、`phase`、`status`、`summary`とする。LED制御MCU向けの命令は、共通のJSON形式の識別要求`identify`と、LEDノード仕様の`CONFIG`、`LIGHT`、`CHEER`、`BUFFER`、`CLEAR`とする。共通の`identify`を除き、プレイヤー向けのJSON形式・同期世代・要求ID・筐体の段階・スコア・残り時間・確定結果の通知をLED制御MCUへ適用しない。

| 分類 | 送信契機 |
|---|---|
| 要求応答 | MCUから受信したSENDへのRESULT、READY・CHOOSEへのSTATUSなど |
| 初期化・復旧 | MCU識別完了、再接続、再同期 |
| 状態変更通知 | MCUに表示させるゲーム情報の変更 |
| 演出指示 | パケットの論理リンク間移動、通常ラウンドの結果確定時のベストスコアなど、表示すべきゲーム上の出来事。LEDノード仕様の命令を使用 |
| 実機確認 | 4.2.2のpreview設定による確認表示の開始・停止と正本表示への復旧。周期描画はMCUが行う |

状態変更通知は、ゲーム状態が変更されたという理由だけでは送信しない。MCUに提示する情報の更新が必要な場合に送信する。

### 5.2. 状態変更と通知先

| ゲーム上の出来事 | appが更新を評価する対象 | 仕様の扱い |
|---|---|---|
| パケット生成 | 生成元プレイヤーMCUのFIFO表示。練習中のノードを除く | 初期実装 |
| パケット転送 | 送信元・転送先MCUのFIFO表示。練習中のノードを除く | 初期実装 |
| パケット配送完了・破棄 | 送信元MCUのFIFO表示。練習中のノードを除く | 初期実装 |
| 筐体の段階の変更 | 対象の接続・識別・割当済みのプレイヤーMCU | 初期実装 |
| BotのFIFO使用量変更 | 対象BotのLED制御MCUへのBUFFER通知。練習中のプレイヤーMCUへのstatus通知（`bots`） | LEDノード仕様に定義済み。`bots`は3.6.1 |
| プレイヤーの操作状態変更 | 接続済みの対象プレイヤーMCUへのconfig.mode設定。ラウンドの開始・終了では送らない | 初期実装 |
| スコア・残り時間・段階の残り時間・カウントダウンの残り秒数・送信成功コンボの変更、加点 | 対象プレイヤーMCUへのstatus通知 | 初期実装 |
| 通常ラウンドの結果確定・結果の段階の同期 | 対象プレイヤーMCUへの確定結果summary通知 | プレイヤー通信仕様に定義済み |
| パケットのリンク間移動 | 対応するLED制御MCUへのLIGHT指示。練習の`send`は送らない | LEDノード仕様に定義済み |
| 通常ラウンドの結果確定 | 結果を確定した1人のノードにつながるリンクを担当するLED制御MCUへのCHEER指示。練習・打ち切りは送らない | LEDノード仕様に定義済み。送り先とSTYLEは5.3 |

FIFO表示の同期範囲、送信メッセージ、更新順序はシリアル通信プロトコル仕様に従う。

`app`は通知対象のSession IDを特定し、送信対象が未接続の場合は、そのセッションへの送信を要求しない。

筐体の段階の変更（3.1）は`phase`で通知する。`phase`は全体のフェーズではなく、その筐体の段階を表す。停止中は`Preparing`、待機は`Idle`、モード選択は`Select`、ラウンドは`Playing`、結果は`Finished`である。自動操作中のプレイヤーMCUも対象とする。ラウンドの開始・終了では`config`を送らない。送ると、筐体の表示状態が初期化されるためである。操作状態が実際に変わる場合の`config`は4.2に従う。

通常の初期設定・再接続時は`config(preview=false)`、`reset`、`phase`、`status`の順、再同期時は`reset`、`phase`、`status`の順に送信する。練習ラウンドの筐体への`reset`は練習用キューの内容で、再同期時の順序は3.6による。運転の開始・停止時は、現行のResetの手順を使い、Startでは`phase(Idle)`、Stopでは`phase(Preparing)`、空FIFOの`reset`、初期値の`status`の順に送信する（4.2）。READYの受理では`phase(Select)`（練習から出る場合は実際のFIFOの`reset`を挟む）と`status`、CHOOSEの受理では`phase(Playing)`と`status`（練習では練習用キューの`reset`を挟む）の順に送る（4.7、4.8、3.6）。通常ラウンドの結果確定では`phase(Finished)`、`status`、`summary`を送り、結果の通常表示中の各同期手順でも`status`の後に新しい同期世代の`summary`を追加する。確認中の対象の復旧・解除は4.2.2に従う。関連する通知は同じ確定状態から生成する。

フェーズ通知だけではFIFOの同期世代や要求IDの履歴を変更しない。MCUはFIFO同期済みかつ取得済みフェーズがPlayingで、`config.mode`がmanualかつpreviewがfalseの場合だけ新規SENDを送信する。フェーズ通知で処理中の転送要求（SEND）の応答待ちを取り消さず、RESULTは既存の照合規則で適用する。長押し（READY）とモード選択（CHOOSE）の確認待ちは、プレイヤー通信仕様に従ってMCUが管理する。サーバー側のSEND受理条件は4.4の規則を引き続き適用する。

`status`は対応付けられたプレイヤーの現在スコアと、その筐体の段階に応じた残り秒数・カウントダウンの残り秒数（`countdown`）・段階が時間切れになるまでの秒数（`window`）を同じ確定状態から取得し、毎回通知する。スコアは絶対値、`ready`は常に`false`とする。通常ラウンドの残り秒数は`ceil(max(0, ゲーム時間 - 経過時間))`とし、カウントダウン中はゲーム時間とする。通常ラウンドの段階以外では`remaining`を0とする。`countdown`は3.1の値とし、カウントダウン中の通常ラウンドと練習ラウンド以外では0とする。`window`は、モード選択では20〜0、結果では30〜0、練習ラウンドでは無操作の残り秒数（60〜0）、それ以外では0とし、いずれも残りの`ceil`である。`round`は、通常ラウンドと結果で`normal`、練習ラウンドで`tutorial`、それ以外で`null`とする。値の型と範囲、各段階での値はプレイヤー通信仕様に従う。

`status`には、`rank`（常に`null`）、獲得点（`gains`）、送信成功コンボ（`combo`）も毎回含める。いずれも筐体の表示専用であり、得点には影響しない。練習ラウンドの`status`には、`bots`も付ける（3.6.1）。

- `rank`は常に`null`とする。ラウンドは1人で行うため、順位を付けない（[ゲームのルール](../rules.md#最終順位)）。一斉ゲームの暫定順位は廃止した。
- `gains`は、そのセッションへ前回`status`を送ってから後に、対応付けられたプレイヤーへ入った点を、4.4・4.3の加点の順に並べた配列とする。`app`はプレイヤーノードごとに未送信の獲得点を積み、`status`の送信時に取り出して空にする。1回の`status`には先に入った16件までを入れ、超えた分は捨てる。初期設定・対応付け変更・操作モード変更・再同期・実機確認の開始と終了の同期手順で送る`status`では`[]`とし、未送信の点も捨てる。通常ラウンドの開始、ラウンドの終了または打ち切り、運転の開始・停止でも捨てる。点が入っていなければ`[]`とし、`null`にしない。練習ラウンドでは常に`[]`とする。
- `combo`は4.4で更新する送信成功コンボの値とする。

初期同期・再同期・段階の変更時と、4.7、4.8で応答対象となるREADY・CHOOSEの受信時は、値が変わらなくても現在の`status`を送信する。それ以外は、入力イベント確定後にスコア・表示する残り秒数・カウントダウンの残り秒数・段階の残り時間・送信成功コンボ・`bots`のいずれかが変わったか、未送信の獲得点があるプレイヤーMCUに送信する。段階の残り時間は、1秒ごとの変化で1回送る。Tick遅延時は最新値だけを通知し、同一イベント中の途中経過を蓄積して送らない。その間に入った獲得点は、1回の`status`の`gains`にまとめる。待機・モード選択・結果・練習中は点を数えないので、スコアと`gains`は変わらない。MCUは独自の加点・カウントダウン・時間切れの処理を行わず、通知された値を表示する。`status`の通知自体は操作モードや段階を変更しない。

自動転送中のプレイヤーMCUについても、FIFO表示を同期する。ただし練習ラウンドのノードには、実際のFIFOではなく練習用キューを同期する（3.6）。MCUからのSENDによらず先頭が削除された場合は、`reset`で同期する。

`summary`は、通常ラウンドの結果を確定したときに、確定した得点と、3.5.6で確定した上位%（`topPercent`、`bottomHalf`）と、3.5.7で確定したベストスコア（`gameBest`、`gameBestNodes`、`hourBest`、`hourBestStart`、`hourBestMine`、`allTimeBest`、`allTimeBestMine`）を、そのセッションの現在の同期世代とともに送る。`rank`は常に`null`、`eligible`は常に`true`である。`topPercent`は3.5.6のとおり、50以下の場合だけ値を送り、それ以外は`null`とする。51以上の場合は値の代わりに`bottomHalf=true`を送る。ベストスコアの`*Mine`は3.5.7に従う。各項目の型・範囲・組合せはプレイヤー通信仕様に従う。結果の通常表示では、結果を確定した筐体だけが通知対象である。停止中・待機・モード選択・ラウンド・確認表示中・未割当MCUには送らない。終了演出の内容や時間はMCU側の実装に委ねる。

正当なSENDによる送信元の先頭削除は対応する`result(ok=true)`で通知する。同期世代が一致した新規SENDを拒否した場合は、割当済みであれば`result(ok=false)`の後に新しい同期世代と現在のFIFO（練習ラウンドでは練習用キュー）の`reset`を送信する。同期世代不一致の拒否では、先行するRESETによって新しい世代を通知済みのため追加のRESETは送信しない。

RESETに使用するFIFOコピーの確定・現在の同期世代の切替・送信キューへの登録は、他の入力イベントを挟まずに行う。結果の通常表示でRESETを送る場合は、その後にphase・status・新しい同期世代のsummaryを続けて同じ確定状態から登録する。同期世代は運転の開始・停止やセッション再接続、サーバー再起動でも再利用しない。初期同期、末尾追加、対応付け変更を含む具体的な送信順序と同期範囲は、プレイヤー通信仕様を正本とする。

### 5.3. LED制御とBot混雑度表示

LED制御MCUの担当リンク・GPIO、経路演出の速度・尾の減衰・重なり時の加算、およびシグナルタワーの表示色は[LEDノード仕様](./led.md)に従う。

パケットが通過した論理リンクについて、`app`は同仕様の対応表からLED制御ノードを特定し、`LIGHT`の隣接ノード・パケットの最終宛先・移動方向へ変換する。パケットの移動が手動SEND、自動プレイヤー、Botのいずれによる場合も同じ対応表を用いる。

BotのFIFO使用量が変化した場合、`app`は対象BotのLED制御MCUへ`BUFFER`で現在の件数を通知する。色の判定・点灯はLED制御MCUが同仕様に従って行う。同じ値を、練習中のプレイヤーMCUへの`status.bots`にも使う（3.6.1）。`CONFIG`による制御ノードの設定と`CLEAR`による表示消去もLEDノード仕様に従う。

通常ラウンドの結果を確定するとき、`app`はそのラウンドを終えたプレイヤーのノード（以下、対象ノード）につながるテープへ、LEDノード仕様の`CHEER`を送る。テープには対象ノードから外へ、取ったベストスコアの種類に応じた色の光が8秒間流れる。ラウンドは1人で行うので、結果を確定するたびに1人分だけを送る。命令は3.5.7のベストスコアと同じ確定状態から、次の規則で作る。打ち切り、練習の`send`、および練習ラウンドの終わりでは`CHEER`を送らない。

- 対象ノードにつながる4本のリンク（プレイヤー同士2本、Botと2本）へ1件ずつ送る。送り先はそのリンクを担当するLED制御MCUとし、`LIGHT`と同じ対応表で決める。BotとのリンクはBot側、プレイヤー同士のリンクは奇数ノード側の基板が担当する。NEIGHBORはその基板から見た相手のノード、NODEは対象ノードとする。例えばP1が対象なら、LED制御P1へ`CHEER P2 P1 STYLE`と`CHEER P8 P1 STYLE`を、LED制御B1・B3へ`CHEER P1 P1 STYLE`を送る。
- 隣り合うプレイヤーのラウンドが続けて終わると、共有するリンクへの`CHEER`が重なる。同じNEIGHBORへの有効な`CHEER`は、LED制御MCUが新しいNODE・STYLEで置き換える（LEDノード仕様）ので、サーバーは重ねて送るだけとし、まとめない。同時に2人分の演出が流れるのは共有しないリンクだけである。
- STYLEは、対象ノードが取ったベストスコアのうち一番上の1つとする。3.5.7の`allTimeBestMine`と同じ判定で通算のベストスコアを取ったなら`record`、そうでなく`hourBestMine`と同じ判定でこのラウンドが終わった時間帯のベストスコアを取ったなら`hour`、どちらでもなければ`game`とする。1時間ごと・通算のベストスコアを取った人はその回のベストスコアでもあるが、演出を順に出したり重ねたりしない。記録を使えない起動（3.5.3）では3.5.7により両方の判定が`false`になるため、`game`だけになる。
- 送るのは結果を確定するときの1回だけとする。演出はLED制御MCUが8秒で終えるため、止める命令は送らない。結果の段階中の再接続・`HELLO`の再受信・担当変更による通常設定や、確認表示の終了では送り直さない。8秒の短い演出なので、遅れて流すと誰のための演出かわからなくなるためである。通常設定や確認表示の開始で送る`CONFIG`はMCUの演出を消すため、その基板の演出は途中で終わる。
- 確認表示中・未割当・未接続のLED制御MCUへは送らない。8秒の途中で運転を開始・停止した場合は、下記の送信でMCUが演出を消すため、止めるための送信を追加しない。

LED制御MCUも4.5の共通識別要求`identify`を受け付け、独自プロトコルの`HELLO UID`で応答する。UIDの自動仮割当・管理操作による交換と、通常設定時の命令順序は4.2.1・4.5に従う。`CONFIG NODE PREVIEW`のPREVIEWは小文字のtrue・falseを必須とし、通常はfalse、実機確認中だけtrueとする。有効な`CONFIG`ではMCUが同じNODE・PREVIEWへの再設定でも表示・演出状態を初期化する。確認中の通常の`LIGHT`・`CHEER`・`BUFFER`はMCUが適用せず、確認周期はMCU内で管理する。実機確認と終了時の復旧は4.2.2とLEDノード仕様に従う。

運転の開始と停止（StartとStop）ではLEDの確認対象を解除する。確認中の割当済みLED制御MCUには現在の担当の`CONFIG NODE false`、Bot用には続けて初期化後の`BUFFER 0`を送る。確認中の未割当MCUには`identify`を送る。通常表示中の接続・識別・割当済みMCUには`CLEAR`、Bot用には`BUFFER 0`を続け、担当NODEを維持して`CONFIG`は再送しない。確認解除用の`CONFIG`と`CLEAR`を重複送信せず、過去の`LIGHT`・`CHEER`を再現しない。未接続の機器は送信対象に含めず、再接続時の通常設定で現在の状態を通知する。4.5のプレイヤー向け接続・切断処理と4.6のプレイヤー向け同期手順はLED制御MCUには適用しない。

LED制御MCUは起動・`identify`受信・USB未接続の100ms連続検出でpreview=falseへ戻し、確認周期を停止して消灯・未設定へ移る。有効な`CONFIG`まで1秒間隔で`HELLO UID`を送る。不正な`CONFIG`、命令を判別できない入力、行長超過、不正文字、行途中の1秒の受信停止でも同じ初期化を行い、同じセッションから`HELLO`で再識別する。種類を判別できる不正な`LIGHT`・`BUFFER`などはその行だけを破棄し、NODE・PREVIEWと表示状態を維持する。同一セッション・同一UIDのHELLO再受信ではセッション・対応表を維持して通常設定をpreview=falseで再実行し、UID変更ではセッションを終了する。重複UIDの接続では既存Session IDを維持する。LEDと識別済みの接続から不正な入力・行長超過・行途中の1秒の受信停止を検出した場合は、`serial`がセッションを終了して`Disconnected`を通知する。MCU側の不正行の破棄・LFまでの復旧・通常無通信の扱いはLEDノード仕様に従う。

LED制御MCUの同時`LIGHT`演出は全出力合計128件を上限とし、満杯なら新しい演出だけを破棄する。表示上の省略でゲーム上の転送・配送・得点を取り消さず、演出枠の受信確認や再送は追加しない。

## 6. 異常時の処理

| 事象 | 検出主体 | 処理主体と動作 |
|---|---|---|
| 不正な管理操作 | app | appが拒否理由を返し、webがHTTPレスポンスへ変換 |
| 不正なSEND | app | appが転送を拒否し、serial経由で規定のRESULTを返す |
| 受理条件を満たさないREADY・CHOOSE | app | 筐体の段階を変更せず、割当済みの有効なセッションには現在のSTATUSを返す |
| 不正な通信データ | serial | serialが通信プロトコルに従って処理 |
| MCU切断 | serial | appが接続状態を更新。プレイヤーMCUの場合は対象プレイヤーを自動操作へ変更し、ラウンド・モード選択・結果を打ち切って待機へ戻す（記録しない） |
| MCU再接続 | serial | appがデバイスを再識別し、表示状態を再同期 |
| 送信キュー溢れ | serial | Sendがerrorを返し、serialが当該セッションを終了してDisconnectedを通知。appは切断処理を行い、再接続時に再同期 |
| シリアル書込失敗 | serial | serialが当該セッションを終了してDisconnectedを通知。appは切断処理を行い、再接続時に再同期 |
| 運転の停止（ラウンド中を含む） | app | appが全プレイヤーのラウンド・モード選択・結果を打ち切り（記録しない）、4.2の範囲でゲーム状態（PIDの採番を含む）を初期化する。旧来の要求は同期世代とセッションの照合で拒否する |
| 通常ラウンドのFIFOが1000件に達した | app | そのラウンドを打ち切って待機へ戻す。記録しない（3.2） |
| 練習ラウンドの無操作が60秒続いた | app | 待機へ戻す。実際のFIFOは自動で捌き続けている（3.6） |
| Tick遅延 | app | appが4.3に従って実際の経過時間に基づく補正を行う |
| Device IDの重複接続 | app | 既存の対応を維持し、重複セッションのゲーム操作を拒否 |
| デバイス対応表の置換前の保存失敗・置換自体の失敗 | app | 操作に伴う割当・対象外情報・操作モード・確認表示を変更しない。管理操作にはエラーを返し、自動仮割当は未割当で待機。既存機器は動作を継続 |
| 対応表の置換後の親ディレクトリ同期失敗 | app・main | 保存結果不明として成功応答と操作に伴う変更・MCU通知を行わず、ログを記録してサーバーを異常終了。再起動時に保存ファイル全体を検証・復元 |
| 起動時の対応表の破損・読込失敗 | main | 理由をログへ記録して起動を中止。ファイル不存在の場合だけ空の対応表で起動 |
| 起動時の記録ファイルの破損・読込失敗 | main | 理由をログへ記録し、記録を使えない状態として起動を続ける。ファイルを変更せず、その起動中は保存しない。ファイル不存在の場合だけ新しく作成（3.5.3） |
| ゲーム記録の保存失敗 | app | ゲームを止めずにログへ記録し、Snapshotに失敗を示す。自動で再試行しない（3.5.4） |

通信失敗のみを理由として、確定済みのゲーム状態を取り消さない。

ゲーム状態の再同期には、`app`が保持する正本を使用する。

ログは初期実装では標準出力に出力する。

## 7. 後日定義する範囲と関連仕様

### 7.1. 後日定義する範囲

以下の詳細は関連仕様で後日定義する。ゲームルールの追加・修正は`rules.md`で行い、本仕様に独立したルールを追加しない。

| 項目 | 決定が必要な内容 |
|---|---|
| デバイス対応付け | Web管理画面の詳細。対応表と自動仮割当の対象外UIDの保存・復元は4.2.3に定義済み |
| LED制御の残件 | 各テープのLED数を長さ確定後に記入。命令の形式・引数、起動・識別・設定・切断・ゲームResetの手順、実機確認、異常時処理と同時演出数の上限はLEDノード仕様に定義済み |
| スコア保存 | 定義済み。ゲーム記録の保存・読込とベストスコアの集計は3.5に従う。保存は通常ラウンドの結果確定時に行うため、運転停止前の保存確認は設けない |

ゲーム記録は3.5に従って保存・復元し、運転の開始・停止では消去しない。Device IDの対応表と自動仮割当の対象外UIDは4.2.3に従って保存・復元し、運転の開始・停止では消去しない。

### 7.2. 関連仕様

**[ゲームのルール](../rules.md)**

ゲームルールの正本。運転とラウンド、ゲーム時間、生成、転送、パケットロス、得点、上位%、およびベストスコアを定義する。

**[プレイヤーノード仕様](./player.md)**

MCUとのメッセージ形式、SEND/RESULT、RESET/PUSH、FIFO表示同期、再送・重複処理および送信順序を定義する。

**[LEDノード仕様](./led.md)**

制御ノードとリンク・GPIOの対応、経路演出、Bot混雑度表示、共通の`identify`による識別、および`HELLO`・`CONFIG`・`LIGHT`・`CHEER`・`BUFFER`・`CLEAR`の命令を定義する。未確定部分は7.1のLED制御の残件を参照する。

**[Web管理API仕様](./web.md)**

状態取得・管理操作のHTTP API、JSON形式、成功・拒否・エラー応答、管理画面からの状態ポーリングと再試行を定義する。画面のレイアウトとDevice IDの対応付けUIの詳細は別途定義する。対応表の保存・復元は本仕様の4.2.3、ゲーム記録の保存とベストスコアの集計は3.5に従う。

ゲームルールに関する記述が矛盾する場合は`rules.md`を優先する。通信メッセージの形式・順序は対応する通信仕様に従い、矛盾する本仕様の記述を修正する。
