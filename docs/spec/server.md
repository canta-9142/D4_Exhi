# サーバー側プログラム

## 1. 概要

### 1.1. 目的

本ドキュメントは、ネットワークゲームの進行を管理するサーバープログラムについて、各Goパッケージの責務、外部インターフェース、入力イベントに対する処理、および状態管理の規則を定義する。

各パッケージの内部実装、ゲームルール、MCUとの通信プロトコルの詳細は対象外とする。

ゲームルールの正本は[ゲームのルール](../rules.md)とする。パケット生成、転送優先順位、処理速度の初期値、配送・破棄、得点およびランキングの判定は同文書に従う。本仕様では、それらをサーバーが処理する契機と状態管理の責務を定義する。Botの処理速度は管理操作によって変更できる。

プレイヤーMCUとの通信は[プレイヤー通信仕様](./player.md)に従う。MCUへのフェーズ・スコア・残り時間・準備完了状態・確定結果の通知、準備完了要求の受理、および`config.mode`・`config.preview`による操作モードと確認表示の設定を対象とする。

LED制御ノードの担当リンク・GPIO、シグナルタワーの混雑度表示、経路演出、および通信命令は[LEDノード仕様](./led.md)を正本とする。本仕様ではゲーム上の出来事とLED制御要求の対応を定義し、LED数など同文書で未確定の項目は7.1に残す。

### 1.2. 用語

| 用語 | 定義 |
|---|---|
| サーバープログラム | `main`、`app`、`serial`、`web`で構成されるGoプログラム全体 |
| 実行ホスト | サーバープログラムを実行するコンピュータ |
| 論理ノード | ゲーム内のネットワークを構成する頂点。プレイヤー8個、Bot3個 |
| プレイヤーノード | プレイヤーが操作できる論理ノード |
| Botノード | `app`が自動操作する論理ノード |
| MCU | USB CDCによって接続される物理的な制御デバイス |
| 管理クライアント | `web`へHTTPリクエストを送る管理用端末上のソフトウェア |
| ゲーム状態 | フェーズ、論理ノード、パケット、FIFO、スコア、ゲーム内時間に関する情報 |
| 接続状態 | MCUの識別情報、セッション、接続状況 |
| 同期状態 | `app`が管理する、セッションごとの現在の同期世代、MCUに送信済みの情報と再同期の要否 |
| 入力イベント | `app`に処理を要求する操作、通知、またはTick |
| 状態変更 | 入力イベントの処理によって確定したゲーム状態または接続状態の変化 |

論理ノードはプレイヤー8個（P1〜P8）とBot3個（B1〜B3）の計11個である。通常構成の物理MCUは次の計15台とし、実行ホストはこの台数に含めない。

| 物理MCUの種別 | 台数 | 割当先 |
|---|---|---|
| プレイヤー基板（ESP32-S3） | 8 | P1〜P8 |
| LED制御基板（ESP32-C3） | 7 | B1・B2・B3・P1・P3・P5・P7 |

Botのゲーム処理は`app`が実行する。B1〜B3のLED制御基板は担当リンクとシグナルタワーの表示を担当し、Bot処理専用のMCUは設けない。プレイヤー基板のP1とLED制御基板のP1は別の物理機器であり、割当先は機器種別とノードIDの組み合わせで区別する。

論理ノードの集合と物理機器の一覧は別に管理する。15台は通常構成の台数であり、未割当の予備基板や交換後の旧基板も機器一覧へ保持できるため、一覧の件数を11件や15件に固定しない。

### 1.3. パッケージ構成

| パッケージ | 責務 |
|---|---|
| `main` | 設定の読み込み、各パッケージの初期化、起動・終了 |
| `app` | ゲーム状態・論理ノード・接続対応付け・同期状態の管理、入力イベントの処理 |
| `serial` | USB CDC接続の管理、メッセージの送受信、通信プロトコルの処理 |
| `web` | 管理クライアントのHTTPリクエスト受付、`app`への操作要求、レスポンスの生成 |

`app`はゲームロジックを内包する。`serial`と`web`はゲーム状態を直接変更しない。

## 2. 外部インターフェース

### 2.1. 基本規則

- `app`はゲーム状態を変更する操作を直列に実行する。
- `app`は操作要求の成否と、操作に伴う状態変更を区別する。
- `serial`はゲームルールを判断しない。
- `web`はゲームルールを判断せず、`app`の返した結果をHTTPレスポンスへ変換する。
- `app`はゲーム状態と接続状態の整合したコピーを管理クライアントへ提供する。

### 2.2. web → app

| 操作 | 入力 | 戻り値 |
|---|---|---|
| `Execute(ctx, command)` | 管理操作 | 成否・拒否理由 |
| `State(ctx)` | なし | 状態のSnapshot |

`Execute`が受け付ける操作は以下とする。

| 操作 | 引数 |
|---|---|
| `Start` | なし |
| `Finish` | なし |
| `Reset` | なし |
| `SetNodeEnabled` | 論理ノードID、有効/無効 |
| `SetBotRate` | BotノードID、処理速度（pkt/s） |
| `SetDeviceAssignment` | Device ID、対応先の種別とノードID（未指定で対応解除） |
| `SwapDeviceAssignments` | 割当を交換する2台のDevice ID |
| `ReplaceDeviceAssignment` | 交換元と交換先のDevice ID |
| `SetDevicePreview` | 確認表示を行うDevice ID（未指定で停止） |

`SetNodeEnabled`の有効は手動操作、無効は自動操作を意味し、Preparing・Finishedでのみ受け付ける。論理ノード自体の生成・転送処理を停止する操作ではない。Playing中の管理操作による切替は拒否する。

Device IDの対応付けはプレイヤーMCU・LED制御MCUの両方を対象とし、`app`が管理する。初回は4.5に従って空きIDへ自動で仮割当し、管理者が実機の表示・点灯から配置を確認してWeb管理画面から本番の割当へ変更する。管理画面は通常の割当・解除、2台の割当交換、予備基板への交換を上記の操作で要求し、対応表を直接変更しない。LED制御ノードの担当リンクはLEDノード仕様の対応表に従う。

`State`は以下の情報を返す。

| 分類 | 情報 |
|---|---|
| ゲーム | フェーズ、経過時間、残り時間、開始可否（canStart）、開始不可理由 |
| 論理ノード | ID、種別、操作状態、FIFO使用量、各プレイヤーの準備完了状態 |
| MCU | 識別子、機器種別、割当先の種別とノードID、接続状態（未割当の識別済みMCUを含む） |
| 実機確認 | 現在確認表示中のDevice IDと確認用ノードID（一時設定を含む。対象がなければ未指定） |
| スコア | 各プレイヤーの現在スコア、ルールに基づくランキング対象情報 |
| Bot | 各Botの処理速度 |

`web`は管理クライアントからの定期ポーリングに応じて`State`を呼び出す。ポーリングそのものはゲーム状態を変更しない。

開始可否は4.2のStart受理条件から導出する。開始不可理由には、Preparing以外、PID不足、および未準備のmanualノードのIDを含める。開始可能な場合は理由を空とする。管理画面はmanualノードごとの準備状況と開始不可理由を表示し、`canStart`がtrueの場合だけ「開始」を有効にする。古いSnapshotによる操作もあり得るため、`app`はStartの処理時点で条件を再検証し、満たさなければ拒否理由を返す。

HTTPエンドポイント、JSON形式、拒否理由とHTTPステータスの対応、および管理画面からの状態取得・再試行は[Web管理API仕様](./web.md)に従う。画面のレイアウトは`web`の担当範囲として別途定義する。

### 2.3. serial → app

`serial`は以下の入力イベントを`app`へ通知する。

| 入力イベント | 内容 |
|---|---|
| `Connected` | シリアル接続が確立した |
| `Disconnected` | シリアル接続が終了した（送信キュー溢れ・書込失敗による終了を含む） |
| `MessageReceived` | MCUからメッセージを受信した |

各入力イベントには、発生元を識別するSession IDを含める。

MCUのDevice IDは識別処理によって取得する。`app`はDevice IDごとに機器種別と割当先の種別・ノードIDを管理し、Session IDと区別する。同じDevice IDでも、再接続時には新しいSession IDを用いる。

### 2.4. app → serial

`app`は`Send(session, message) error`によって、指定したシリアルセッションへのメッセージ送信を要求する。送信キューへの登録に成功した場合は`nil`、失敗した場合は`error`を返す。

`serial`は接続ごとに送信順序を維持する。

`Send`の成功は送信キューへの登録成功を意味し、MCUによる受信完了を保証しない。

送信キュー溢れ、または登録後の書込失敗が発生した場合、`serial`は当該セッションを終了し、`Disconnected`を通知する。終了したセッションへの追加送信は`error`を返す。`app`は通常の切断処理を行い、再接続・識別完了後に現在のゲーム状態へ再同期する。通信失敗によって確定済みのゲーム状態を取り消さない。

メッセージ形式、送信順序、応答・同期・再送処理は、別途定義されたシリアル通信プロトコル仕様に従う。

## 3. ゲーム状態と処理規則

### 3.1. ゲームフェーズ

| フェーズ | ゲームの動作 |
|---|---|
| `Preparing` | パケット生成・転送・スコア更新を行わない |
| `Playing` | パケット生成・転送・スコア更新を行う |
| `Finished` | ゲーム進行を停止し、最終スコアを保持する |

サーバー起動時はPreparingとし、パケット・FIFO・スコア・ゲーム内時間を初期化する。プレイヤーノードは自動操作かつ準備未完了（false）で開始する。4.2.3に従って保存済みの対応表を復元し、保存のない機器は4.5の条件で自動仮割当する。管理者が実機の表示から対応を確認・調整して手動操作へ切り替える。

許可するフェーズ遷移は以下とする。

| 操作 | 遷移 |
|---|---|
| `Start` | Preparing → Playing |
| `Finish` | Playing → Finished |
| ルールで定めるゲーム時間の終了 | Playing → Finished |
| `Reset` | 任意のフェーズ → Preparing |

定義されていない遷移は拒否する。

ゲーム時間の終了は`app`が経過時間から判定する。Finishedへの遷移後は、MCUの接続・再同期や管理クライアントの状態取得によって最終スコアを変更しない。

Finishedへの遷移時に最終スコア・ランキング資格・順位を同じ確定状態から決定し、以後の操作状態変更、切断・再接続、基板交換によって当該ゲームの結果を変更しない。順位計算はゲームルールの「最終順位」に従い、ランキング対象外のプレイヤーを比較にも人数にも含めない。同点の対象者は同順位とする。対象外にもスコアを保持し、順位は未指定とする。

### 3.2. 論理ノード

| 項目 | プレイヤーノード | Botノード |
|---|---|---|
| 個数・パケット生成 | ゲームルールに従う | ゲームルールに従う |
| 転送方式 | 手動または自動 | 自動 |
| 転送順序 | FIFO | FIFO |
| バッファ容量 | ゲーム上は無制限 | ゲームルールに従う |
| 経路選択 | 手動時はプレイヤー、自動時は事前計算した優先順位 | 事前計算した優先順位 |

生成元・宛先の条件、転送速度の初期値、転送先の優先順位、パケットロスの判定はゲームルールに従う。

Botの処理速度は初期値1pkt/sとし、SetBotRateでノードごとに変更できる。プレイヤーの自動転送速度はゲームルールに従い、SetBotRateの対象としない。

`app`は各パケットについて、所在・FIFO順序に加え、ゲームルールの判定に必要な発信元、宛先、ホップ数、TTL、通過ノードを管理する。MCUは表示用キャッシュを持ち、ゲーム状態の正本は持たない。

PIDは0〜65535の範囲で、サーバープロセス内の通し番号として昇順に発行する。配送・破棄・Resetによって採番カウンタを戻さず、同じプロセス内でPIDを再利用しない。未発行のPIDが次ゲームの最大生成数である1000件分に満たない場合、Startを拒否し、サーバー再起動が必要であることを管理クライアントへ返す。PIDを周回させて再利用しない。

初期実装では1ゲームに生成される全パケット数が1000件を超えないことを前提とする。プレイヤーFIFO全体をMCUの最大1024件のキャッシュへ同期し、部分キャッシュや分割補充は行わない。この前提を超えるゲーム、およびキャッシュ容量を超えた場合のサーバー動作は本仕様では定義しない。通信データの検証はプレイヤー通信仕様に従う。

### 3.3. ノードの操作状態

プレイヤーノードは手動操作または自動操作で動作し、初期値は自動操作とする。MCUへの通知は`config.mode`の`manual`・`auto`を用いる。

- Preparing・Finishedで管理者がプレイヤーノードを無効化すると、`app`は当該ノードを自動操作へ切り替える。
- 対応するプレイヤーMCUが切断されると、`app`は当該ノードを自動操作へ切り替える。
- 対応するMCUが未接続の場合、管理者による手動操作への切替要求は拒否する。
- 自動操作中もパケット生成、FIFO管理およびゲーム上の転送を継続する。
- MCUが再接続しても手動操作には自動復帰せず、自動操作を継続して`config(mode=auto)`を送信する。手動操作への切替はPreparing・Finishedでの管理者の操作による。
- Playing中は管理操作による切替を行わず、MCU切断時のみ自動操作へ切り替える。
- Finishedでの再接続は現在のゲーム状態への再同期を行い、ゲーム進行を再開しない。
- 得点計算および自動操作ノードのランキング対象判定はゲームルールに従う。

ゲーム上の操作状態と、MCUの接続状態は別々に管理する。

### 3.4. プレイヤーの準備完了状態

準備完了状態は`app`がプレイヤーノードごとに保持する。初期値はfalseとし、操作モード・FIFO同期状態・ゲームフェーズとは独立して扱う。準備完了の通知で操作モードを変更せず、管理操作による手動・自動操作の設定は管理者だけが行う。切断時の自動操作への切替は3.3の規則に従う。autoノードは常に準備未完了とし、Startの準備完了判定から除外する。

| 契機 | 準備完了状態 |
|---|---|
| 4.7の条件を満たすREADYを受理 | 対象ノードをtrue。重複してもtrueのまま |
| ゲームのReset | 全プレイヤーをfalse |
| MCU切断、実際の操作モード変更 | 対象ノードをfalse |
| 対応付けの解除・変更 | MCUを失うノードと新たに割り当てられるノードをfalse |
| 通常のFIFO再同期、同一セッション・同一UIDのHELLO再受信、同じ設定の再通知 | 保持 |
| Playing・Finishedへの遷移 | 保持。以後のゲーム進行を制御する条件にはしない |

同じモードや対応付けを再設定しただけでは、受理済みの準備完了を解除しない。ゲームのResetはPreparing中でも全員をfalseへ戻す。準備完了の再要求で取り消す操作は設けない。

現在manualである全プレイヤーが準備完了になると、他のStart受理条件も満たす場合に管理画面から開始できる。manualノードが0台の場合、準備完了の条件は満たしているものとして扱う。準備完了だけではPlayingへ自動遷移せず、管理者のStartを待つ。

## 4. 入力イベントの処理

### 4.1. 共通規則

`app`は入力イベントを直列に処理する。

各入力イベントについて、`app`は受理条件の判定、ゲーム状態の変更、要求元への応答、MCUへの通知の要否判定を行う。

異なる入力元から同時に到着した入力イベントについては、`app`が受け付けた順序で処理する。入力元間の固定優先順位は定めない。

ゲーム状態の変更は、1入力イベントの処理単位で確定させる。

管理操作、MCUからの入力イベント、およびTickを処理する際は、まず`app`が処理を開始した時点の単調増加する時刻を基準に、未処理の生成・自動転送を期限順に確定する。その後、更新後の状態に対して入力イベントの受理条件を判定し、操作を適用する。Tickの発行時刻やMCU側の時刻によってゲーム時間を巻き戻さない。

ゲーム終了時刻に達している場合は、終了時刻より前の生成・転送を確定してFinishedへ遷移した後、入力イベントを処理する。`State`は確定済み状態のSnapshotを取得するだけとし、時間進行処理を起動しない。

### 4.2. 管理クライアントからの入力

| 入力 | 受理条件 | appの処理 | webへの結果 |
|---|---|---|---|
| Start | Preparing、未発行PIDが1000件分以上あり、現在manualの全プレイヤーが準備完了。manualが0台の場合は準備完了条件を満たす | Playingへ遷移し、時間基準とランキング対象情報を設定 | 成否・拒否理由 |
| Finish | Playing | Finishedへ遷移し、最終スコア・ランキング資格・順位を確定 | 成否 |
| Reset | 全フェーズ | Preparingへ遷移し、パケット・スコア・タイマーを初期化 | 成否 |
| SetNodeEnabled | PreparingまたはFinished。プレイヤーが指定され、手動操作にする場合は対応MCUが接続・識別済み | 操作状態を変更し、接続中ならconfigから再同期 | 成否 |
| SetBotRate | 全フェーズ。Botが指定され、設定値が有限の正数 | 処理速度を変更 | 成否 |
| SetDeviceAssignment | PreparingまたはFinished。識別済みDevice IDと同じ機器種別の有効な対応先で、対応が競合しない。解除も可 | 対応表を更新し、接続中なら対象MCUを再設定 | 成否 |
| SwapDeviceAssignments | PreparingまたはFinished。同じ機器種別の異なる2台が割当済み | 2台の対応を一括で交換し、接続中なら再設定 | 成否 |
| ReplaceDeviceAssignment | PreparingまたはFinished。交換元が割当済みで、交換先が同じ機器種別の別UIDかつ接続・識別済み。交換元は未接続でも可 | 交換元の役割を交換先へ付け替え、交換元を未割当にする | 成否 |
| SetDevicePreview | 開始はPreparingまたはFinishedで、対象が接続・識別済み。未割当も可。割当済みプレイヤーの場合はauto。停止は全フェーズで可 | 4.2.2に従い、対象1台の確認表示を開始・停止 | 成否・拒否理由 |
| State | 常時 | Snapshotを取得 | Snapshot |

ResetではMCUとのシリアル接続、Device IDの対応表、プレイヤーの操作状態、Botの処理速度、およびPIDの採番カウンタを維持する。パケット・FIFO・スコア・当該ゲームのランキング対象情報・ゲーム内時間および生成・転送タイマーを初期化し、全プレイヤーの準備完了をfalseにする。割当済みプレイヤーMCUには`phase(Preparing)`、新しい同期世代の空FIFOの`reset`、`status(score=0, remaining=ゲーム時間, ready=false)`の順に送信する。初期化後のランキング対象判定はゲームルールに従う。

LED制御MCUには5.3とLEDノード仕様のゲームReset手順を適用する。確認対象を解除し、確認中の割当済みMCUには現在の担当の`CONFIG NODE false`、Bot用には続けて初期化後の件数の`BUFFER 0`を送る。確認中の未割当MCUは`identify`で一時設定を解除する。それ以外の接続・識別・割当済みMCUには`CLEAR`、Bot用には続けて`BUFFER 0`を送り、担当NODEを維持して`CONFIG`は再送しない。確認解除用の`CONFIG`直後に`CLEAR`を重複送信しない。

Start時に現在の操作状態からランキング対象情報を設定する。Playing中にMCU切断で自動操作へ切り替わった場合は、ゲームルールに従って当該ゲームのランキング対象から外す。Finishedで手動操作へ戻しても当該ゲームの確定済みランキング対象情報を変更しない。

SetBotRateで速度を変更した場合、Playing中でFIFOが空でなければ、変更時刻から新しい速度に基づく1パケット分の待ち時間を経て次回の転送を行う。FIFOが空の場合は、次にパケットが到着した時点から待ち時間を計る。PreparingとFinishedでは設定のみ変更し、転送を実行しない。

SetNodeEnabledの対象はプレイヤーノードのみとする。Botは常に自動操作とし、この操作の対象に含めない。

SetNodeEnabledで操作モードを変更した場合、対象ノードの準備完了をfalseにし、接続済みの対象MCUへ現在のモードを含む`config(preview=false)`、現在のFIFOの`reset`、現在の`phase`、現在の`status`の順に送信する。Finishedなら続けて`summary`を送る。同じセッション内の要求IDの履歴は維持する。同じモードの再設定では準備完了を保持する。Playing中の再接続・識別に伴う`config`は現在モードの通知であり、管理操作による切替や手動操作への復帰を意味しない。

#### 4.2.1. デバイスの割当・交換

対応は機器種別ごとにDevice IDとノードIDの一対一とする。プレイヤーMCUはP1〜P8、LED制御MCUはLEDノード仕様のB1・B2・B3・P1・P3・P5・P7を割当先とする。例えばプレイヤーP1とLED制御P1は別の割当先であり、機器種別をまたぐ割当・交換は拒否する。

| 操作 | 対応表の変更 |
|---|---|
| SetDeviceAssignment | 空いている対応先へ割当・移動する、または解除する。同じ対応の再設定も受け付ける。他のUIDが使用中の対応先は上書きせず拒否する |
| SwapDeviceAssignments | 2台の割当先を一括で交換する。一方だけの変更は確定しない |
| ReplaceDeviceAssignment | 交換元の割当を解除し、同じ役割を交換先へ割り当てる。交換先に仮割当などの既存の役割があれば、その割当も解除する。交換元へはその役割を引き継がせない |

`app`は各操作の条件を処理時に検証し、4.2.3の保存に成功してから、対応表の変更を1入力イベント内で一括確定する。条件不成立または保存失敗なら、その操作に伴う対応表・自動仮割当の対象外情報・操作モード・準備完了状態・確認表示の変更とMCUへの通知を行わない。交換・付け替えは物理基板の担当を変更する操作であり、ノード間でFIFO・スコア・ランキング対象情報を移動・初期化しない。

担当UIDが実際に変わるプレイヤーノードは、担当を失う側・新たに受け取る側ともに自動操作へ切り替え、準備完了をfalseにする。同じ対応の再設定では変更しない。管理者は表示を確認して手動操作へ切り替え、プレイヤーは再度準備完了を行う。

接続済みプレイヤーMCUが新しい担当を受け取る場合は、`config(mode=auto, preview=false)`、現在のFIFOの新しい同期世代の`reset`、現在の`phase`、そのプレイヤーの現在の`status`の順に同期する。Finishedなら続けて新しい担当の`summary`を送る。担当を失って未割当になる接続済みプレイヤーMCUへは`identify`を送り、旧設定・表示・操作・最終結果を無効化する。以後の`hello`では再割当せず、管理操作を待つ。同じセッション内の要求IDの履歴は維持する。

LEDの担当変更・交換・予備基板への付け替えでは、割当が実際に変わるUIDに確認対象が含まれる場合だけ、サーバーの確認対象を解除する。変更対象と無関係な機器の確認表示は継続する。新しい担当を受け取る接続済みMCUへ`CONFIG NODE false`、新担当がBot用ならそのBotの現在の正本FIFO使用量の`BUFFER`を送る。`CONFIG`自体でMCUの確認周期を停止し、全出力の消灯と演出状態の初期化を行うため、直前の`CLEAR`は送らず、旧担当の`BUFFER`も復旧しない。未割当になるMCUには`identify`を送り、確認表示・一時設定を解除して未設定へ戻す。自動仮割当や再接続による通常のLED設定も`CONFIG NODE false` → 新担当がBot用なら`BUFFER`の順とする。実機確認中の一時設定は4.2.2とLEDノード仕様に従う。

#### 4.2.2. 実機の確認表示

Web管理画面でUIDを選択し、`SetDevicePreview`で実機の確認表示を行う。サーバー全体で同時に1台だけを対象とし、開始条件を満たす別のUIDを選択した場合は、現在の確認表示を終了・復旧してから新しい対象を開始する。条件不成立なら現在の確認表示を変更しない。同じ対象への再要求は確認表示を継続し、停止要求は対象がなくても成功とする。共通の`identify`は通信上の識別要求のままとし、確認表示専用のMCU命令は追加しない。

未割当の予備基板も、既存の担当を解除せずに確認できる。確認用ノードIDは、割当済みなら現在の担当、未割当なら機器種別に応じたP1を使用する。未割当への`config`・`CONFIG`は表示のための一時設定とし、P1が既に使用中でも送信できる。正式な対応表、既存P1の担当・操作状態・ゲーム状態、および自動仮割当の対象外UID情報は変更しない。SnapshotのMCU欄は未割当のままとし、一時設定は実機確認欄にだけ公開する。一時設定をゲーム操作の受理や通常通知の送信先として使用しない。

| 対象 | 確認表示の通知 |
|---|---|
| プレイヤーMCU | 確認用ノードIDの`config(mode=auto, preview=true)`、新しい同期世代の`reset`、現在の`phase`、確認用の`status`を順に送信。MCUは通常画面に代えてノードの表示名・色を大きく点滅させる。FIFOは割当済みなら正本、未割当なら空配列を通知する |
| LED制御MCU | 確認用ノードIDの`CONFIG NODE true`を送る。MCUが表示・演出状態を初期化してGPIO0・1の1秒周期の確認表示を開始する。サーバーから確認用の`LIGHT`・`BUFFER`・`CLEAR`を周期送信しない |

プレイヤーの確認用`status`は、割当済みなら現在の担当の正本値、未割当なら`score=0`・`ready=false`と実際のゲームの残り秒数を通知する。未割当へのスコア・準備完了状態は表示専用であり、正式なP1の値を参照・変更しない。確認中は結果を表示せず、未割当・割当済みのいずれにも`summary`を送らない。

確認表示のためのダミーパケットは生成・送信しない。正本FIFO・パケット管理・PID採番・生成数・得点を変更せず、PIDの値による確認表示の判別も行わない。確認中もゲームフェーズ・操作モード・ランキング資格・確定結果を変更しない。プレイヤーはautoかつpreview=trueのため`send`・`ready`を送らず、同期世代の発行・更新と要求照合は通常の規則に従う。

割当済みプレイヤーの確認終了時は、現在の担当・モードの`config(preview=false)`、新しい同期世代の正本FIFOの`reset`、現在の`phase`、現在の`status`の順に復旧し、Finishedなら続けて新しい同期世代の`summary`を送る。未割当プレイヤーには`identify`を送り、一時設定・表示・同期状態を無効化して未設定へ戻す。以後の`hello`は通常の未割当機器として扱い、確認表示だけを理由に正式なP1へ対応付けない。

LEDの確認終了時は、正式に割当済みなら現在の担当の`CONFIG NODE false`を送り、Bot用なら続けてそのBotの現在の正本FIFO使用量の`BUFFER`を送る。未割当なら`identify`で一時的なNODE・PREVIEWを解除して未設定へ戻す。`CLEAR`はPREVIEWを変更しないため、確認解除には使用しない。担当変更時は4.2.1の新担当への再設定に解除を統合し、旧担当の`BUFFER`は送らない。過去の`LIGHT`は再現しない。先にサーバーの確認対象を解除し、未割当MCUの続く`HELLO`で確認表示を再開しない。

次の場合は確認表示を自動終了する。

- 受理されたStartでPlayingへ遷移する前、ゲームのReset時。
- 対象プレイヤーをmanualへ切り替える前。
- 対象の割当を実際に変更・交換・解除する前。未割当の対象への自動仮割当・管理操作による割当も含む。
- 対象MCUから`hello`・`HELLO`の再受信または`resync`があった場合、および対象セッションの切断時。

開始可否などの操作条件は通常どおり検証し、拒否された操作だけを理由に確認表示を終了しない。Startではpreview=falseへの再設定と正本への復旧、または未割当機器の一時表示の解除を、`phase(Playing)`より先に送信キューへ登録する。モード・割当変更、HELLO・RESYNCへの通常の設定・同期が確認解除も含めて正本を復旧する場合は、それを復旧処理として用い、重複した同期は不要とする。Resetで確認中の割当済みプレイヤーには`config(preview=false)`を先に送り、以後は通常の`phase(Preparing)`、空FIFOの`reset`、初期値の`status`で復旧する。未割当プレイヤーの確認終了では、先に確認対象を解除してから`identify`を送り、その応答の`hello`では確認表示を再開しない。Resetで確認中の割当済みLEDには`CONFIG NODE false`を送り、Bot用には初期化後の件数の`BUFFER 0`を続ける。確認中の未割当LEDは`identify`で一時設定を解除する。切断時は確認対象を解除し、MCUは確認モードを初期化する。再接続時は通常の設定・同期を行い、確認表示を自動再開しない。復旧中の送信失敗は2.4の通常の切断処理に従う。

#### 4.2.3. デバイス対応表の保存・復元

対応表と自動仮割当の対象外UIDは、1つのUTF-8のJSONファイルへ保存する。保存先は起動設定で指定でき、既定は作業ディレクトリからの相対パス`data/devices.json`とする。`main`が起動時の読込と検証を行い、`app`は復元された情報を正本として管理し、以後の変更と保存を直列に処理する。実行中にファイルを再読込する機能や、保存専用の管理操作は設けない。

保存形式は次のとおりとする。割当済み、または自動仮割当の対象外である機器を保存し、未接続の機器も含める。未割当かつ対象外ではない機器は保存せず、再起動後に接続・識別された時点で再登録する。

```json
{
  "version": 1,
  "devices": [
    {"deviceId": "001122334455", "kind": "led", "nodeId": "B1", "autoAssignExcluded": false},
    {"deviceId": "112233445566", "kind": "player", "nodeId": null, "autoAssignExcluded": true},
    {"deviceId": "AABBCCDDEEFF", "kind": "player", "nodeId": "P1", "autoAssignExcluded": false}
  ]
}
```

| フィールド | 保存する値 |
|---|---|
| version | ファイル形式のバージョンを表す整数。現行は1 |
| devices | Device ID順の配列。保存対象がなければ空配列 |
| deviceId | MCUのUIDと同じ大文字・ゼロ埋め12桁の16進文字列 |
| kind | `player`または`led` |
| nodeId | 4.2.1で機器種別ごとに許可された`P1`などの文字列。未割当はnull |
| autoAssignExcluded | 未割当時に自動仮割当の対象から外すかを表すboolean。交換元や管理操作で解除されたUIDの情報も保持する |

全フィールドを必須とし、型の暗黙変換や欠落時の補完は行わない。UIDは機器種別をまたいで重複させず、割当先は機器種別ごとに一意とする。対象外フラグは割当先とは別に保持し、明示的な再割当だけでは消去しない。接続ポート・Session ID・接続状態・同期世代・操作モード・準備完了状態・確認表示の一時設定・ゲーム状態は保存しない。

保存と変更の確定は次の順で行う。

1. 受理条件を検証し、変更後の対応表と対象外情報の候補を作る。自動仮割当も同じ手順を使う。
2. 保存内容が変わる場合は、候補全体を保存先と同じディレクトリの一時ファイルへ完全に書き込み、そのファイルの`fsync`とクローズに成功してから、既存ファイルを原子的に置き換える。親ディレクトリがなければ作成し、新規作成した各階層のディレクトリについて、その親ディレクトリも同期して作成を永続化する。交換・付け替えの複数UIDの変更は、1回の置換にまとめる。
3. 置換後に保存先の親ディレクトリを`fsync`し、その成功を保存完了とする。保存内容が同一なら書込・置換・同期を省略し、既存の同じ対応への再要求の規則に従う。
4. 割当先が実際に変わるUIDに確認対象が含まれる場合は、先にサーバーの確認対象を解除する。この時点ではMCUへ通知せず、旧担当の通常表示を復旧しない。無関係な機器の確認表示は維持する。
5. 候補をメモリ上の正本へ一括反映し、4.2.1に従って操作モード・準備完了状態を変更して、新しい割当に従ってMCUを再設定する。未割当になるMCUには`identify`を送る。これらを同じ入力イベント内で処理し、管理操作の成功応答はその後に行う。

置換前のディレクトリの作成・同期、一時ファイルの作成・書込・同期・クローズ、または原子的な置換そのものに失敗した場合は、既存の保存ファイルと正本を維持し、一時ファイルを復元には使用しない。管理操作では保存失敗をログへ記録してエラーを返し、Web APIは`500 internal_error`へ対応付ける。自動仮割当では識別情報・接続状態を維持して未割当で待機させ、ログへ記録する。既存機器の動作を継続し、4.5の仮割当の契機で再試行する。保存失敗だけを理由に自動仮割当の対象外へ変更しない。

置換に成功した後の親ディレクトリの同期に失敗した場合は、保存結果を不明とする。旧ファイルの維持や永続化完了を保証せず、ファイルを旧内容へ書き戻さない。候補を正本へ反映せず、その操作に伴う確認対象・操作モード・準備完了状態の変更とMCUへの通知、管理操作の成功応答を行わない。管理操作と自動仮割当のどちらでも理由をログへ記録し、以後の入力イベントの処理と送信要求を停止してHTTP・シリアル接続を終了し、サーバープロセスを異常終了する。再起動時は通常の検証・復元手順で保存ファイルを読み込み、旧版・新版のどちらが残っていても全件を検証してから起動する。失敗した管理操作を自動再送しない。

空きの発生などに続く別機器の自動仮割当は、それぞれ独立した保存・確定とする。その失敗で、既に保存・確定した管理操作や他の機器の割当を取り消さない。保存完了後のMCUへの送信失敗は2.4に従い、保存済みの対応表を戻さない。ゲームのReset・切断・確認表示の開始と停止自体は保存内容を変更しないため、保存を要求しない。ただし、Preparingへの遷移などを契機に自動仮割当が成立する場合は、その変更を保存してから確定する。

起動時はHTTP・シリアル通信の受付前に、指定した保存ファイル全体を読み込み、構文・必須フィールド・型・バージョン・UID形式・機器種別・割当先の範囲・UIDと割当先の重複を検証する。全件が正常な場合だけ一括で復元する。ファイルが存在しない場合に限り、初回起動として空の対応表から開始する。空ファイル、不正な内容、未対応バージョン、権限不足などの読込失敗では理由をログへ出力して起動を中止し、空の対応表への置換や部分的な復元を行わない。

復元した機器はSnapshotにも未接続として公開し、Session IDと同期状態を新たに作るのは接続・識別後とする。未接続でも保存された割当先は予約済みとして扱い、他UIDへ自動仮割当しない。UIDと機器種別を照合し、保存された種別と異なる識別応答のセッションは終了して保存内容を維持する。割当済みなら通常の初期同期を行い、未割当かつ対象外なら管理操作を待つ。ゲームは3.1の初期状態で開始し、全プレイヤーをauto・未準備とする。確認表示を再開しない。

### 4.3. Tick

**発生元：** `app`の100ms周期タイマー

**受理条件：** 時刻更新は全フェーズで受け付け、ゲーム進行処理はPlaying中のみ実行する。

**処理：**

1. `app`は4.1の規則に従って処理開始時点の時刻を求め、ゲーム終了時刻より前の未処理区間を処理対象とする。
2. 対象区間内で最も早く期限を迎えるパケット生成または自動転送を選択する。
3. 生成の場合はゲームルールに従ってパケットを生成し、自動転送の場合は対象Botまたは自動操作中のプレイヤーのFIFO先頭の転送を試行する。
4. パケットの生成・移動・配送・破棄をゲーム状態へ反映し、得点規則に従ってスコアを更新する。
5. 次回の生成・転送期限を更新し、対象区間内の未処理の期限がなくなるまで2〜5を繰り返す。
6. ゲーム時間が終了している場合はFinishedへ遷移し、終了時刻以降の生成・転送・加点を行わない。

`app`はゲーム上の出来事に基づいて、MCUへの通知を生成する。LEDの確認表示の周期はMCUが管理し、Tickから確認用の周期送信は行わない。Tick自体に対する外部応答は生成しない。

処理周期の判定にはTickの回数ではなく経過時間を使用する。

Tickが遅延した場合も、未処理の生成・転送を期限順に処理する。新たに生成・到着したパケットを、その生成・到着時刻より前の期限で転送してはならない。管理操作やMCUイベントの前処理も同じ時間進行規則を用い、既に処理した区間を再処理しない。

生成・自動転送の期限は以下の規則で設定する。

- 各プレイヤーの最初のパケット生成はStartの1秒後とし、以後はゲームルールに従う周期で生成する。ゲーム終了時刻と同時刻の生成・転送は行わない。
- Botまたは自動操作中のプレイヤーのFIFOが空から非空になった場合、その到着時刻から`1 / 処理速度`秒後を最初の転送期限とする。空のFIFOには転送期限を設定しない。
- 転送・破棄によって先頭を取り除いた後もFIFOが非空の場合は、その処理時刻から`1 / 処理速度`秒後を次回の転送期限とする。FIFOが空になった場合は転送期限を解除する。
- FIFOが非空のプレイヤーを手動操作から自動操作へ切り替えた場合、切替時刻から`1 / 処理速度`秒後を最初の転送期限とする。手動操作へ切り替えた場合は自動転送期限を解除する。
- 生成・転送の期限が同じ場合は、パケット生成、Botの自動転送、プレイヤーの自動転送の順に処理する。同じ種類の処理はノードIDの昇順で行う。この規則はゲーム内の期限が同じ処理に適用し、外部入力イベントの先後は4.1に従う。

### 4.4. SEND

**発生元：** プレイヤーMCU

**入力：** Session ID、同期世代（`sync`）・要求ID（`rid`）・PID・転送先を含むSENDメッセージ

**受理条件：**

- ゲームフェーズがPlayingである。
- ゲーム時間が終了していない。
- Session IDがプレイヤーノードに対応している。
- `sync`が当該セッションの現在の同期世代と一致する。
- 対象プレイヤーノードが手動操作中である。
- SENDの内容がFIFOおよびゲームルールに適合している。

SENDのPIDは現在の送信元FIFO先頭と一致する必要がある。配送・破棄済みのパケットやReset前のゲームのPIDを指定した要求は拒否する。ResetをまたいでPIDを再利用しないため、受信が遅れた旧ゲームのSENDを新ゲームへ適用しない。

要求IDはSession IDと組み合わせて扱い、同じセッション内の重複要求を再適用しない。同期世代は新しいRESETを送信キューへ登録する時点で更新し、旧世代のSENDはPIDが先頭と一致しても実行しない。同期世代不一致の新規SENDには要求の`sync`・`rid`で`result(ok=false)`だけを返し、追加のRESETを発行しない。同期世代・要求IDの形式・発行・重複処理はプレイヤー通信仕様に従う。

**処理：**

1. `app`はSession IDから送信元論理ノードを特定する。
2. `app`は同期世代、FIFO先頭および転送先の妥当性を検証する。
3. `app`はゲームルールに従い、転送・配送完了・パケットロスを判定する。
4. `app`は判定結果を送信元と転送先のFIFO、およびパケットの管理情報へ反映する。
5. 配送完了時は、ゲームルールに従って発信者・中継者のスコアを更新する。

**出力：**

- `app`は受信した同期世代と要求IDをそのまま付けた`RESULT`の送信を`serial`へ要求する。
- `app`はパケット移動によって表示内容が変わったMCUの同期処理を実行する。
- `app`はパケットが通過した論理リンクに対応するLED制御MCUへの演出を、LEDノード仕様の`LIGHT`として要求する。宛先色・方向・点灯パターンは同仕様に従う。

初回に処理するSENDについては、成功・失敗にかかわらず、既定プロトコルが要求する応答の送信を`serial`へ要求する。重複要求はプレイヤー通信仕様に従って無視する。送信不能時は2.4に従ってセッションを終了し、再接続時に再同期する。

`result.ok`は転送要求の受理を表し、最終目的地への配送成功を表さない。正当なSENDを受理し、送信元FIFOから先頭を取り除いた場合は、転送先でパケットロスとなる場合も`ok=true`を返す。不正なSENDやフェーズ・操作状態による拒否では`ok=false`を返し、要求によってFIFOを変更しない。パケットロスの条件と得点への影響はゲームルールに従う。

RESULTと表示同期の順序、再送、重複要求の扱いはプレイヤー通信仕様に従う。旧ゲームの要求はPIDの非再利用で、RESET前の要求は同期世代の照合で拒否する。MCUも同期世代と要求IDを照合し、取り消された要求の遅延応答を新しい要求へ適用しない。

### 4.5. MCUの接続種別判別とプレイヤーMCU接続・切断

サーバーは新しいシリアルセッションで接続先の種別を未確定として扱い、共通の識別要求`{"type":"identify","data":{}}`をLF終端で直ちに送信する。有効な識別応答を受信するまで1秒間隔で再送する。

`serial`は識別前の受信行を、プレイヤー通信仕様のJSON形式の`hello`と、LEDノード仕様の`HELLO UID`の両形式で判定する。有効な応答の形式から種別を確定し、UIDをDevice IDとして識別したら`identify`の再送を停止する。不正な入力は破棄して識別要求を継続し、片方の形式で解釈できないことだけを理由にセッションを終了しない。

種別未確定の受信蓄積上限は32768バイトとする。LEDの`HELLO`候補はLEDノード仕様の96バイト上限・文字・引数を検証し、LEDと識別した後はそのセッションに96バイト上限を適用する。HELLO待ちの行長超過・行途中の1秒の受信停止は当該行をLFまで破棄して識別要求を継続する。識別後は対応する通信仕様の異常時処理に従う。

初めて識別したUIDには、Preparing・Finishedで同じ機器種別の空いているノードIDを一つ選んで自動で仮割当する。既存の対応は未接続の機器の分も予約済みとして扱い、上書きしない。仮割当は4.2.3の保存に成功してから通常と同じ対応表へ確定し、専用の確定操作は設けない。置換前の保存失敗・置換自体の失敗では未割当で待機し、置換後の親ディレクトリ同期失敗では4.2.3に従ってサーバーを停止する。管理者が実機の表示・点灯を確認し、4.2.1の操作で本番の配置へ合わせる。

空きがない場合とPlaying中に初めて識別した場合は、UID・機器種別・接続状態を管理画面に公開して未割当のまま待機させる。まだ一度も割り当てていない接続済み機器については、Preparing・Finishedへの遷移時と、両フェーズで空きが生じた時点で仮割当を再試行する。管理操作の結果として未割当になったUIDは自動仮割当の対象から外し、再接続しても明示的な管理操作を待つ。この対象外情報も4.2.3に従って保存・復元する。

切断だけでは対応を解除しない。同じUIDの再接続では現在の対応表に従って元の役割へ戻す。予備基板への交換後に旧基板が再接続しても、旧UIDの割当を自動復元せず、交換先の担当を奪い返させない。対応表と自動仮割当の対象外となったUIDの情報はゲームのResetで維持し、サーバー再起動時も4.2.3の保存ファイルから復元する。

種別確定後は、その種別の通信形式・設定・同期手順を適用する。以下の表と4.6はプレイヤーMCUを対象とし、LED制御MCUの識別と識別後の手順はLEDノード仕様に従う。

| 入力イベント | appの処理 |
|---|---|
| Connected | Session IDを登録し、identifyを送信してMCUの識別処理を開始する |
| 識別完了（割当済み） | 対応表からプレイヤーノードを特定し、初期同期を実行する。自動仮割当した場合も同じ |
| 識別完了（未割当） | 上記の仮割当条件を満たせば割り当て、満たさなければ管理クライアントへ公開して待機 |
| Disconnected | Session IDを無効化し、対象MCUを未接続にする |
| 再接続後の識別完了 | 新しいSession IDを登録し、現在のゲーム状態に基づいて再同期する |

プレイヤーMCUの切断時は、対応するプレイヤーノードを自動操作へ切り替え、準備完了をfalseにする。

未割当のMCUからゲーム操作を受け付けない。再接続時は最新の対応表を使用し、3.3の規則に従って操作状態を維持する。無効化済みSession IDからの遅延イベントはゲーム状態に反映しない。

同じDevice IDを持つ接続が既に有効な場合、既存Session IDを維持し、新しいセッションを論理ノードに対応付けない。重複をログに記録し、重複セッションからゲーム操作を受け付けない。既存セッションの切断後に行われた識別は、通常の再接続として扱う。

MCUの接続・切断はゲームフェーズを変更しない。

### 4.6. プレイヤーMCUのIDENTIFY・HELLO・RESYNCと通信形式の不正

新しいセッションでは直ちに`identify`を送信し、有効な`hello`を受信するまで1秒間隔で再送する。MCUはどの状態でも`identify`で操作を停止して`hello`を返すため、100ms以上の切断検知に依存せず再識別できる。UIDをDevice IDとして識別したら`identify`の再送を停止し、4.5の仮割当・再接続規則を適用する。割当済みなら`config(preview=false)`、新しい同期世代と現在のFIFOの`reset`、現在の`phase`、現在の`status`の順に送信し、Finishedなら続けて`summary`を送る。未割当なら管理画面へ公開して待機する。HELLOの再受信でセッションや要求IDの履歴を初期化しない。

HELLO待ちに受信した旧SEND・READY・RESYNCはゲーム操作や要求IDの履歴に反映せず破棄し、切断せずに識別要求を継続する。不正な行や受信途中の旧データもプレイヤー通信仕様に従って破棄する。

通常表示中の割当済みMCUからの`resync`には、全フェーズで現在のFIFOの`reset`、現在の`phase`、現在の`status`の順に返し、Finishedなら新しい同期世代の`summary`を続ける。確認中の対象からの`resync`では先に確認を終了し、4.2.2の復旧手順で`config(preview=false)`から送る。同期を理由にゲーム状態・操作状態・受理済みの準備完了状態・要求IDの履歴を初期化しない。入力前の時間進行処理は4.1に従う。未割当の識別済みMCUからの`resync`は、実機確認中なら確認表示を終了して`identify`で一時設定を解除し、それ以外は対応付けを待つ。再試行周期、識別前のメッセージ、不正データおよび切断時の処理は[プレイヤー通信仕様](./player.md)に従う。

初期設定・再同期でMCUが`status`を取得できなかった場合や、Finishedの通常表示で`summary`を取得できなかった場合も、プレイヤー通信仕様の3秒の取得期限に従って`resync`が送信される。サーバーはこれを通常の再同期要求として処理し、値が変わっていなくても現在の`status`と、Finishedなら確定結果の`summary`を返す。正常な無通信を検出するための定期的な`status`・`summary`送信は追加しない。

識別後の通信データのJSON形式・必須フィールド・型・範囲の不正は`serial`が検出し、当該セッションを終了して`Disconnected`を通知する。HELLO待ちの不正な入力は切断せず破棄する。形式が正しいSENDの同期世代・フェーズ・操作状態・FIFO・隣接関係による拒否は`app`が判定する。

### 4.7. READY（準備完了要求）

**発生元：** プレイヤーMCU

**入力：** Session ID、最後に適用したRESETの同期世代（`sync`）

**受理条件：**

- Session IDが現在有効で、識別・プレイヤーノードへの割当が済んでいる。
- ゲームフェーズがPreparingである。
- 対象プレイヤーノードがmanualである。
- 当該セッションでRESETを発行済みで、要求の`sync`が現在の同期世代と一致する。

`app`は4.1の入力イベントの処理単位で条件を検証し、成立した場合だけ対象ノードの準備完了をtrueにする。要求の重複はtrueのままとし、操作モード・FIFO・スコア・ゲームフェーズ・SENDの要求ID履歴を変更しない。長押し時間の判定はMCUが担当し、サーバーは通信仕様の受理条件を検証する。

割当済みの有効なセッションから形式が正しいREADYを受信した場合、受理・拒否・重複にかかわらず、同じ確定状態から生成した現在の`status`を返す。RESULTや追加のRESETは送らない。同期世代不一致、auto、Preparing以外では準備完了を変更しない。未割当の識別済みセッションは無視して対応付けを待ち、HELLO待ち・無効な旧Session IDは既存の規則に従って破棄する。

ゲームのResetでは全員の準備完了を解除するとともに新しい同期世代へ切り替える。Reset前の遅延READYは、次ゲームもPreparingであっても準備完了を復活させない。READYとStart、Reset、切断、設定変更が競合した場合も、4.1の受け付け順で直列に確定し、各処理で最新状態を検証する。

## 5. MCUへの出力

### 5.1. 出力の分類

`app`が`serial`へ送信を要求する契機を以下に限定する。プレイヤーMCU向けメッセージは、プレイヤー通信仕様の`identify`、`config`、`reset`、`push`、`result`、`phase`、`status`、`summary`とする。LED制御MCU向けの命令は、共通のJSON形式の識別要求`identify`と、LEDノード仕様の`CONFIG`、`LIGHT`、`BUFFER`、`CLEAR`とする。共通の`identify`を除き、プレイヤー向けのJSON形式・同期世代・要求ID・フェーズ・スコア・残り時間・確定結果の通知をLED制御MCUへ適用しない。

| 分類 | 送信契機 |
|---|---|
| 要求応答 | MCUから受信したSENDへのRESULT、READYへのSTATUSなど |
| 初期化・復旧 | MCU識別完了、再接続、再同期 |
| 状態変更通知 | MCUに表示させるゲーム情報の変更 |
| 演出指示 | パケットの論理リンク間移動など、表示すべきゲーム上の出来事。LEDノード仕様の命令を使用 |
| 実機確認 | 4.2.2のpreview設定による確認表示の開始・停止と正本表示への復旧。周期描画はMCUが行う |

状態変更通知は、ゲーム状態が変更されたという理由だけでは送信しない。MCUに提示する情報の更新が必要な場合に送信する。

### 5.2. 状態変更と通知先

| ゲーム上の出来事 | appが更新を評価する対象 | 仕様の扱い |
|---|---|---|
| パケット生成 | 生成元プレイヤーMCUのFIFO表示 | 初期実装 |
| パケット転送 | 送信元・転送先MCUのFIFO表示 | 初期実装 |
| パケット配送完了・破棄 | 送信元MCUのFIFO表示 | 初期実装 |
| フェーズ変更 | 接続・識別・割当済みのプレイヤーMCU | 初期実装 |
| BotのFIFO使用量変更 | 対象BotのLED制御MCUへのBUFFER通知 | LEDノード仕様に定義済み |
| プレイヤーの操作状態変更 | 接続済みの対象プレイヤーMCUへのconfig.mode設定 | 初期実装 |
| スコア・残り時間・準備完了状態の変更 | 対象プレイヤーMCUへのstatus通知 | 初期実装 |
| Finishedへの遷移・Finished中の同期 | 対象プレイヤーMCUへの確定結果summary通知 | プレイヤー通信仕様に定義済み |
| パケットのリンク間移動 | 対応するLED制御MCUへのLIGHT指示 | LEDノード仕様に定義済み |

FIFO表示の同期範囲、送信メッセージ、更新順序はシリアル通信プロトコル仕様に従う。

`app`は通知対象のSession IDを特定し、送信対象が未接続の場合は、そのセッションへの送信を要求しない。

Start、Finish、ゲーム時間終了、およびResetによるフェーズ変更は`phase`で通知する。自動操作中のプレイヤーMCUも対象とする。通常の初期設定・再接続時は`config(preview=false)`、`reset`、`phase`、`status`の順、再同期時は`reset`、`phase`、`status`の順、ゲームのReset時は`phase(Preparing)`、空FIFOの`reset`、初期値の`status`の順に送信する。Finishedへの遷移では`phase(Finished)`、`status`、`summary`を送り、Finishedの通常表示中の各同期手順でも`status`の後に新しい同期世代の`summary`を追加する。確認中の対象の復旧・解除は4.2.2に従う。関連する通知は同じ確定状態から生成する。

フェーズ通知だけではFIFOの同期世代や要求IDの履歴を変更しない。MCUはFIFO同期済みかつ取得済みフェーズがPlayingで、`config.mode`がmanualかつpreviewがfalseの場合だけ新規SENDを送信する。フェーズ通知で処理中の転送要求（SEND）の応答待ちを取り消さず、RESULTは既存の照合規則で適用する。準備完了要求（READY）の確認待ちは、プレイヤー通信仕様に従ってMCUがフェーズ変更時に解除する。サーバー側のSEND受理条件は4.4の規則を引き続き適用する。

`status`は対応付けられたプレイヤーの現在スコア・準備完了状態（`ready`）と、ゲームの残り秒数を同じ確定状態から取得し、3フィールドを毎回通知する。スコアは絶対値、準備完了はbooleanとし、autoノードの`ready`はfalseとする。残り秒数は`ceil(max(0, ゲーム時間 - 経過時間))`とし、Preparingではゲーム時間、Finishedでは終了時点の値を保持する。時間満了時は0、手動Finish時はその時点の残り秒数とする。値の型と範囲はプレイヤー通信仕様に従う。

初期同期・再同期・フェーズ変更時と、4.7で応答対象となるREADYの受信時は、値が変わらなくても現在の`status`を送信する。それ以外は、入力イベント確定後にスコア・表示する残り秒数・準備完了状態のいずれかが変わったプレイヤーMCUに送信する。Tick遅延時は最新値だけを通知し、同一イベント中の途中経過を蓄積して送らない。自動操作中のスコアも通常どおり通知する。MCUは独自の加点・カウントダウンを行わず、通知された値を表示する。`status`の通知自体は操作モードやランキング対象の判定を変更しない。

自動操作中のプレイヤーMCUについても、FIFO表示を同期する。MCUからのSENDによらず先頭が削除された場合は、`reset`で同期する。

`summary`は3.1で確定した最終スコア・順位・ランキング資格を、そのセッションの現在の同期世代とともに送る。eligibleとrankの対応・型・範囲はプレイヤー通信仕様に従う。Finishedの通常表示ではautoのプレイヤーも通知対象とし、現在のモードによって確定済みのランキング資格を上書きしない。Preparing・Playing・確認表示中・未割当MCUには送らない。終了演出の内容や時間はMCU側の実装に委ねる。

正当なSENDによる送信元の先頭削除は対応する`result(ok=true)`で通知する。同期世代が一致した新規SENDを拒否した場合は、割当済みであれば`result(ok=false)`の後に新しい同期世代と現在のFIFOの`reset`を送信する。同期世代不一致の拒否では、先行するRESETによって新しい世代を通知済みのため追加のRESETは送信しない。

RESETに使用するFIFOコピーの確定・現在の同期世代の切替・送信キューへの登録は、他の入力イベントを挟まずに行う。Finishedの通常表示でRESETを送る場合は、その後にphase・status・新しい同期世代のsummaryを続けて同じ確定状態から登録する。同期世代はゲームのResetやセッション再接続、サーバー再起動でも再利用しない。初期同期、末尾追加、対応付け変更を含む具体的な送信順序と同期範囲は、プレイヤー通信仕様を正本とする。

### 5.3. LED制御とBot混雑度表示

LED制御MCUの担当リンク・GPIO、経路演出の速度・尾の減衰・重なり時の加算、およびシグナルタワーの表示色は[LEDノード仕様](./led.md)に従う。

パケットが通過した論理リンクについて、`app`は同仕様の対応表からLED制御ノードを特定し、`LIGHT`の隣接ノード・パケットの最終宛先・移動方向へ変換する。パケットの移動が手動SEND、自動プレイヤー、Botのいずれによる場合も同じ対応表を用いる。

BotのFIFO使用量が変化した場合、`app`は対象BotのLED制御MCUへ`BUFFER`で現在の件数を通知する。色の判定・点灯はLED制御MCUが同仕様に従って行う。`CONFIG`による制御ノードの設定と`CLEAR`による表示消去もLEDノード仕様に従う。

LED制御MCUも4.5の共通識別要求`identify`を受け付け、独自プロトコルの`HELLO UID`で応答する。UIDの自動仮割当・管理操作による交換と、通常設定時の命令順序は4.2.1・4.5に従う。`CONFIG NODE PREVIEW`のPREVIEWは小文字のtrue・falseを必須とし、通常はfalse、実機確認中だけtrueとする。有効な`CONFIG`ではMCUが同じNODE・PREVIEWへの再設定でも表示・演出状態を初期化する。確認中の通常の`LIGHT`・`BUFFER`はMCUが適用せず、確認周期はMCU内で管理する。実機確認と終了時の復旧は4.2.2とLEDノード仕様に従う。

ゲームのResetではLEDの確認対象を解除する。確認中の割当済みLED制御MCUには現在の担当の`CONFIG NODE false`、Bot用には続けて初期化後の`BUFFER 0`を送る。確認中の未割当MCUには`identify`を送る。通常表示中の接続・識別・割当済みMCUには`CLEAR`、Bot用には`BUFFER 0`を続け、担当NODEを維持して`CONFIG`は再送しない。確認解除用の`CONFIG`と`CLEAR`を重複送信せず、過去の`LIGHT`を再現しない。未接続の機器は送信対象に含めず、再接続時の通常設定で現在の状態を通知する。4.5のプレイヤー向け接続・切断処理と4.6のプレイヤー向け同期手順はLED制御MCUには適用しない。

LED制御MCUは起動・`identify`受信・USB未接続の100ms連続検出でpreview=falseへ戻し、確認周期を停止して消灯・未設定へ移る。有効な`CONFIG`まで1秒間隔で`HELLO UID`を送る。不正な`CONFIG`、命令を判別できない入力、行長超過、不正文字、行途中の1秒の受信停止でも同じ初期化を行い、同じセッションから`HELLO`で再識別する。種類を判別できる不正な`LIGHT`・`BUFFER`などはその行だけを破棄し、NODE・PREVIEWと表示状態を維持する。同一セッション・同一UIDのHELLO再受信ではセッション・対応表を維持して通常設定をpreview=falseで再実行し、UID変更ではセッションを終了する。重複UIDの接続では既存Session IDを維持する。LEDと識別済みの接続から不正な入力・行長超過・行途中の1秒の受信停止を検出した場合は、`serial`がセッションを終了して`Disconnected`を通知する。MCU側の不正行の破棄・LFまでの復旧・通常無通信の扱いはLEDノード仕様に従う。

LED制御MCUの同時`LIGHT`演出は全出力合計128件を上限とし、満杯なら新しい演出だけを破棄する。表示上の省略でゲーム上の転送・配送・得点を取り消さず、演出枠の受信確認や再送は追加しない。

## 6. 異常時の処理

| 事象 | 検出主体 | 処理主体と動作 |
|---|---|---|
| 不正な管理操作 | app | appが拒否理由を返し、webがHTTPレスポンスへ変換 |
| 不正なSEND | app | appが転送を拒否し、serial経由で規定のRESULTを返す |
| 受理条件を満たさないREADY | app | 準備完了を変更せず、割当済みの有効なセッションには現在のSTATUSを返す |
| 不正な通信データ | serial | serialが通信プロトコルに従って処理 |
| MCU切断 | serial | appが接続状態を更新。プレイヤーMCUの場合は対象プレイヤーを自動操作・準備未完了へ変更 |
| MCU再接続 | serial | appがデバイスを再識別し、表示状態を再同期 |
| 送信キュー溢れ | serial | Sendがerrorを返し、serialが当該セッションを終了してDisconnectedを通知。appは切断処理を行い、再接続時に再同期 |
| シリアル書込失敗 | serial | serialが当該セッションを終了してDisconnectedを通知。appは切断処理を行い、再接続時に再同期 |
| ゲーム中のReset | app | appが4.2の範囲でゲーム状態を初期化し、旧ゲームの要求が新状態へ適用されないようにする |
| Tick遅延 | app | appが4.3に従って実際の経過時間に基づく補正を行う |
| Device IDの重複接続 | app | 既存の対応を維持し、重複セッションのゲーム操作を拒否 |
| デバイス対応表の置換前の保存失敗・置換自体の失敗 | app | 操作に伴う割当・対象外情報・操作モード・準備完了状態・確認表示を変更しない。管理操作にはエラーを返し、自動仮割当は未割当で待機。既存機器は動作を継続 |
| 対応表の置換後の親ディレクトリ同期失敗 | app・main | 保存結果不明として成功応答と操作に伴う変更・MCU通知を行わず、ログを記録してサーバーを異常終了。再起動時に保存ファイル全体を検証・復元 |
| 起動時の対応表の破損・読込失敗 | main | 理由をログへ記録して起動を中止。ファイル不存在の場合だけ空の対応表で起動 |
| 次ゲーム分のPID不足 | app | Startを拒否し、サーバー再起動が必要であることを管理クライアントへ返す |

通信失敗のみを理由として、確定済みのゲーム状態を取り消さない。

ゲーム状態の再同期には、`app`が保持する正本を使用する。

ログは初期実装では標準出力に出力する。

## 7. 後日定義する範囲と関連仕様

### 7.1. 後日定義する範囲

以下の詳細は関連仕様で後日定義する。ゲームルールの追加・修正は`rules.md`で行い、本仕様に独立したルールを追加しない。

| 項目 | 決定が必要な内容 |
|---|---|
| デバイス対応付け | Web管理画面の詳細。対応表と自動仮割当の対象外UIDの保存・復元は4.2.3に定義済み |
| LED制御の残件 | 各テープのLED数を長さ確定後に記入。命令の形式・引数、起動・識別・設定・切断・ゲームResetの手順、実機確認、異常時処理と同時演出数の上限はLEDノード仕様に定義済み |
| スコア保存 | 外部保存の方法とReset前の保存確認 |

スコアの外部保存・再起動時の復元は後日定義する。Device IDの対応表と自動仮割当の対象外UIDは4.2.3に従って保存・復元し、ゲームのResetでは消去しない。
